### Equipment attributes to keep separate

Do not infer one property from another or collapse these into one overloaded machine label:

- **Loading/resistance system:** selectorised/pin-selected, plate-loaded, fixed-weight, adjustable, bodyweight or unknown, as applicable.
- **Movement mechanics:** fixed-path, converging handle path, independent/iso-lateral arms and other reviewed mechanics where relevant.
- **Physical orientation:** for example, 45-degree sled, horizontal seated or vertical leg press.
- **User fit/setup:** seat and pivot adjustment, pad position, handle/attachment, stance and other details needed to identify the actual configuration.
- **Location/access:** Gym, Home or another user-named location; availability is user-owned and may change independently of the system definition.

The owner has confirmed the intended Gym environment contains both pin-selected and plate-loaded equipment. The data model must represent both. This does not identify the loading system or geometry of any particular machine. No machine instance should be pre-filled with an inferred configuration.

## 5. Injury-aware metadata — minimum curation requirements

Legacy source muscle keys cannot support injury-aware alternative selection. They do not separate primary and secondary involvement, do not describe stabilisation and do not capture all the ways an exercise loads a body area.

Each reviewed exercise/variation needs explicit, evidence-backed fields covering, as applicable:

- Primary and secondary muscle/body-region involvement, separately labelled.
- Joint actions and movement pattern.
- Body position, support points, stance, laterality and relevant range of motion.
- Stabilisation and balance demands.
- Foot contact, foot pressure and ankle/calf contribution.
- Weight-bearing, impact/landing and propulsion demands.
- Setup/bracing demands and meaningful machine/body-position constraints.
- Equipment requirements and exact supported configurations.
- Cautions/limitations with provenance, reviewer scope and supporting evidence.

A body-area restriction (for example, a user-reported calf restriction) must be evaluated against direct and secondary loading plus support, balance, foot-pressure, impact, propulsion, weight-bearing, position and bracing demands. A primary-muscle list alone is insufficient.

Unknown or unreviewed fields mean **not assessed**. Do not mark an exercise as an injury-aware alternative based on name similarity, broad category, a “low impact” label, muscle overlap, equipment availability or an AI-generated guess. The app cannot promise zero effect on an area or provide medical clearance.

The user-reported restriction persists until the user explicitly updates or clears it. A readiness result must never silently clear it. If no alternative has sufficient reviewed evidence, provide Remove/skip or Keep restricted rather than suggesting an unverified movement.

## 6. Proposed catalogue record contract — still to be reviewed

This is a field checklist, not a production schema approval.

### System equipment definition

A system equipment definition should have a stable opaque ID, canonical label, family/category, supported configuration dimensions, provenance, review status and source evidence. It must not represent a user's physical machine or location inventory.

The current catalogue-delivery payload supports exercise definitions and variations, including string-valued requiredEquipmentDefinitionIds; it does not carry or resolve a system equipment-definition collection. A future payload expansion must validate that every required equipment ID resolves to a definition in the same released catalogue.

### User equipment access record

A personal equipment record should be scoped to the user/profile and a named location; identify either a system equipment-definition ID or a user-described custom item; record access/availability; and store configuration details only when the user has provided them. Legacy migrated gear records such as gym-equipment and gym-custom-equipment must remain intact and must not be assumed to satisfy the new record contract.

The current equipment store has only a by_module index and is already included in full V2 backup. It is a generic user-data store, not a validated system-equipment catalogue. A namespaced record type in that store is a candidate for personal access entries, subject to migration, integrity and restore tests. Do not write system catalogue definitions into it.

### Exercise definition and variation

Exercise definitions and meaningful variations use separate opaque IDs. Variation IDs are created only for curated differences that affect execution or interpretation. Do not generate a Cartesian product of every implement, grip, stance, position and machine attribute. Prescription/performance values remain separate from identity.

## 7. Explicit unresolved decisions before production IDs

1. **Equipment payload storage:** keep system equipment definitions in the verified immutable release asset and read them from its release cache, or add a dedicated IndexedDB materialisation store. The current equipment store must remain personal/legacy equipment data. A new store/index would require a new database-schema and backup/restore gate.
2. **Catalogue payload evolution:** determine the next payload schema version, validation rules and foreign-key checks needed to carry equipmentDefinitions. The existing catalogue-delivery approval did not create equipment definitions or approve a new database/backup contract.
3. **Controlled vocabularies:** curate body regions, muscles, joint actions, movement patterns, support, stabilisation, balance, impact, weight-bearing and equipment attributes with appropriate evidence and reviewer input.
4. **Custom equipment:** decide how user-described equipment remains visibly distinct from verified system equipment and how an uncertain custom item is handled by library matching.
5. **Ambiguous legacy labels:** resolve combined or configuration-dependent entries before IDs are minted (including Superman / Back Extension, Hip / Ankle Mobility, Chair Squat / Sit-to-Stand, High Knees options, cable-station descriptions and machine geometry).
6. **Reviewer process:** define who is qualified to approve exercise instructions and movement/safety metadata, verify credentials/scope, and retain exact content/version/digest review evidence. No reviewer is selected by this document.
