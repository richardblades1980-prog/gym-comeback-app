**Date:** 2026-11-19  
**Development implementation baseline:** `c2ac43b6d23219b67396daf7cfa89578127f34eb`

## 1. Intended outcome

Publish V21.2 at:

`https://richardblades1980-prog.github.io/gym-comeback-app/v21.2/`

while retaining V21.1 at the repository root:

`https://richardblades1980-prog.github.io/gym-comeback-app/index.html`

Both paths use the `https://richardblades1980-prog.github.io` browser origin. V21.1 remains the fallback. The V21.2 owner trial starts with an empty IndexedDB user-data space and does not run legacy migration. Existing `gym-comeback-*` localStorage keys must remain unchanged.

## 3. Release artifact contents

Do not publish the full development branch as the Pages source, and do not publish `v21.2/` as the whole site. The assembled site artifact must have this shape:

- Repository root: exact V21.1 `index.html`, manifest, icons, artwork and other root assets from the agreed `main` baseline.
- Repository root `sw.js`: the reviewed dual-app version from `V21.2-development`. It must bypass every `/gym-comeback-app/v21.2/` request, retain only its `gym-comeback-v21-1b-` cache namespace during activation cleanup, and precache the root V21.1 `index.html`.
- `v21.2/`: the complete approved V21.2 subtree from the reviewed implementation commit, including manifest, PNG/SVG/Apple icons, assets, app files and scoped worker.

No other development-only source or test folders are required in the published artifact.

## 4. Choose the deploy route only after Settings → Pages is inspected

- If the configured source is a branch/folder, do not repoint it to the development branch as a shortcut. Prepare a tightly scoped, reviewed release from the selected production baseline. A main-branch update or release PR is a production change and needs separate explicit approval.
- If the agreed route is GitHub Actions, GitHub Pages must be configured to use Actions. Adding that workflow and changing the Pages source are separate controlled actions; a manual deployment should accept an exact approved release SHA/artifact, not deploy every development push.
- Do not create a deploy workflow, change Pages settings, merge, or publish as part of this design-only plan.

## 5. Pre-publication validation of the assembled artifact

Before any deploy:
1. Assemble the artifact from the exact source SHAs listed above.
2. Verify root `index.html` is byte-for-byte the selected V21.1 file; verify root `sw.js` is the reviewed coexistence worker; verify the full V21.2 subtree matches the approved development source.
3. Run the full Chromium browser suite against the assembled artifact served under `/gym-comeback-app/`. Include root V21.1 install, V21.2 install, root worker update, cache ownership, offline cold starts and seeded legacy localStorage preservation.
4. Run backup validation against the same source commit.
5. Record SHA, artifact digest, validation run links, Pages source and rollback target.

## 6. Live-host acceptance after a separately authorised publication

On the exact intended URL:
- Confirm HTTPS and successful entry-page, manifest, PNG, SVG, Apple touch-icon, script and stylesheet responses.
- Confirm manifest identity/start/scope and all icon URLs resolve beneath `/gym-comeback-app/v21.2/`; check content types and that the returned raster files decode at their declared dimensions.
- Confirm V21.2 controller script is `/gym-comeback-app/v21.2/sw.js`; confirm V21.1 remains controlled by the root worker.
- In a clean V21.2 database, verify user-data stores remain empty and migration marker absent. Confirm legacy V21.1 localStorage values remain byte-for-byte unchanged; do not click migration.
- On available iPhone Safari and Android Chrome devices, test Add to Home Screen/Install, icon rendering, standalone launch, app navigation, reload and cold offline start. Record actual device and OS/browser versions. Do not generalise one device's result to all.
- Create only clearly labelled disposable Gym/Hiking/Schedule test entries; download and validate a backup; reload and confirm persistence; clear only the test V21.2 profile if needed, not V21.1 localStorage.

## 7. Rollback

- Record the exact prior published artifact/commit before deploying.
- If the root V21.1 route, root service worker, V21.2 route, manifest, install or offline startup regresses, restore the recorded prior Pages artifact/commit using the configured deployment method.
- Do not delete V21.1 localStorage or V21.2 IndexedDB during rollback. Keep V21.1 available as the user's fallback.
- Re-run root V21.1 and V21.2 browser smoke checks after rollback.

## 8. Approval boundary

This document records a design only. It does not approve:
- changing Settings → Pages;
- adding or running a Pages deployment workflow;
- merging or pushing a release to `main`;
- publishing V21.2;
- migrating, deleting or overwriting any V21.1 data.

Each production-facing action requires separate explicit approval after the Pages source is confirmed.
