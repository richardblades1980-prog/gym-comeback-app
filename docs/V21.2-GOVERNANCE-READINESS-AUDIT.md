## 1. Executive finding

**Readiness outcome: NO-GO for production reviewer-trust operation or implementation. GO for a separately gated technical-design stage once the outstanding governance inputs are resolved or explicitly carried as blockers.**

The owner has now recorded G-01 and G-02 directions and PASS decisions for the G-03 through G-12 governance frameworks. That completes the current governance-principles decision sequence. It does not complete the operational policy, professional qualification matrix, privacy/legal assessment, operating model or machine-enforceable trust chain.

The current application has meaningful foundations for immutable catalogue delivery, exact target/digest binding, guide-registry validation, SHA-256 integrity and fail-closed handling. Those controls are not equivalent to authenticating a reviewer. The repository's own authentication trust model states that catalogue review-binding validation does not authenticate reviewer identity, qualification, scope, signature, current status or revocation.

No evidence was found in the inspected source tree of a production reviewer-governance service, authenticated reviewer registry, trust-root bootstrap, reviewer-signed approval attestation, revocation service or restricted credential-record system. The exercise-guide registry currently validates digest-bound review metadata; its review digest is not a reviewer signature or proof of competence.

## 3. Source-grounded application and test findings

### 3.1 Existing foundations

- `src/data/catalogue-delivery.js` implements catalogue manifest/payload checks, SHA-256 byte integrity, review-binding structure and exact target-digest binding, plus transactional catalogue materialisation/activation.
- `src/modules/exercise-guide-crypto.js` provides canonical SHA-256 digest operations with domain separation and fail-closed behaviour when Web Crypto is unavailable.
- `src/modules/exercise-guide-registry.js` validates guide, asset-set, assignment and review metadata against exact digests, versions, programme slots and scopes. It resolves incomplete when required review bindings are absent or mismatched.
- `src/modules/exercise-guide-runtime.js` validates the guide registry against the current programme snapshot and verified local assets.
- `v21.2/sw.js` caches the V21.2 application shell and guide/catalogue support assets. Catalogue release assets are handled in a separate namespace by the catalogue delivery code.

These are useful integrity, provenance and fail-closed foundations. They do not establish who made a review, whether that person was qualified and authorised at the relevant time, whether the reviewer's credential was later restricted, or whether a release authority was entitled to publish the result.

### 3.2 Critical trust gap

The authentication model explicitly records that `src/data/catalogue-delivery.js` validates review-binding structure and target digest only; it does not authenticate reviewer identity, qualifications, scope, signatures, current status or revocation. The exercise-guide crypto design likewise states that client-side hashes detect integrity/binding changes but do not authenticate reviewers. A user able to replace local review metadata and recompute its digest is not thereby a qualified reviewer.

Accordingly, do not reuse guide-artwork/content hashes as a reviewer trust chain. A later design must separately specify authenticated reviewer authorisation, signed attestations, trust-root bootstrap, release authority, key custody/rotation, revocation, freshness, audit and offline failure behaviour.

### 3.3 Production-content readiness

The exercise-guide review-readiness document describes a 52-entry human review queue: 35 editorially ready for qualified review, 15 requiring clarification and 2 on hold. “Ready for review” is not approval. The same document states the production registry remains empty. The catalogue curation/reviewer gate also requires a separate machine-enforceable trust-boundary decision before production publication.

The current app's manual exercise-swap UI explicitly says substitutions are not catalogue-verified. No injury-aware candidate matching may be inferred from the presence of review metadata or guide-integrity code. High-consequence movement-demand/injury-relevance use remains blocked until the approved professional review and freshness conditions can actually be enforced.

### 3.4 Test coverage boundary

The current browser workflow runs catalogue-delivery contracts, exercise-guide registry/digest/runtime tests, review-readiness source contracts, backup validation and browser/offline tests. The inspected test inventory does not contain a dedicated end-to-end reviewer-authentication suite proving credential verification, signed reviewer authorisation, trust-root bootstrap, independent approval enforcement, revocation propagation, restricted-record privacy/retention or production publication governance. Existing passing code tests therefore cannot be treated as reviewer-trust operational assurance.

## 4. Blocking prerequisites before production reliance

1. **Professional qualification:** obtain appropriately qualified Australian professional input; define the five scope pathways, authoritative sources, exclusions and movement-demand/injury-relevance standard. Do not use AI or informal credential claims as the qualifying authority.
2. **Identity and appointment:** decide who independently verifies identity/credentials, who grants each scope, who rechecks, and how finite terms and adverse events are enforced.
3. **Independence and decisions:** complete delegation, conflict thresholds, dual-review independence, suspension/investigation/appeal roles and operational timeframes.
4. **Privacy/legal:** complete an Australian privacy/legal assessment for the actual responsible entity and proposed processing before collecting any real identity, credential, conflict, complaint or appeal data. Set access, notices, retention, correction, disclosure, incident, provider and cross-border controls.
5. **Operations and funding:** identify accountable and operational roles, deputy/succession, resourcing, funding authority, independent audit, service continuity and exit arrangements. If these are unavailable, affected approval activity must pause.
6. **Freshness and public traceability:** justify scope-specific freshness and revocation requirements; settle public/restricted fields, redaction authority and safe user language.
7. **Machine-enforceable trust:** design a separate authenticated chain that binds reviewer identity reference, authorised scope, exact target/version/digest, decision, evidence reference, validity and lifecycle state to verifiable signatures and an independently trusted root. Specify release authority, key custody/rotation, revocation, trusted time, offline status and rollback resistance.
8. **Independent verification and tests:** define threat model and security review, then test positive and negative cases including forged reviewer IDs, out-of-scope approvals, expired/revoked credentials, compromised keys, stale/offline devices, altered targets, incomplete dual review, rollback and preservation of user workout history.

## 5. Recommended next gate — design only

Prepare a bounded **Reviewer Trust Technical Gate Design** with these deliverables:

- traceability matrix mapping each approved G-01–G-12 principle to a proposed control, responsible role, evidence and test;
- unresolved-decision register, clearly distinguishing blockers that require professional/legal/owner decisions from technical choices;
- trust-boundary and threat model, including trust-root bootstrap, reviewer authorisation, attestation, release signing, revocation and offline freshness;
- data-class and data-flow map separating public catalogue, restricted governance records, application data and user workout/health data;
- proposed lifecycle/state machine and fail-closed behaviour;
- source impact map identifying only candidate files and interfaces, with no edits to them;
- test and independent-assurance plan;
- explicit implementation, data-collection, production-publication and deployment approval gates.

The design must not silently choose professional credentials, legal bases, retention periods, freshness intervals, operational appointments or funding. Where those decisions are unavailable, record a blocker and design the system to remain unavailable for the affected approval use.
