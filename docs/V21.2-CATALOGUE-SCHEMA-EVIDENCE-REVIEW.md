# V21.2 — Catalogue schema and evidence review

**Status:** architecture proposal only. No catalogue payload, production IDs, equipment definitions, movement metadata, user restriction records, database change or backup-format change is created by this review.

**Inspected development checkpoint:** bd94374dde22a43ee3372efe306360fc33fb2528.
**Prerequisite inventory:** docs/V21.2-EQUIPMENT-EXERCISE-CURATION-MATRIX.md.
**Architecture baseline:** V21.2 IndexedDB schema v6, full backup format V2, catalogue manifest/payload schema v1.

## 1. Executive recommendation

Use one immutable, versioned exercise catalogue release containing both reviewed exercise data and reviewed system equipment definitions. Keep the verified release bytes in the existing dedicated Catalogue CacheStorage namespace. Expose equipment-definition lookup from the verified cached payload rather than writing system equipment definitions into the existing personal equipment store.

Keep a user's physical equipment and location access as user-owned records in the existing equipment store, using a new explicitly validated record type while preserving all legacy records. The existing store is already included in V2 full backup.

Use explicit equipment requirement groups with defined OR/AND semantics. Do not use substring gear matching or assume that custom equipment is equivalent to a system definition.

For injury-aware matching, create a separate, reviewed movement-demand profile. It must capture direct and secondary loading plus stabilisation, support, balance, foot-contact, weight-bearing, impact, propulsion, position and bracing demands. Missing metadata is **unknown**, not a clean bill of health.

Represent persistent user-reported restrictions separately from daily readiness. The recommended implementation is a dedicated restriction store with explicit lifecycle and backup coverage. That is a new data contract and must receive its own database/backup stage gate before implementation.

## 2. Exact current architecture facts

The live source at the inspected checkpoint confirms:

| Area | Current implementation | Implication |
|---|---|---|
| IndexedDB | Schema v6 | A new object store or index needs a separate schema-upgrade review |
| Personal equipment | Existing equipment store, keyPath id, only by_module index | It is suitable for user-owned/legacy equipment records, not a system catalogue |
| Identity stores | Exercise definitions, variations, aliases, review events, releases, configurations, programme versions/days/slots | Identity and programme foundations already exist |
| Catalogue payload | Manifest/payload schema v1 | Contains exercise definitions and variations; no equipmentDefinitions collection |
| Catalogue materialisation | catalogueReleases, exerciseDefinitions, exerciseVariations and metadata | System equipment definitions are not currently materialised |
| Catalogue asset | Dedicated release-specific CacheStorage namespace with byte length, SHA-256, payload validation and read-back | Already provides an offline home for immutable system reference data |
| Full backup | Formats V1 and V2; V2 includes all current stores | A new store is not currently represented by V2 |
| Exercise configuration | Only preferred progression focus and recording-mode override | It is not machine configuration or prescription storage |
| Programme versioning | Version/day/slot stores with published-version immutability | Candidate foundation for future editable programmes; current Gym UI does not yet use it as a builder |

The existing catalogue delivery approval implemented verified delivery and exercise definition/variation materialisation. It did not approve a system equipment-definition payload, new schema, new backup format or restriction store. This review does not extend that approval.

## 3. System equipment definitions — recommended release-asset model

### 3.1 Separate the catalogue from personal equipment

Three things must remain distinct:

1. **System equipment definition:** reviewed description of an equipment family and its supported configuration attributes.
2. **User equipment-access record:** a particular item or group the user can access at a named location, with configuration details the user has actually confirmed.
3. **Exercise equipment requirement:** reviewed rule connecting an exercise/variation to one or more equipment definitions.

The current equipment store belongs to item 2. Its migrated V21.1 records include legacy shapes such as gym-equipment and gym-custom-equipment, each carrying the original source key/raw value. Those records must remain intact and must not be reinterpreted as approved system definitions.

### 3.2 Keep system definitions in the verified release bytes

Recommendation: add a system equipment-definitions collection to a future catalogue payload schema version and read it through the existing verified release asset/cache service.

Reasons:

- System equipment definitions are immutable shared reference data, not personal user data.
- The catalogue asset is already content-addressed, integrity-checked and stored in a dedicated cache that is kept separate from the shell cache.
- Equipment definitions are a small lookup/reference set; a separate IndexedDB index is not justified yet by measured scale or query needs.
- Keeping these definitions in the release asset avoids using the personal equipment store for two incompatible purposes.
- It avoids an immediate IndexedDB v7 and V2-to-V3 backup-format change solely to materialise static catalogue definitions.

The delivery service would need a narrow API that reads the active release manifest, retrieves its exact cached bytes through the existing verification path, validates them, and returns only the equipment definitions. It must not trust an arbitrary cache entry or a manifest without verified asset status. If the required asset is absent/corrupt and cannot be recovered from the exact immutable URL, equipment-catalogue lookup must report unavailable. It must not show an empty list as if no equipment exists.

IndexedDB may still materialise exercise definitions and variations as it does today. CacheStorage remains the authority for the bundled system equipment-definition collection; the user equipment store remains the authority for personal access/configuration.

### 3.3 Why not reuse the equipment store for system definitions

Putting catalogue definitions alongside user equipment rows would blur ownership and lifecycle. Catalogue refresh could then accidentally replace a user's machine entry, custom equipment or availability status. It would also make it difficult to distinguish an absent system definition from equipment the user has removed or cannot access.

Do not store system equipment definitions in the current equipment store, metadata store, preferences or exerciseConfigurations as a shortcut.

### 3.4 Release pins and history

A user equipment-access record should retain:

- Stable user record ID and profile scope.
- Location ID and a visible location-name snapshot.
- System equipment-definition ID, or a visibly custom user-entered name when no system definition is confirmed.
- The catalogue release ID used when the definition was selected.
- A display snapshot of the equipment label/category used at that time.
- User-confirmed configuration attributes, availability state, notes and provenance.

The snapshot keeps the user's saved inventory understandable if an older release asset is unavailable after restore. Exact release references should be included in the future catalogue-retention reference scan. No automatic release garbage collection is proposed.

A definition ID is stable across releases only while the underlying equipment concept remains the same. A materially different equipment family or configuration concept requires a new ID. Do not silently rebind a user's existing equipment record to a merely similar current definition. If its exact definition is unavailable, render the saved snapshot and mark definition-based matching unavailable until it can be resolved.

## 4. Catalogue payload v2 — proposed record structure

This is a schema proposal, not an approved production payload. No actual IDs or records are created here.

### 4.1 Equipment definitions

Each equipment definition should include:

- Opaque stable ID.
- Canonical label and equipment family.
- Short scope/description that distinguishes the equipment from nearby families.
- Supported configuration dimensions and controlled values, where known.
- Provenance to exact source labels/evidence.
- Curation/review state and the exact release containing it.
- Optional reviewed illustration reference; an illustration is never identity evidence.

The 44 legacy gear choices in the curation matrix are candidates. They must be reviewed for duplicate, combined and ambiguous concepts before definitions are created. The system should not mint 44 IDs automatically.

### 4.2 Configuration dimensions must remain orthogonal

For gym machines, keep at least these dimensions independent when applicable:

- **Loading/resistance system:** selectorised/pin-selected, plate-loaded, fixed-weight or unknown; additional systems only after evidence.
- **Movement mechanics:** fixed path, converging handle path, independent/iso-lateral arms and other reviewed mechanics.
- **Orientation/body position:** for example, 45-degree sled, horizontal seated or vertical leg press; seated versus prone/lying leg curl.
- **Fit/setup attributes:** seat, pad, pivot, handle/attachment, stance and other configuration needed to distinguish the physical machine.
- **User instance details:** optional user-entered make/model/notes, without requiring these details to use the app.

The owner has confirmed the intended Gym contains both pin-selected and plate-loaded machines. That means both must be representable. It does not establish which loading system, geometry or mechanics belong to any particular machine.

Do not infer that a plate-loaded machine is iso-lateral, that a pin-selected machine has a fixed path, or that a leg-press orientation follows from its loading system.

### 4.3 Exercise-to-equipment requirements

The current string array requiredEquipmentDefinitionIds does not define whether multiple IDs mean AND or OR. A future schema should replace ambiguity with explicit groups.

Recommended semantics:

- Every requirement group must be satisfied.
- Within one group, the user may satisfy any one complete alternative.
- Every equipment ID within a chosen alternative must be available.
- A group can therefore express alternatives such as one machine OR the combination of a bench AND dumbbells.
- A reviewed “no equipment required” declaration is different from an absent/unknown requirements field.

Suggested conceptual fields:

- equipmentRequirementReviewStatus: reviewed-required, reviewed-none or incomplete.
- equipmentRequirementGroups: array of groups.
- Each group has a stable group key and an alternatives array.
- Each alternative is a list of equipment-definition IDs that are all required together.

The release validator must reject duplicate equipment IDs, unknown references, malformed groups, unsupported configuration values and references to definitions absent from the same release. Exercise variations may narrow or explicitly override the parent equipment requirement only where reviewed; there must be no implicit inheritance that changes the actual setup.

A custom user item does not automatically satisfy a system equipment requirement because its name happens to contain “dumbbell”, “press” or “cable”. It can be linked to a system equipment definition only through an explicit user choice or a separately reviewed exact mapping. Until then, availability is unknown for definition-based recommendations.

### 4.4 Payload compatibility

The current loader accepts schema v1. A later implementation should support the existing v1 reader path and a new v2 path without interpreting old v1 data as if it had the new fields.

For v2, validation should additionally check:

- equipmentDefinitions exists and is an array;
- equipment-definition IDs are non-empty and unique, including cross-type collision checks;
- configuration schema values are supported and internally consistent;
- every exercise/variation equipment reference resolves in that same release;
- the equipment requirement status distinguishes reviewed-none from incomplete;
- requirement groups have valid OR-of-AND structure;
- every exercise and equipment definition has valid provenance/review-state fields;
- payload counts and digest still cover the exact bytes.

The system equipment definitions remain in the verified release bytes. No equipmentDefinitions IndexedDB store is proposed in this version of the design.

## 5. User equipment-access records

A future personal inventory record should be explicitly typed, for example recordType = equipment-access, and versioned independently of the legacy equipment record shape.

Recommended fields:

- id, recordType, recordSchemaVersion and profileId;
- moduleId and locationId/locationNameSnapshot;
- equipmentDefinitionId or a custom user-entered display name;
- catalogueReleaseId and equipmentDisplaySnapshot when a system definition is selected;
- availabilityStatus (available, temporarily unavailable, unknown);
- userConfirmedConfiguration, with only attributes actually known to the user;
- provenance and optional user notes.

A user may have multiple physical machines that share a broad definition. Each instance remains a separate user record so that, for example, a pin-selected and a plate-loaded chest press can coexist at the same Gym location.

Availability is a user-managed fact, not a system inference. Temporary unavailability must not erase the record or change exercise identity. A custom item remains visibly custom and unreviewed unless an explicit definition mapping is confirmed.

The existing equipment store is a candidate location for these typed records because it is already included in full V2 backup. Before implementation, validate restore behavior for legacy and typed records together, uniqueness, location editing, removal, unavailable states, cross-release references and collision handling. Do not mutate migrated gym-equipment or gym-custom-equipment records as part of introducing the new UI.

## 6. Movement and body-region evidence model

### 6.1 Preserve source fields; add reviewed metadata separately

The source library's muscle keys are useful historical clues only. They do not encode primary versus secondary muscle involvement, joint action, stability, body position, foot contact, impact or propulsion. Preserve them exactly as sourceMuscleKeys and add reviewed fields rather than rewriting them.

Proposed reviewed movement metadata should include:

- muscles/body regions with explicit primary/secondary roles;
- joint actions and movement-pattern references;
- body position, stance, laterality, range and support points;
- stabilisation and balance demands;
- foot contact and foot-pressure demands;
- weight-bearing, impact/landing and propulsion demands;
- setup/bracing and equipment-configuration requirements;
- reviewer status, source evidence and review scope.

Do not introduce unsupported low/medium/high scores until reviewers have agreed what each score means. Prefer evidence-backed descriptors over false precision.

### 6.2 Distinguish missing metadata from reviewed non-involvement

The data must distinguish:
- known relevant involvement/demand;
- reviewed demand profile with no material demand identified for the reviewed area/scope;
- unreviewed or incomplete coverage.

An absent body-region entry by itself is never proof that the exercise does not load that region. A movement profile must have a completeness/review marker and its source/reviewer scope. The UI must not convert a review statement into a guarantee that an exercise is safe or has zero effect.

### 6.3 Candidate screening states

For a user-reported restriction, a candidate should resolve to one of three states:

1. **Known conflict:** reviewed metadata identifies relevant direct/secondary or mechanical loading for the restricted area. Do not offer it as an alternative.
2. **Unknown / incomplete:** relevant metadata is absent, ambiguous, stale or outside the review scope. Fail closed; do not recommend it.
3. **Reviewed candidate:** the required movement-demand coverage exists and the review did not identify material loading conflict for the specified area/scope. The UI may offer it as a possible alternative, but must clearly say suitability cannot be guaranteed and this is not medical clearance.

A user confirmation is still required before the swap. Worsening symptoms block progression advice. If no candidate qualifies, provide Remove/skip or Keep restricted rather than guessing.

## 7. Persistent user-reported training restrictions

### 7.1 Keep restrictions separate from readiness

The existing readiness store is date-oriented. A readiness answer describes a check-in for a date; it is not the lifecycle of an injury or persistent activity restriction. A favourable readiness score must never clear a restriction.

Recommendation: create a dedicated trainingRestrictions store with a typed, profile-scoped record. This is clearer and safer than hiding health-adjacent restriction state inside generic preferences or free-text notes.

A record should contain only what the user chooses to report:

- stable record ID and profile ID;
- active/cleared status;
- reported date and explicit user-reported affected body area(s);
- laterality only when the user supplies it;
- optional user wording/context, without converting it into a diagnosis;
- explicit activity limitation supplied by the user, if any;
- user action and timestamp when updated/cleared.

Do not infer diagnosis, tissue injury, clinical severity, healing progress or recovery date. Do not set an automatic expiry. Do not auto-clear on elapsed time, improved readiness, a completed workout or an adaptive recommendation.

### 7.2 Persistence and privacy

This is personal health-adjacent information. Keep it local-first under the existing user-data ownership model; there is no cloud sync. Include it in the user's full backup/restore only after the corresponding backup contract is approved. Make the backup/restore preview explicit that user-reported training restrictions are included. The user must be able to inspect and explicitly clear/delete them.

### 7.3 Database and backup gate

A dedicated object store would advance IndexedDB schema v6 to a new version and require a backup format that includes the new store (likely a V3 format while retaining V1/V2 restore compatibility). That change requires:
- a separate explicit stage gate;
- pre-upgrade verified safety backup and rollback behavior;
- migration/version tests from existing v6;
- V1/V2 restore into the new store shape;
- V3 export/restore validation;
- retention and conflict semantics;
- cold/offline browser tests;
- exact-SHA browser and backup validation.

No schema or backup change is approved here. If the team later proposes reusing preferences instead, that must be separately evaluated for typing, integrity, restore, privacy and lifecycle; do not silently repurpose it.

## 8. Programme and swap semantics

Use the existing version/day/slot foundations, but do not treat their existence as a working UI.

- The five-day source programme remains available unchanged.
- A current-session swap changes only the current session's performed exercise choice and retains the original programme slot and history.
- Remove/skip records the user's decision for that slot/session without deleting the source slot.
- Keep restricted leaves the exercise out while the restriction remains active.
- A future-programme change creates a new draft/version and requires explicit selection. It does not change completed sessions or already-started workouts.
- A published programme version remains immutable.
- Every action makes its scope visible: this session only, or a new programme version for future sessions.
- A later decision to resume an original exercise requires the user to explicitly update the restriction. That is an app-state change, not a medical clearance.

## 10. Required tests before implementation can be called complete

Catalogue:
- v1 fixture still validates and remains readable;
- v2 equipment IDs are unique and all cross-references resolve;
- malformed equipment groups, unsupported configuration values and unresolved IDs are rejected before activation;
- failed staging/activation leaves the previous active release intact;
- equipment-definition lookup works offline after verified installation and reports unavailable if the exact release bytes are absent/corrupt;
- shell-cache cleanup never removes catalogue release bytes.

User equipment:
- legacy gear records remain byte/semantically preserved;
- typed inventory records are separate, profile/location scoped and backed up;
- two configurations of the same equipment family can coexist at one location;
- custom equipment is not automatically mapped to a reviewed system definition;
- restore retains equipment IDs, release references and display snapshots.

Injury restrictions:
- a restriction survives reload, app restart, new session, programme change and backup/restore;
- readiness cannot clear or weaken it;
- unknown movement metadata fails closed;
- direct, secondary, stabilisation, balance, foot-pressure, weight-bearing, impact, propulsion, positioning and bracing demands are considered;
- Swap, Remove/skip and Keep restricted are explicit actions;
- original programme slots and past workout values never change;
- a session-only action cannot silently alter a future programme;
- explicit user clearing does not display medical clearance language.

## 11. Decisions retained for the owner / qualified reviewers

No user-specific equipment model/configuration is identified by the legacy source. The Gym-wide presence of both pin-selected and plate-loaded machines is known, but the specific machine geometry remains unknown.

Still requires deliberate evidence/review:
- whether the combined legacy equipment choices should split into distinct definitions;
- the controlled body-region, muscle, joint-action and movement-pattern vocabularies;
- whether each candidate exercise is one definition or has distinct variations;
- exact setup/configuration requirements for chest press, shoulder press, leg press, leg extension, leg curl and cable stations;
- accepted qualifications and verification process for reviewers of exercise movement and safety metadata;
- whether the proposed v2 payload and v7/V3 restriction-store gates are accepted before any implementation.

## 12. Boundary

This review is design only. It creates no equipment or exercise IDs, no v2 release payload, no movement metadata, no injury records, no new database store, no backup-format change and no runtime implementation. The production exercise catalogue and guide registry remain unpopulated. No source-programme label, historical workout, V21.1 data, protected main branch, Pages candidate, hosting setting or deployment is changed.

The next approval decision is the bounded catalogue payload v2 design (C1). The restriction store (C3) is a separate approval and must not be bundled into C1.
