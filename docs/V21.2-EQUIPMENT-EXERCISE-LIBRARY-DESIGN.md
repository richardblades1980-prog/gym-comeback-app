# V21.2 — Equipment and Exercise Library design

**Status:** source-grounded audit and design proposal only. No application implementation, catalogue content publication, database change, backup-format change or live-data operation is included in this checkpoint.

**Inspected development checkpoint:** \`V21.2-development\` at \`31ef2ea323bced532d5fba765d2d8dffcc2ef56e\` (19 November 2026). The browser and backup workflows both passed on that exact source checkpoint.

## 1. Executive finding

The V21.2 application has meaningful foundations for a future equipment and exercise system, but it does not yet provide the selectors or management screens needed to use them.

The current Gym runner still starts from the fixed, source-preserved five-day base programme. A user can enter a free-text manual substitution and mark equipment as unknown, available or unavailable. That is not a searchable exercise library, equipment inventory, verified substitution system or programme builder.

The recommended design keeps four concepts separate:

1. **System equipment catalogue:** what a type of equipment is, its capabilities and the configuration attributes that distinguish it.
2. **User equipment access:** what the user can access at each location, including the actual configuration of a particular machine.
3. **Exercise catalogue:** reviewed exercise definitions and meaningful variations, including movement and injury-relevance metadata.
4. **Programmes and performed workouts:** versioned plans and slots on one side; immutable historical session/set performance on the other.

The existing five-day programme remains intact and available as the original source programme. A new library or builder must not silently replace it, reinterpret an old slot, or rewrite workout history.

## 2. Live-source audit

### 2.1 Current UI and runtime

- The V21.2 navigation currently contains Overview, Gym, Hiking, Assessments, Schedule and Data & backup. There is no Equipment or Exercise Library view.
- The Gym launch screen selects programme week, one of five fixed days, workout date, programme length and days per week. The exercise list is generated from the source-preserved five-day base programme.
- Each exercise card currently has a manual free-text exercise change and an equipment status selector. The UI explicitly warns that the replacement details are not catalogue-verified.
- The Gym workout engine preserves the original source exercise name, source description and programme slot identity separately from the performed free-text exercise label. A replacement cannot be made once a set has started, completed or contains recorded values.
- The shared Programme Manager is currently a calendar/schedule service; it is not a Gym programme editor or exercise selector.

### 2.2 Existing storage foundations

The V6 database already contains:

- An \`equipment\` store, keyed by ID and indexed only by module ID.
- \`exerciseDefinitions\`, \`exerciseVariations\` and \`exerciseAliases\`.
- Append-only \`identityReviewEvents\` and \`catalogueReleases\`.
- \`exerciseConfigurations\`.
- \`programmeVersions\`, \`programmeDays\` and \`programmeSlots\`.

The equipment store is currently a generic user-data store, not a validated system equipment catalogue. The V21.1 migration projects the old selected/custom gear objects into records such as \`gym-equipment\` and \`gym-custom-equipment\`, preserving the original key and raw value. Those legacy records must not be reinterpreted as reviewed equipment definitions.

The existing reusable exercise-configuration service is deliberately narrow. It allows only a preferred progression focus and a recording-mode override. It does not store a machine's physical configuration, an exercise prescription or workout performance. Do not broaden that record silently.

The full V2 backup already includes the equipment store and the V6 identity/programme stores. A new equipment manager should be designed to preserve that coverage. Any new store, index or backup contract still requires a separate review and explicit stage gate.

### 2.3 Catalogue delivery and curation

The current catalogue delivery service verifies immutable release bytes, SHA-256, byte length, payload identity, definition/variation counts, unique IDs, variation parent links, CacheStorage read-back and atomic V6 materialisation. The release is available offline after successful installation.

However:

- The production payload model currently contains exercise definitions and variations; it does not contain a system equipment-definition collection.
- The current lookup searches canonical exercise names by substring. It does not provide equipment filtering, movement filters, curated injury metadata queries or a full equipment-definition lookup.
- No approved production exercise catalogue asset/manifest is present. The browser tests use a clearly labelled test-only fixture. A fresh device correctly reports the production catalogue as unavailable until a real release is curated and installed.

The source inventory contains 42 optional-library rows and 32 source-programme slots. Ten base-programme labels do not directly match an optional-library row. Every source slot remains unassigned to a canonical exercise ID. The guide review inventory has 52 entries (25 existing descriptions and 27 draft gaps); all still require qualified human review. The production guide registry remains empty. These source counts and draft recommendations are review evidence, not catalogue approval.

### 2.4 Programme foundations

The five-day base programme is explicitly a source snapshot, not a published catalogue-backed programme. Its source labels, descriptions, source grouping and muscle keys are retained, and every slot is marked unreviewed for identity.

The V6 programme stores already provide version-scoped days and slots, stable lineage fields, catalogue-release pins and immutability for published versions. The live Gym UI and workout runner do not yet use those stores to let a user create, select or edit a programme.

## 3. Recommended information architecture

Add a **Gym Setup** area, separate from the live workout runner, with three clear destinations:

1. **My Equipment** — equipment access grouped by location.
2. **Exercise Library** — searchable reviewed definitions and variations.
3. **Programmes** — choose, copy, build and manage versioned workout plans.

The Gym tab remains the place to start/resume and record a workout. It should offer a clear route to Gym Setup, but equipment edits and programme edits should not be mixed into an in-progress workout.

### 3.1 My Equipment

Support multiple named locations from the start (for example, Gym and Home), rather than one global equipment tick-list. Each equipment entry represents either a particular machine/configuration or a useful group of equipment, such as a dumbbell set.

The user should be able to:

- Add equipment from a searchable system equipment list.
- Add a custom item when no reviewed catalogue definition matches.
- Assign it to a location and mark access as available, temporarily unavailable or not confirmed.
- Add more than one entry for an equipment family when the physical configurations differ.
- Edit or remove their own equipment-access entry without changing the system equipment definition or a historical workout.
- Record relevant machine details without being forced to know a brand/model.

For machines, keep these characteristics independent:

- **Loading system:** selectorised/pin-selected, plate-loaded, fixed-weight, adjustable, bodyweight or unknown.
- **Movement mechanics:** for example fixed-path, converging or independent/iso-lateral arms, where relevant.
- **Physical orientation/configuration:** for example 45-degree sled, horizontal seated or vertical leg press.
- **Optional fit/setup details:** only where they are useful and can be entered accurately.

A pin-selected machine is not automatically a different exercise from a plate-loaded machine. Conversely, two machines with materially different movement geometry must not be collapsed just because their display names are similar. Do not infer one attribute from another: an iso-lateral label does not prove a particular loading system.

### 3.2 Exercise Library

Provide search and filters for name, body area/muscle, movement pattern and required equipment. Each result should distinguish the canonical definition from a specific variation.

A reviewed exercise record should be able to describe:

- Canonical name, stable opaque ID, provenance and review status.
- Primary and secondary muscles/body regions, with source evidence.
- Movement pattern and relevant joint actions.
- Body position, support, stance and laterality where these affect execution.
- Stabilisation and balance demands.
- Foot contact, weight-bearing, impact and propulsion demands.
- Equipment requirements, including explicit alternative equipment paths where supported.
- Cautions/limitations and the evidence/reviewer status for those statements.
- Links to separately reviewed setup and exercise-guide content, where available.

Do not treat source description text or the old group/muscle keys as verified biomechanical metadata. They are source clues for curation only. Search synonyms may improve discovery, but they must not silently become verified identity aliases for old programme labels.

A custom exercise can remain visible as user-created content. Unless its movement and loading metadata have been reviewed, it must be labelled unreviewed and excluded from injury-aware alternative recommendations.

### 3.3 Programmes

The Programme area should eventually support:

- The original five-day source programme, unchanged and clearly identified as the original.
- Creating a new programme from a blank plan or a copy of an existing plan.
- Adding, removing, reordering and swapping exercise slots in a draft.
- Choosing a reviewed exercise definition and, where applicable, a specific variation.
- Setting prescription fields independently from exercise identity (sets, reps, load, target duration and rest).
- Saving a draft, reviewing it and explicitly publishing a new immutable version.
- Selecting which programme version is used for future new sessions.

Published versions are immutable. Editing a published plan creates a new draft/version. Existing and completed sessions continue to point to the exact source/version and display snapshot they were created with.

The base programme must not be overwritten by a user's custom plan. A programme swap or removal must have an explicit scope: this session only, or a new/future programme version. The app must never make a one-session decision permanent without telling the user.

## 4. Recommended data boundaries

### 4.1 System equipment definitions

Extend the immutable system catalogue payload with a reviewed equipment-definition collection. These entries describe equipment families and supported configuration attributes. They are not the user's physical machines and are not user-owned inventory.

The delivery service will need an explicit payload-schema evolution and tests for equipment IDs, duplicate IDs, definition references and unsupported configuration values. The existing G2 approval covers the current exercise-definition/variation delivery implementation; it should not be treated as blanket approval for a new payload schema or any database/backup change.

### 4.2 User equipment access records

First evaluate using the existing \`equipment\` store for new, namespaced, user-owned equipment-access records. A new record shape should have an explicit record-type/schema discriminator and include:

- Stable user record ID and owner/profile scope.
- Location ID and visible location label.
- System equipment-definition ID, or an explicitly named custom-equipment entry.
- Availability state.
- User-entered machine configuration attributes and optional notes.
- Provenance indicating which fields came from the system definition and which were entered by the user.

Legacy migration records remain unchanged. New code must validate the new record type rather than assuming every historical record has the new shape. The small personal inventory can initially be filtered from the existing store without adding an index; confirm that this is adequate in tests before considering a schema/index upgrade.

Do not store system equipment definitions as if they were personal equipment rows. The immutable catalogue asset remains the source of truth for system definitions; CacheStorage provides verified offline bytes. The user's equipment-access records remain in IndexedDB and the full backup.

### 4.3 Exercise definitions and variations

Extend the reviewed exercise catalogue to reference system equipment definitions. Where an exercise can be performed using more than one equipment path, use an explicit structured requirement model (for example, separate acceptable equipment groups) rather than ambiguous free-text gear terms.

Variations receive separate opaque IDs only where a curated difference changes execution or history/progression interpretation. Machine orientation and movement mechanics may require distinct variation metadata or, where the movement itself materially changes, a separate exercise definition. The loading system remains a separate equipment attribute unless curation establishes a real movement distinction.

Do not generate a combinatorial set of variations from every possible grip, stance, loading system and machine attribute.

### 4.4 Injury-aware metadata and restrictions

The user's injury-aware requirement is a core acceptance condition, not an optional enhancement. A reported pulled calf is an example of a user-reported restriction; the app must not diagnose it, infer a recovery date or decide that the injury has healed.

For injury-aware alternatives, reviewed exercise metadata must cover more than the primary muscle label. It must account for direct and secondary involvement plus stabilisation, balance, foot pressure, propulsion, impact, weight-bearing, positioning and setup/bracing demands.

A restriction must remain active until the user explicitly updates or clears it. A favourable readiness score must not clear it. The app must distinguish current-session changes from changes to future programme versions.

The interface must present explicit choices:

- **Swap** to a reviewed alternative only when relevant movement/equipment demands are sufficiently understood.
- **Remove/skip** the exercise when no suitable reviewed alternative is available.
- **Keep restricted** and leave the exercise out for now.

Fail closed: unknown, incomplete, ambiguous or unreviewed movement metadata means the system cannot recommend that exercise as an injury-aware alternative. The UI must not say an exercise is safe, has zero effect on the area or constitutes medical clearance. The original programme slot and its history stay intact.

The current \`readiness\` store is date-oriented and is not an appropriate substitute for a persistent activity restriction. A dedicated user-reported training-restriction record is the recommended future model. Adding it may require a new store, indexes and backup-format compatibility work; that must be designed and separately approved before implementation. Do not hide restrictions in free-text notes or silently repurpose readiness fields.

### 4.5 Programme and performed-workout lineage

Use the existing programme-version/day/slot foundation for future plans, after validating its record contract in tests. Each plan slot needs:

- Version-specific record identity and stable slot lineage.
- Optional source base-programme slot lineage.
- Exact exercise definition and variation IDs, pinned catalogue release and display snapshot.
- Prescription fields separate from exercise identity.
- Explicit status for active, removed or skipped slots, without deleting the source slot.

Performed workout records continue to preserve the source programme identity separately from what was actually performed. A substitute must be recorded as the performed exercise/variation and must not rewrite the source slot or historical trend. Existing started/completed sets and user-owned values must remain untouched.

## 5. Injury example — required behaviour

If a user reports a pulled calf muscle:

1. Capture the user's reported affected area and any stated activity restriction. Do not create a diagnosis or recovery estimate.
2. Mark the restriction active across future sessions until the user explicitly changes it.
3. Check the current and upcoming plan against reviewed exercise metadata, including secondary and indirect loading demands.
4. Exclude exercises with known relevant calf loading. Treat unknown metadata as not assessed, not as safe.
5. Offer a reviewed replacement only if the movement and equipment demands are sufficiently understood and do not materially load the restricted area based on the reviewed information.
6. Ask the user to choose Swap, Remove/skip or Keep restricted. State whether the action affects this session only or a future programme version.
7. Preserve the original source slot and all historical records.
8. When the user later asks to resume the original exercise/programme, require an explicit user update and confirmation. That records the user's decision; it is not a medical clearance.

Progression convenience and a favourable readiness result never override an active restriction. If the metadata cannot support a defensible alternative, no replacement is invented.

## 6. Staged implementation recommendation

| Stage | Work | Gate / constraint |
|---|---|---|
| A — Audit and design | This source-grounded audit, conceptual model, UI plan and acceptance criteria | Documentation only; current checkpoint |
| B — Catalogue contract and curation | Define the equipment-definition and exercise-metadata payload; reconcile source rows/slots; review the controlled vocabularies and source evidence | Separate catalogue payload/review gate; no invented IDs or published content |
| C — Equipment manager and library browser | Add locations, user equipment-access records, equipment configuration UI and searchable exercise browsing against a real verified release | Prefer existing V6 stores where they fit; tests must prove backup/restore and no legacy-record mutation |
| D — Programme selector/builder | Create and select draft/published programme versions and explicit slot edits | Preserve the fixed original source programme and immutable history; versioned-plan tests required |
| E — Persistent restrictions and alternatives | Add user-reported restriction capture, persistence, scope-aware swap/skip choices and fail-closed alternative matching | Dedicated data/backup safety review and explicit approval before any new store or backup-format change |
| F — Adaptive Brain | Connect readiness, workout history, reviewed movement metadata, equipment access and active restrictions to advisory proposals | Explicit Apply/OK only; no user-owned values overwritten; no medical-safety claims |

Do not jump directly from the Gym milestone into Adaptive Brain. The library, equipment and restriction foundations are prerequisites for recommendations that are grounded rather than guessed.

## 7. Acceptance checks before implementation can be called complete

- Equipment can be managed separately for at least two named locations, with multiple configurations of the same equipment family.
- Pin-selected/selectorised, plate-loaded, fixed-path, converging, iso-lateral and machine-orientation attributes remain independent where applicable.
- A custom equipment item is visible but is not automatically treated as a reviewed system-equipment match.
- Equipment and exercise lookup work offline only after a verified production catalogue release is installed; unseeded catalogue state is visibly unavailable.
- Required equipment references resolve exactly; missing or duplicate IDs fail the release before activation.
- Exercise filters use reviewed data. Source text, muscle names or equipment labels do not silently become identity or injury-safety evidence.
- Every base programme slot retains its exact source label, day, order and lineage until an explicit new programme version is selected.
- Draft edits do not mutate a published programme or any completed/in-progress workout.
- Per-session swaps and future-programme edits are visibly different actions.
- Injury alternatives fail closed on unknown metadata and preserve the active restriction until explicit user update.
- Full backup/restore retains user equipment records, custom exercises, programme versions, restriction data and historical display snapshots under the approved backup contract.
- Canonical source and browser-loaded asset mirrors remain byte-identical where required; browser and backup validation pass on the exact final commit.
