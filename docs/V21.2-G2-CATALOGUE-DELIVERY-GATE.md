## 1. Trigger and goal

A system catalogue needs immutable release packaging, verified delivery, offline materialisation, cache retention and recovery. These affect release identity, historical interpretation, offline-first behaviour and backup/restore. A bad update could expose incomplete definitions, lose a pinned release or silently reinterpret history. This is G2.

**Goal:** deliver one trusted, versioned system catalogue release at a time, with exact-byte integrity and offline lookup after verified local materialisation, while keeping historical records readable without old catalogue assets.

## 2. Bounded implementation proposed

In scope only after PASS:
- source-controlled immutable JSON release artifact and manifest;
- SHA-256, byte length, content type, schema, catalogue/release/version identity, entry count, unique IDs and reference validation before acceptance;
- dedicated catalogue CacheStorage namespace, separate from shell cache;
- stage exact bytes, verify cache re-read, then materialise definitions/variations and switch active-release pointer in one IndexedDB transaction;
- use existing schema v6 stores where adequate; any schema/index change reopens this gate;
- preserve custom definitions, aliases, review events, configurations, performed records and programme snapshots;
- offline lookup only after verified matching materialisation;
- V2 restore without archived system asset bytes; preserve pins/snapshots and report unavailable pinned assets;
- include direct programme-slot references in release retention; no automatic GC;
- real browser, CacheStorage, service-worker, IndexedDB and backup/restore tests.

## 3. Explicit exclusions

No V21.1 or production `main` edits; no merge/deployment; no schema upgrade unless separately reviewed and explicitly passed; no remote/CDN service, signatures, cloud sync or server-side editor; no fuzzy identity resolution or legacy setting promotion; no automatic release GC; no historical record rewriting or substitution of a missing pinned release with latest. A checksum alone is not publisher authentication.

## 5. Options and recommendation

| Option | Benefit | Risk |
|---|---|---|
| Ordinary shell cache for catalogue JSON | Minimal code | Shell activation can purge retained release bytes |
| Treat manifest checksum string as integrity proof | Minimal storage | No bytes are hashed |
| Mutable latest URL and overwrite | Simple refresh | Not reproducible; unsafe interruption/history semantics |
| Immutable versioned artifact + SHA-256 + isolated cache + IndexedDB materialisation | Reproducible, offline, recoverable | Requires staging, validation and recovery |

**Recommendation:** immutable artifact + manifest; stage/verify bytes in dedicated release cache; materialise and activate in one IndexedDB transaction; preserve previous active release until commit. IndexedDB is the offline queryable materialisation; CacheStorage is the verified artifact cache.

## 6. Compatibility and historical-data impact

- Schema v6 and V2 backup are the starting point; do not assume another schema version is needed.
- Backups preserve release IDs/checksums, user-owned records, programme/session lineage and immutable display snapshots. System bytes remain app distribution artifacts.
- Restore succeeds when archived bytes are absent; old history renders from snapshots.
- Pinned release IDs never change. If a pinned asset is unavailable, mark it unavailable for edit/replay; never silently switch to current.
- System refresh cannot overwrite custom definitions, aliases, audit events, configurations, performed records or snapshots.
- A required new store, backup format change, incompatible field, historical semantic change or broader network trust boundary reopens G2.

## 7. Failure and recovery requirements

1. Missing/offline asset: keep current release; if no verified materialisation exists, report catalogue unavailable.
2. Wrong digest/truncated bytes: reject before parse/write; preserve active release.
3. Invalid schema/IDs/references: reject as a new invalid release; do not mutate current data.
4. Interrupted fetch/cache write: never activate; retry immutable release and clean only unreferenced staging cache.
5. IndexedDB abort: old active pointer/materialisation remain unchanged; retry idempotently.
6. Shell update: delete obsolete shell caches only; preserve catalogue caches.
7. Missing pinned asset after restore: display snapshot; editing unavailable until exact release recovered.
8. CacheStorage corruption: use matching verified IndexedDB materialisation if intact; otherwise unavailable and re-fetch.
9. Retain explicit references from published programme versions, slots, pinned non-terminal sessions and review events. No GC.

## 8. Acceptance evidence required

- Exact byte SHA-256 and byte-length validation before JSON parse.
- Payload identity/schema/count/duplicate ID/foreign-key validation.
- Immutable release ID/version and same-version conflict rejection.
- Failure injection for interrupted fetch, partial cache write, cache re-read mismatch and IndexedDB transaction abort.
- Old active release remains usable until new release commits.
- Real CacheStorage tests prove release cache survives shell activation cleanup.
- Real Playwright offline lookup after materialisation and explicit unavailable state before initial seed.
- Stale manifest/asset mismatch and corrupt/missing cache recovery.
- V2 restore on clean device/profile without old asset bytes; snapshots render, pins unchanged and unavailable editing explicit.
- Retention tests include direct programme-slot references.
- Browser and backup workflows on every exact commit; V21.1 and `main` unchanged.

Design/characterization test passes do not prove production catalogue delivery exists.

## 13. G2 decision and bounded implementation checkpoint

The user explicitly approved PASS on 17 November 2026.

Implementation is limited to:
- Exact-byte SHA-256 and byte-length validation before JSON parsing.
- Strict manifest/payload identity, schema, count, duplicate-ID and variation-parent validation.
- Release-specific CacheStorage namespace, read-back verification and isolation from service-worker shell cleanup.
- Atomic IndexedDB V6 transaction across the existing catalogueReleases, exerciseDefinitions, exerciseVariations and metadata stores. The release manifest, materialised definitions/variations and active pointer commit together; no DB version change.
- Offline lookup only when the active manifest and materialised release counts agree.
- Explicit unavailable status on an unseeded device; historical snapshots and backup format remain unchanged.

No approved production exercise catalogue dataset was present in the inspected source. No synthetic catalogue has been presented as the production library. The browser integration test uses a clearly labelled test-only fixture to prove delivery, materialisation, lookup and offline persistence. Until a real catalogue asset/manifest is curated and approved, a fresh device correctly reports the catalogue as unavailable.

A schema/index change, backup-format change, release garbage collection, remote delivery/signing, profile-owned data migration, lookup UI, merge or deployment remains outside this PASS.
