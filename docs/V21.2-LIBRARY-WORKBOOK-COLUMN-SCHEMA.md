# V21.2 — Library workbook column schema proposal

**Status:** design proposal and test fixture only. No importer/exporter, UI, production catalogue content, database or backup changes are implemented.

**Design base:** `V21.2-development` at `80e4d882d95ca4d5f038d64ff253c2b698c979b9`.
**Workbook format proposal:** `library-workbook-v1`.
**Runtime catalogue reference:** current catalogue delivery payload schema v2.

## 1. Important compatibility finding

The live catalogue-delivery v2 contract already supports stable equipment IDs, canonical equipment names, equipment-family IDs, configuration vocabularies, exercise and variation IDs, structured equipment requirements, controlled vocabulary IDs/labels, and reviewed movement-demand coverage.

It does **not** currently define first-class description fields or an alias collection in the v2 catalogue payload. Although the application has an IndexedDB exercise-alias store, the immutable offline catalogue-delivery payload does not currently export/import that store as part of a release.

Therefore:
- Canonical equipment, exercise and vocabulary labels can be edited in the current conceptual contract while retaining their IDs.
- Descriptions and aliases must be included as **proposed workbook-only extension fields**, clearly marked as not publishable through the current v2 payload.
- Before descriptions or aliases can be round-tripped into an installed catalogue, their payload representation, validation, lookup behaviour and release compatibility must be designed and approved as a separate catalogue schema evolution.
- The importer must never accept a description or alias column and then silently discard it.

This is a deliberate compatibility stop, not a reason to abandon the spreadsheet approach.

## 2. Workbook metadata

The Read Me sheet contains a two-column key/value metadata block. Required keys:

| Key | Meaning |
|---|---|
| workbook_schema | Exact value `library-workbook-v1` |
| catalogue_id | Exact value `exercise-catalogue` |
| base_release_id | Immutable release exported; blank only for an explicitly labelled empty-catalogue bootstrap workbook |
| base_release_version | Integer release version; blank only for empty-catalogue bootstrap |
| exported_at | ISO 8601 timestamp |
| locale | BCP 47 locale; initial default `en-AU` |
| workbook_status | `exported` or `test-fixture`; importer rejects test fixtures for production publication |

The importer checks the workbook's base release against the current catalogue before staging. It does not silently rebase stale workbooks.

## 3. Sheets and exact proposed columns

All identifiers are text, even if they contain digits. One row represents one entity or one relationship. Do not use comma-separated IDs, row numbers or display names as foreign keys. Empty optional cells are blank, not the strings `null`, `N/A` or `unknown`.

### 3.1 Equipment

One row per system equipment definition.

| Column | Required | Mapping / rule |
|---|---|---|
| equipment_id | Existing rows: yes; new rows: blank proposal | Payload `equipmentDefinitions[].id`; immutable for existing IDs |
| proposal_key | New proposals: yes | Workbook-only temporary key; unique within workbook; never published |
| canonical_name | Yes | Payload `canonicalName`; editable without changing ID |
| family_id | Yes | Must reference `equipmentFamilies` vocabulary |
| review_status | Yes | Exported payload uses `approved`; edits/new rows become pending review in staging |
| source_ref | Yes, one or more rows | One source reference per row in Equipment Sources |
| description | Optional, extension only | Not supported by current payload v2; must be rejected from publish until schema evolution is approved |

### 3.2 Equipment Sources

One row per source reference.

| Column | Required | Mapping / rule |
|---|---|---|
| equipment_id_or_proposal_key | Yes | Equipment row reference |
| source_ref | Yes | Exact provenance/source locator |

The payload requires at least one `sourceRefs` entry per equipment definition.

### 3.3 Equipment Configuration

One row per supported configuration term.

| Column | Required | Mapping / rule |
|---|---|---|
| equipment_id_or_proposal_key | Yes | Equipment row reference |
| attribute | Yes | One of `loadingSystemIds`, `movementMechanicIds`, `orientationIds`, `setupAttributeIds` |
| vocabulary_term_id | Yes | Must exist in the corresponding controlled vocabulary |

The importer groups rows into the payload's four separate arrays. A value must exist in the matching vocabulary. Do not infer loading system from movement mechanics or orientation.

### 3.4 Exercises

One row per canonical exercise definition.

| Column | Required | Mapping / rule |
|---|---|---|
| exercise_id | Existing rows: yes; new rows: blank proposal | Payload `definitions[].id`; immutable |
| proposal_key | New proposals: yes | Workbook-only temporary key |
| canonical_name | Yes | Payload `canonicalName`; editable without changing ID |
| kind | Yes | Published system definitions use `system`; new proposals remain staging-only |
| equipment_review_status | Yes | `reviewed-required`, `reviewed-none` or `incomplete` |
| movement_review_status | Yes | `complete` or `incomplete` |
| description | Optional, extension only | Not currently defined for reliable v2 catalogue round-trip; do not publish until schema evolution |

### 3.5 Variations

One row per meaningful exercise variation.

| Column | Required | Mapping / rule |
|---|---|---|
| variation_id | Existing rows: yes; new rows: blank proposal | Payload `variations[].id`; immutable |
| proposal_key | New proposals: yes | Workbook-only temporary key |
| parent_exercise_id_or_key | Yes | Must reference an exercise row |
| name | Yes | Payload `name` |
| equipment_review_status | Yes | Same statuses as Exercises |
| movement_review_status | Yes | Same statuses as Exercises |
| description | Optional, extension only | Not currently defined for reliable v2 round-trip |

A variation is created only when a reviewed execution difference justifies a separate identity. Do not create every grip/stance/loading combination as a variation.

### 3.6 Vocabulary

One row per controlled vocabulary term. This sheet covers every current v2 vocabulary category.

| Column | Required | Mapping / rule |
|---|---|---|
| category | Yes | One exact category key listed below |
| term_id | Existing rows: yes; new rows: blank proposal | Stable vocabulary item `id`; globally unique across all categories |
| proposal_key | New proposals: yes | Workbook-only temporary key |
| label | Yes | Vocabulary item `label`; editable without changing ID |

Allowed category values:
- `bodyRegions`
- `muscles`
- `jointActions`
- `movementPatterns`
- `bodyPositions`
- `supportPoints`
- `stabilisationDemands`
- `balanceDemands`
- `footContactDemands`
- `footPressureDemands`
- `weightBearingDemands`
- `impactDemands`
- `propulsionDemands`
- `bracingDemands`
- `equipmentFamilies`
- `equipmentLoadingSystems`
- `equipmentMovementMechanics`
- `equipmentOrientations`
- `equipmentSetupAttributes`

Current v2 vocabulary objects define only `id` and `label` as their required term fields. Parent/child hierarchy, long definitions, synonyms and aliases are not current v2 vocabulary fields. They remain proposed extension data until separately designed.

### 3.7 Equipment Requirements

One row per equipment-definition member of an alternative. Repeat group and alternative IDs for each member.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Parent exercise/variation reference |
| group_id | Required for reviewed-required | Requirement group `id` |
| alternative_id | Required for reviewed-required | Workbook-only key identifying one OR alternative within a group |
| equipment_id_or_key | Required for each alternative member | Each alternative's `equipmentDefinitionIds[]` member |

A group represents alternatives: the app can satisfy one alternative. Every selected alternative's equipment IDs are conjunctive (all listed members required). An alternative cannot be empty.

### 3.8 Equipment Constraints

One row per configuration constraint.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Subject reference |
| group_id | Yes | Equipment Requirements group |
| alternative_id | Yes | Equipment Requirements alternative |
| equipment_id_or_key | Yes | Must be a member of this same alternative |
| attribute | Yes | One of the four supported configuration attributes |
| vocabulary_term_id | Yes | Must exist in matching vocabulary and be supported by the referenced equipment definition |

### 3.9 Movement Profiles

One row per exercise or variation.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Subject reference |
| review_status | Yes | `complete` or `incomplete` |

The payload's movement profile is a structured object. This sheet declares its review state; the detailed coverage belongs in the next two sheets.

### 3.10 Movement Involvement

One row per involvement entry. Use a shared involvement_key to group a body-region/muscle pair where the reviewed evidence describes one combined involvement entry.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Subject reference |
| role | Yes | `primaryInvolvement`, `secondaryInvolvement` or `otherRelevantInvolvement` |
| involvement_key | Yes | Workbook grouping key |
| body_region_id | Optional per row | Must reference `bodyRegions` |
| muscle_id | Optional per row | Must reference `muscles` |

Each grouped involvement entry must contain at least one body-region or muscle ID. No role or muscle involvement may be inferred from old labels or exercise names.

### 3.11 Movement Coverage

One row per coverage term.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Subject reference |
| coverage_field | Yes | Exact payload field from the list below |
| vocabulary_term_id | Yes | Must reference the matching vocabulary category |

Allowed coverage fields and categories:

| coverage_field | Vocabulary category |
|---|---|
| jointActionIds | jointActions |
| movementPatternIds | movementPatterns |
| bodyPositionIds | bodyPositions |
| supportPointIds | supportPoints |
| stabilisationDemandIds | stabilisationDemands |
| balanceDemandIds | balanceDemands |
| footContactDemandIds | footContactDemands |
| footPressureDemandIds | footPressureDemands |
| weightBearingDemandIds | weightBearingDemands |
| impactDemandIds | impactDemands |
| propulsionDemandIds | propulsionDemands |
| setupBracingDemandIds | bracingDemands |

A complete movement profile must explicitly include all 16 coverage arrays in the runtime contract, including the three involvement roles and equipment configuration constraints. An empty list means reviewed as no applicable terms only when the qualified review supports that conclusion; it must not be used as a substitute for unknown data.

### 3.12 Movement Equipment Constraints

One row per movement-profile equipment configuration constraint.

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `exercise` or `variation` |
| subject_id_or_key | Yes | Subject reference |
| equipment_id_or_key | Yes | Existing equipment definition |
| attribute | Yes | Supported configuration attribute |
| vocabulary_term_id | Yes | Must be in the matching vocabulary and supported by that equipment definition |

### 3.13 Alias Proposals — staging only

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `equipment`, `exercise`, `variation` or `vocabulary` |
| subject_id_or_key | Yes | Stable ID or proposal key |
| alias_text | Yes | Proposed alternate search text |
| locale | Yes | BCP 47 locale |
| alias_status | Yes | `proposed` only in this workbook version |

**Compatibility:** aliases are not part of the current catalogue-delivery v2 payload. This sheet is retained as staging-only research/proposal data. It cannot be published or treated as a verified identity alias until an explicit catalogue schema and lookup extension is approved.

### 3.14 Description Proposals — staging only

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | `equipment`, `exercise`, `variation` or `vocabulary` |
| subject_id_or_key | Yes | Stable ID or proposal key |
| description | Yes | Plain text; no executable markup |
| description_status | Yes | `proposed` only in this workbook version |
| source_ref | Yes | Provenance for the proposed text |

**Compatibility:** descriptions are not a defined, round-trippable field in the current v2 delivery contract. They cannot be silently published or dropped. The payload schema must be explicitly evolved before this sheet becomes publishable.

### 3.15 Review Notes

| Column | Required | Mapping / rule |
|---|---|---|
| subject_type | Yes | Record type |
| subject_id_or_key | Yes | Stable ID or proposal key |
| change_summary | Yes | Human-readable proposed change |
| evidence_ref | Yes for substantive claims | Traceable source/review evidence |
| reviewer_note | Optional | Context for human review |

Review approval bindings and target digests are generated by the trusted review/publishing process. They are never edited or supplied by spreadsheet cells. Editing reviewed content invalidates its prior approval binding and returns it to pending review.

## 4. Status and validation rules

- Exported, approved catalogue rows preserve their IDs and payload status.
- New rows must use proposal keys and remain pending/unreviewed.
- Existing IDs cannot be changed, reused or reassigned to a different concept.
- A canonical rename is a proposed edit to the same ID; it does not create an alias or establish identity equivalence with legacy programme labels.
- A description/alias proposal is preserved in staging and blocks publication until its payload extension is approved.
- Unknown, incomplete or ambiguous movement data remains incomplete. It cannot be treated as a safe alternative for an active user restriction.
- Retirements are explicit status transitions; hard deletion is prohibited for referenced records.
- Every foreign key must resolve exactly once. Ambiguous labels never resolve automatically.
- All unknown columns, unsupported categories and unrepresentable values are hard errors, not ignored warnings.
- Formula cells in data columns are rejected. No macros or external workbook links are evaluated.
- Workbook status `test-fixture` is never accepted for production publication.

## 5. Test fixture acceptance plan

The companion fixture `tests/fixtures/library-workbook-v1/fixture.json` is synthetic and marked TEST ONLY. It contains no production exercise approval, no medical or injury claim and no real equipment recommendation.

Required importer/exporter tests once implementation is separately approved:

1. Export then import unchanged: zero semantic changes.
2. Rename a canonical equipment label: same equipment ID, one changed field.
3. Rename a muscle vocabulary label: same vocabulary ID; every reference remains intact.
4. Add a new vocabulary proposal: staged only; no active release change.
5. Add a new equipment proposal with a temporary key: staged only; no active release change.
6. Unknown muscle ID: hard error with sheet/row/column.
7. Duplicate IDs and duplicate prohibited labels: hard errors.
8. Broken exercise parent, requirement alternative or configuration reference: hard error.
9. Attempted ID mutation: hard error.
10. Stale base release: explicit conflict; no automatic rebase.
11. Description or alias proposal: preserved in staging and blocks publish until schema extension exists.
12. Approved content edited after review: prior review binding invalidated; new approval required.
13. Import leaves personal equipment, original programme, workout history and active catalogue unchanged until explicit publication.
14. V1 and V2 existing catalogue delivery tests remain passing.

## 6. Explicit next decision

This is a column-schema proposal, not an implementation approval. Before writing exporter/importer code, review the column names and especially decide whether descriptions and aliases should be part of a deliberate catalogue payload schema evolution. The current v2 delivery contract cannot honestly promise those two fields as published catalogue data.
