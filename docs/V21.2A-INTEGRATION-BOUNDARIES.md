# V21.2A — Safe App Integration Boundaries

Status: integration boundary design; same-origin worker coexistence implemented and browser-validated on V21.2-development only. No live publication or main-branch change.
Applies to: V21.2-development.

## Existing V21.1 boundary

The current V21.1 app is a single root `index.html` with a large inline script and localStorage-backed Gym behaviour. It registers the root `sw.js`. That worker has a root scope, caches the V21.1 app shell/assets, and handles navigation fallback to the cached root index. It must not be repurposed for V21.2 while the V21.1 app remains live.

## Safest initial integration shape

Build V21.2 as an isolated route/directory (proposed: `/v21.2/`) with its own entrypoint, styles/assets and service worker. Keep the root `index.html`, root `sw.js`, manifest and all V21.1 UI behaviour unchanged.

- Use relative asset and script paths so the isolated app works under a repository subpath as well as a custom-domain root.
- Register any V21.2 service worker only from inside the V21.2 directory. Its default scope must remain that directory; do not request root scope.
- Use a distinct V21.2 cache name and V21.2-only asset list. Do not delete or replace V21.1 caches.
- Do not cache user records in the service worker. IndexedDB remains the source of truth and is already available offline after the app has loaded.
- Keep V21.2 scripts as ordered classic scripts initially because the existing services are browser IIFEs exposing named `window.ProjectComeback*` APIs. Load database first, then Gym/shared normalisers and migration, then module registry, backup, programme manager and workload services. Avoid changing their public names during first integration.

## Storage and migration gate

- V21.2 IndexedDB database name and stores remain as defined in `src/data/database.js`.
- The browser origin is shared by root and subdirectory routes, so IndexedDB is origin-scoped, not path-scoped. Do not assume `/v21.2/` creates a separate database from V21.1; the V21.1 app currently uses localStorage and does not use this V21.2 database.
- Do not run migration automatically on page load. Show a clear migration screen with source-key count and a downloadable JSON safety snapshot first.
- Require the user to create/save the downloadable safety snapshot and explicitly confirm migration before invoking `migrateAndVerify()`.
- Migration must retain all original localStorage keys. No cleanup/removal of V21.1 data in this phase.
- If migration warnings or conflicts occur, keep the user in a recoverable state, show the warnings and do not report success unless the typed completion marker is confirmed.
- Provide full versioned JSON backup and a non-destructive restore preview before offering restore confirmation.

## Module boundaries

- Initialise the module registry before enabling module writes.
- Gym writes only to its owned stores: sessions, exerciseRecords, setRecords and progression.
- Hiking writes only to hikingRecords. Completed manual hikes require moduleId=hiking and status=completed.
- Shared profile, objectives, equipment, readiness, schedules and preferences remain module-neutral.
- The shared programme manager may coordinate dated schedules but must not rewrite either module's programme or combine unlike loads into one score.

## Smallest implementation sequence

1. Create isolated `v21.2/` entrypoint and V21.2-only styles; do not edit root V21.1 files.
2. Load and initialise IndexedDB and module registry; display module status and basic navigation only.
3. Add a migration preflight screen: inspect legacy keys, download safety snapshot, explicit confirmation, run migration, verify typed marker and present warnings.
4. Add full backup, backup validation, restore preview and explicit restore confirmation.
5. Add Gym and Hiking screens against their own module services; implement manual Hiking record validation against the documented Hiking record contract.
6. Add shared schedule and descriptive workload views without changing training plans automatically.
7. Validate persistence/reload, source preservation, transaction failures, offline shell, accessibility and browser behaviour using a controlled dataset.
8. Ask the user for phone regression only after the browser build is stable. Do not cut over the root app or main branch until the user has tested and explicitly approved it.

## Release boundary

This is not a cutover plan. The root V21.1 app and main branch remain production-safe and unchanged until all migration, browser, offline and phone checks pass and the user explicitly approves release. A future cutover must be a separate reviewed task with a reversible deployment and data-backup plan.


## G3.7.3a — GitHub Pages same-origin worker coexistence (2026-11-19)

The selected target is the existing V21.1 GitHub Pages project site, `https://richardblades1980-prog.github.io/gym-comeback-app/`, with V21.2 intended at `/v21.2/`. This keeps both app paths on the same browser origin while retaining their separate root and subdirectory service-worker scopes.

The development-only root V21.1 worker change:
- derives the V21.2 prefix relative to its own `sw.js` URL, so the repository project path is not hard-coded;
- returns without calling `respondWith` for V21.2 requests, allowing the V21.2 scoped worker and network to handle them;
- limits activation cleanup to the V21.1 cache prefix `gym-comeback-v21-1b-`;
- precaches the root `index.html` as part of installation so a worker replacement retains an offline entry page.

The browser suite runs both apps under the simulated GitHub Pages project path `/gym-comeback-app/`. It installs the root V21.1 worker first, then the V21.2 subdirectory worker; verifies the two controllers and cache namespaces coexist; confirms the root cached homepage remains V21.1; simulates a root worker update and verifies only the prior V21.1 cache is retired; then tests offline cold start of both routes and checks same-origin localStorage preservation.

Exact implementation checkpoint: `8097a505cb8d5637ccbf26fb2226c99cb435fed8`.
