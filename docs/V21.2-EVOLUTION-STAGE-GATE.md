# V21.2 Evolution Stage Gate Standard

**Status:** Adopted development-governance standard for V21.2 design and implementation.  
**Applies to:** `V21.2-development`; it does not authorise changes to protected V21.1 or production `main`.  
**Purpose:** Let Gym Comeback evolve without silently damaging historical data, compatibility, user trust or the ability to recover.

## 1. Governing principle

**Evolution must preserve the past while making room for the future.**

New features may change what the application can do. They must not silently rewrite what a user previously did, what a programme prescribed, what a historical record meant, or what data the user owns.

A stage gate is a deliberate review before a consequential decision or implementation step. It is not a meeting or approval ritual for every small change. The assistant should recommend a gate when risk, irreversibility, broad impact or future cost makes one useful. The user retains the decision to pass, hold, revise or reject it.

## 2. When a gate is and is not needed

### Mandatory recommendation — gate before proceeding

Recommend a gate before implementation or commitment when a change affects, or could plausibly affect:

- persisted data structures, IndexedDB schema/version, IDs, relationships, identity resolution or historical interpretation;
- data migration, import/export, backup, restore, deletion, retention or recovery;
- exercise catalogue releases, aliases, programme versions, historical snapshots or progression comparability;
- offline-first behaviour, service-worker caching, synchronisation or conflict resolution;
- authentication, profiles, ownership boundaries, privacy, security or sensitive data;
- public interfaces, integrations, file formats or compatibility with previous app versions;
- core progression/recovery logic, calculations, or decisions that can materially change a user's training guidance;
- initial-release scope, architecture, deployment, production data or other difficult-to-reverse commitments;
- a major refactor that spans modules or changes a shared contract.

### Lightweight review — no formal gate normally needed

A formal gate is usually unnecessary for isolated visual polish, copy changes, small accessibility improvements, contained bug fixes or refactors that demonstrably preserve behaviour and data contracts.

Even a small change must be escalated if investigation reveals a hidden data, compatibility, privacy or safety impact. The classification depends on consequences, not the number of changed lines.

## 3. Gate levels

| Level | Use | Required treatment |
|---|---|---|
| **G0 — Routine** | Contained change with no material data/contract impact | Normal review and relevant regression tests; no user pause |
| **G1 — Focused evolution** | One bounded contract or subsystem changes | State the impact, compatibility and rollback plan; user approval before irreversible implementation |
| **G2 — Foundation evolution** | Data model, migration, identity, backup, offline, security or cross-module contract changes | Written impact assessment, options/recommendation, acceptance criteria and regression plan; explicit user pass before implementation |
| **G3 — Release/production gate** | Release readiness, deployment, production data operation, major scope or irreversible rollout | Full readiness evidence, recovery/rollback proof, scope confirmation and explicit user authorisation; no implied approval |

G0 is not a formal stop. G1–G3 are stop-and-review gates. If uncertain between levels, choose the higher level until evidence narrows the risk.

## 4. Required gate record

For each G1–G3 gate, present a concise record containing:

1. **Trigger and level** — what changed or is about to change, and why a gate is warranted.
2. **Goal and boundaries** — intended outcome, non-goals and affected modules/data.
3. **Current-state evidence** — live branch, commit, source files, schema/backup versions and relevant tests inspected.
4. **Options and recommendation** — viable approaches, trade-offs and why the recommendation is safer for future evolution.
5. **Compatibility and historical-data impact** — existing records, old backups, previous app versions, IDs, names, units, blanks, dates, programme history and unresolved data.
6. **Failure and recovery analysis** — interruption, retry/idempotency, partial failure, rollback or forward-recovery strategy.
7. **Acceptance evidence** — tests required, exact commands/workflows, and what a passing result proves or does not prove.
8. **Scope classification** — initial release, deferred future enhancement or commercial opportunity. A gate must not silently promote deferred work into launch scope.
9. **Decision** — pass, hold, revise or reject, with the user's decision recorded in the handover.

Do not ask the user to approve a vague bundle. Separate independent decisions where they have materially different consequences.

## 5. Non-negotiable data and compatibility rules

- Preserve original historical values and source evidence. Never silently normalise, infer, overwrite or discard them.
- Use immutable opaque IDs for durable identity; never derive identity from mutable display text.
- Keep identity, reusable defaults, programme prescriptions and performed results separate.
- Keep published programme versions and historical snapshots immutable.
- Resolve legacy identity only with verified evidence. Ambiguous values remain unresolved and visible.
- Make migrations additive where practical, idempotent, restart-safe and observable. A retry must not duplicate records or events.
- Never delete or recycle IDs still referenced by history, programmes, backups or audit evidence.
- Treat backup and restore as part of every persisted-data feature, not as later housekeeping.
- Test compatibility from every supported schema/backup version. Preserve the original backup until restore is verified.
- Do not claim offline capability based only on a test fixture; validate the production app shell, assets and persistence path.
- Keep user-owned data isolated from system catalogue refreshes and other profiles.
- Do not change protected V21.1 or production `main` without separate, explicit authorisation.

## 6. Evidence and validation rules

A gate passes only when its stated evidence exists. A successful test run is evidence only for the code and commit SHA it actually tested.

For GitHub work on V21.2:

- inspect the live branch head and relevant source before edits;
- keep changes on `V21.2-development`;
- run the applicable browser and backup workflows for each meaningful resulting commit;
- verify each workflow's `head_sha` exactly matches the commit under review;
- do not describe a commit as validated while required workflows are pending, failed or testing a different SHA;
- after a handover/documentation commit, validate that final commit too;
- inspect the protected `main` and V21.1 baseline read-only to confirm they remain unchanged;
- report failures and limitations plainly. Never turn a fixture-level pass into a claim of production functionality.

For a G2/G3 data change, add specific evidence for migration idempotence, interruption/restart, backup/restore round trips, old-format compatibility and historical-value preservation where relevant. Offline changes also require a real production-path offline test.

## 7. Approval and stop conditions

The assistant recommends whether a gate is needed and prepares the evidence. The user decides whether to pass it.

- **Pass:** proceed only within the approved scope and conditions.
- **Hold:** stop implementation; gather missing evidence or defer.
- **Revise:** update the proposal and return for review.
- **Reject:** do not implement the proposal.

Silence, a request to continue researching, or a passing automated workflow is not approval for a consequential design choice, data migration, production operation or deployment.

If new evidence materially changes the risk after a gate passes, pause and reopen the gate. Approval applies to the reviewed scope, not to materially different later work.

## 8. How the assistant should use gates during development

The assistant should raise a gate proactively, before the risky work, and explain in plain language:

- what decision is approaching;
- what could become difficult to change later;
- what data or compatibility is at risk;
- what options exist;
- which option is recommended and why;
- what evidence is needed to pass.

Do not interrupt routine work with unnecessary gates. Batch related low-risk tasks, but do not bundle unrelated high-risk decisions merely to reduce checkpoints. Where useful, use a gate to agree a staged implementation plan and then allow the approved, bounded work to proceed without repeatedly asking for the same approval.

## 9. Initial application to the current V21.2 work

The canonical exercise identity proposal is a **G2 foundation evolution** because it introduces new durable identities, catalogue ownership, programme lineage, auditability and eventual data migrations. The current work remains design-only. The next implementation step must first resolve the remaining identity-review/audit and reusable-configuration boundaries, then prepare a migration/backup/offline implementation gate before adding stores or writing user data.

The current repository has IndexedDB schema v5 and backup format v1. Those are observed current-state facts, not permission to change either. The existing 16 exercise-identity tests are design-level fixture contracts, not production-service tests.

No application implementation, schema migration, backup-format change, V21.1 edit, merge or deployment is authorised by adopting this standard.
