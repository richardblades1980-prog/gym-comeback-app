### Migration
Files: src/data/migration.js, src/data/gym-migration.js, src/data/shared-migration.js
- migrateAndVerify() is now the full migration entry point.
- First preserves every Gym-prefixed localStorage key/value string in legacyRecords and verifies exact raw values.
- Then runs Gym and shared-data normalisers for sessions/exercises/sets, profile, equipment, readiness, weigh-ins and preferences.
- Confirms source localStorage has not changed.
- Commits all typed projections and the final complete marker in one IndexedDB read-write transaction through database.js commitLegacyMigration().
- Existing deterministic IDs are accepted only when the existing record matches the same legacy source; conflicting records abort the transaction rather than being overwritten.
- A failed normalisation leaves the verified raw snapshot in place and the marker at snapshot-verified. Original localStorage is never modified or deleted.
- Browser IndexedDB transaction and restart behaviour still needs real-browser validation; mocked orchestration tests are not a substitute.

### Backup / restore
File: src/data/backup.js
- Full JSON backup envelope, format version 1.
- Validates required stores, record IDs and duplicate IDs.
- Restore requires explicit confirmation.
- Restores all stores in one IndexedDB read-write transaction.
- Saves pre-restore snapshot in metadata within the restore transaction.
- New previewRestore(input) is non-destructive and reports per-store current/incoming/add/change/unchanged/remove counts.
- Preview does not write to the database.
- New test added for preview counts and no writes.

### Module registry
File: src/modules/module-registry.js
- Gym Comeback and Hiking Preparation modules.
- Gym owns sessions, exerciseRecords, setRecords, progression.
- Hiking owns hikingRecords.
- Disabling a module blocks new writes but preserves existing data.
- getOwnedRecords relies on database getAllByIndex export, now fixed.

### Programme manager

## Legacy completion evidence review
- Read the V21.1 main-branch implementation of setStatusStorageKey(), activeWorkoutSessionToken() and hasCompletedWorkout(). Status keys have the exact form gym-comeback-set-status-v1-{week}-{day}-{date-or-undated}-{session-token}; the session token is stored separately under gym-comeback-active-session-v1-{week}-{day}-{date-or-undated}.
- The old hasCompletedWorkout() scans any status snapshot for the week/day and checks the *currently active exercise list and current exercise configs*, not the saved log's exercise list. This can differ from historical workout contents after later swaps/config changes.
- The V21.2 normaliser deliberately uses date-scoped snapshots and the saved log's exercise/setCount values. This is conservative and avoids falsely marking a saved session complete from another date/session or from today's changed workout configuration. It may not exactly reproduce legacy day-unlock eligibility in edge cases; keep that distinction explicit and add dedicated tests before migration integration.
