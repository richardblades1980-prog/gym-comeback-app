# V21.2 canonical exercise identity — proposed data model

**Status:** Design proposal and test contract only. Not implemented.  
**Branch reviewed:** `V21.2-development` at `49606d38a886d475c640d1b3f2501147a99aa8ed`  
**Scope:** Canonical exercise identity, variations, equipment references, programme versions/slots, verified aliases, unresolved legacy records and reusable configuration.

## 1. Decision summary

Use separate immutable identities for:

1. **Exercise definition** — the reusable movement concept.
2. **Exercise variation** — a meaningful variant of that movement.
3. **Performed exercise record** — one occurrence inside one workout session.
4. **Programme version** — an immutable published snapshot of a programme.
5. **Programme slot** — one exercise position inside one programme version, with a lineage reference to its logical position across versions.
6. **Equipment definition** — a controlled catalogue concept, separate from equipment owned/selected by a user.

Names, descriptions, equipment availability and programme prescriptions may change. Identity IDs must not be derived from names and must not change when labels change.

**No historical exercise record is assigned a canonical ID merely because its name resembles a library entry.** An identity link requires a verified exact alias or explicit review. Unresolved records remain usable and visible as unresolved.

## 2. Source-grounded current state

The live source inspection at the branch SHA above confirmed:

- `src/data/database.js` is IndexedDB schema version 5. It has `exerciseRecords` indexed by session and module, but no exercise-definition, variation, alias or exercise-configuration stores.
- `src/data/gym-migration.js` creates a performed exercise ID from its session ID and exercise position. It preserves the supplied name and raw exercise JSON. That ID is a workout-instance identity, not a reusable movement identity.
- `src/programme-manager/programme-manager.js` validates and summarises calendar schedule entries. It does not define programme versions or exercise slots.
- The existing `programmes` store is separate from the `schedules` store; a scheduled session title or schedule ID is not a programme version or exercise slot.
- The existing `equipment` store contains module-owned/user equipment records. It is not a controlled global equipment taxonomy.
- V21.1 library and programme definitions are name-led. Its normalised exercise-name matching/config-key behavior has known collisions. The collision tests deliberately characterize this; they do not endorse it.
- The backup service enumerates stores explicitly. Any future store addition must also be added to backup/restore, schema migration and integration tests.

This document proposes future structures; it does not claim they exist in V21.2 today.

## 3. Proposed record model

The names below are logical entity/store names, not a request to add them in this design-only checkpoint.

### 3.1 Exercise definitions — `exerciseDefinitions`

One record per canonical movement identity.

| Field | Purpose |
|---|---|
| `id` | Immutable opaque ID, e.g. `exd_01J...`; never derived from a display name |
| `kind` | `system` or `custom` |
| `canonicalName` | Current preferred display label; editable without changing ID |
| `status` | `active`, `deprecated` or `retired`; never reuse a retired ID |
| `description` | Optional neutral description |
| `movementPattern` | Optional controlled classification, only when curated/verified |
| `requiredEquipmentDefinitionIds` | References to equipment catalogue concepts |
| `optionalEquipmentDefinitionIds` | Optional equipment catalogue concepts |
| `createdAt`, `updatedAt` | Audit timestamps |

The catalogue should be version-controlled and reviewed. System IDs are assigned once and committed as data; custom IDs are generated once (UUID/secure random) and persisted. Renaming a definition does not create a new ID. A materially different movement does.

### 3.2 Exercise variations — `exerciseVariations`

A separately identified variation belongs to exactly one exercise definition.

| Field | Purpose |
|---|---|
| `id` | Immutable opaque variation ID, e.g. `exv_01J...` |
| `exerciseDefinitionId` | Required parent definition reference |
| `name` | Variation label |
| `attributes` | Explicit characteristics such as grip, stance, laterality, range or implement |
| `equipmentDefinitionIds` | Equipment concepts specifically associated with this variation |
| `status` | Active/deprecated/retired |

Use a variation ID when a difference materially changes movement execution, recording or comparability. Do not invent variation metadata from historical names. A variation and its parent are not automatically interchangeable for history or progression. The exact taxonomy (e.g. whether grip changes merit a variation) remains a review decision.

### 3.3 Equipment definitions — `equipmentDefinitions`

A controlled taxonomy of equipment concepts, such as dumbbell, barbell, cable station or selectorised machine. IDs are opaque and stable (`eqd_...`). Definitions may have category, label and status.

This is deliberately separate from the existing `equipment` store, which represents the user's selected/owned equipment records. A user equipment record may optionally reference an equipment-definition ID after a verified match. Do not repurpose existing user equipment IDs as catalogue IDs.

### 3.4 Performed exercise records — existing `exerciseRecords`

Keep the existing session-scoped `id`, `sessionId`, exact `name`, set relationships and raw legacy values. Add only optional, additive identity fields in a later implementation:

- `exerciseDefinitionId` — nullable until verified.
- `exerciseVariationId` — nullable unless a specific variation is verified.
- `identityStatus` — `unresolved` or `verified`.
- `identityResolutionId` — optional reference to the review event that established the link.

The exact historical/performed name and `legacyRawValue` are evidence and must never be overwritten by a canonical display label. Existing set weights, repetitions, durations and blank values remain untouched.

A record with no verified link stays unresolved. Do not group unresolved records across sessions merely because their names are equal or normalise similarly. Once verified, cross-session history can group by `exerciseDefinitionId` and, where present, `exerciseVariationId`. Never fall back to fuzzy name matching.

### 3.5 Verified aliases — `exerciseAliases`

An alias is a reviewed mapping from a source-specific exact string to one canonical definition (and optionally one variation).

Required fields:

- opaque `id`
- `sourceNamespace` (e.g. V21.1 exercise-library name, or a separately identified user vocabulary)
- `exactValue` (preserved exactly, including case, punctuation and whitespace)
- `exerciseDefinitionId` and optional `exerciseVariationId`
- `verificationStatus`: `unreviewed`, `verified`, `ambiguous` or `rejected`
- evidence/provenance, reviewer and review timestamp

Only a unique, verified, exact source/value mapping can resolve automatically. Normalised text may be used to suggest candidates in a review UI, but must not be a unique key or automatic mapping rule.

Two different exact aliases may share a normalised search key and still be separately verified if the source evidence distinguishes them. A legacy configuration key that already collapsed those names is different: it has lost the distinguishing information and remains unresolved unless other evidence uniquely identifies its target.

### 3.6 Unresolved legacy records

Do not create fake canonical definitions to make migration appear complete.

An unresolved performed record keeps:
- original session-scoped record ID;
- exact supplied name (including blank/missing state);
- original raw JSON and source key/index;
- all original set values;
- null/absent canonical definition and variation IDs;
- `identityStatus: "unresolved"` when the new field is introduced.

If a separate review/audit store is later added, it should be append-only and record the evidence, reviewer, previous and new mapping, and timestamp. A correction must not rewrite the historical source evidence.

### 3.7 Programmes, versions and slots

Use the existing `programmes` store for the stable programme identity only after checking existing record compatibility. Do not confuse it with calendar `schedules`.

Add a `programmeVersions` record per version:
- immutable opaque `id` (`prv_...`);
- `programmeId`;
- monotonically assigned `versionNumber`;
- `status`: draft, published or retired;
- optional `basedOnVersionId`;
- created/published timestamps.

A published version is immutable. Changes create a new version; do not edit a published plan in place.

Add `programmeSlots` records:
- unique version-scoped opaque `id` (`psl_...`);
- `programmeVersionId`;
- `slotLineageId`, stable across versions only when it is the same logical programme position;
- day/section and order;
- `exerciseDefinitionId` and optional `exerciseVariationId`;
- prescription fields (sets, rep/time targets, rest, notes) kept separate from exercise identity.

When a programme is revised, create new slot records for the new version. Reuse the lineage ID for a continuing logical slot. If the exercise is swapped, update the assignment in the new version only. A performed session should optionally reference the exact `programmeVersionId` and `programmeSlotId` used at the time, so later programme edits cannot rewrite what was prescribed or performed.

### 3.8 Reusable exercise configuration — `exerciseConfigurations`

Store reusable per-profile exercise preferences by identity, not by name:

- opaque `id` or deterministic composite key built only from stable IDs;
- `profileId`;
- `exerciseDefinitionId`;
- optional `exerciseVariationId`;
- optional equipment-definition context when the setting genuinely depends on it;
- `settings` object for reusable defaults (not workout results);
- timestamps and provenance.

The logical uniqueness scope is profile + definition + variation + optional equipment context. A variation-specific setting must not silently overwrite the base exercise setting. Programme-slot prescriptions belong to programme slots; actual sets/loads/reps belong to performed exercise/set records. Keep those three concepts separate.

Do not migrate legacy name-derived exercise configurations when the old key is collision-prone. Preserve the raw preference in `preferences`/`legacyRecords` and mark it unresolved until a unique mapping is supported.

## 4. Identity and matching rules

1. IDs are immutable, opaque and never generated from mutable names.
2. Exercise definition, variation, performed record, programme version, programme slot and equipment definition have different ID namespaces.
3. A performed record may exist without a canonical identity.
4. History grouping requires verified canonical IDs. Variation-aware history uses both definition and variation IDs.
5. Exact aliases are source-scoped and reviewed. Fuzzy/normalised matching only suggests candidates.
6. Ambiguous aliases/configurations stay unresolved; never choose the first match.
7. Names and raw source JSON remain as historical evidence.
8. Programme version and slot history is immutable after publication.
9. Equipment requirements reference equipment definitions, not the user's equipment-record IDs.
10. Configuration defaults, programme prescriptions and performed measurements are separate data.

## 5. Proposed IndexedDB store/index additions

Candidate stores (subject to DB migration design and compatibility tests):

- `exerciseDefinitions`: `by_status`, optionally `by_kind`.
- `exerciseVariations`: `by_definition`, `by_status`.
- `equipmentDefinitions`: `by_category`, `by_status`.
- `exerciseAliases`: `by_source`, `by_definition`, and a non-unique `by_normalized_search` suggestion index. Never make the normalised index unique.
- `programmeVersions`: `by_programme`, `by_status`.
- `programmeSlots`: `by_version`, `by_lineage`, `by_exercise_definition`.
- `exerciseConfigurations`: `by_profile`, `by_exercise_definition`.

Existing `exerciseRecords` may gain non-unique indexes for definition, variation and identity status. The schema version must be incremented only when implementation is approved. Every added store must be included in full backup validation, preview, restore and safety snapshot logic. Schema upgrades must preserve all existing stores and records.

## 6. Migration and rollout sequence

1. Add schema and pure validation services without modifying V21.1.
2. Seed a reviewed catalogue with immutable IDs; include provenance for each curated entry.
3. Add definition/variation/equipment and programme-version/slot tests.
4. Add optional identity references to new performed records; leave existing records unresolved by default.
5. Add exact alias review and an explicit resolution workflow.
6. Only apply a mapping when source namespace + exact value has one verified target. Never infer from fuzzy similarity.
7. Keep colliding name-derived configuration preferences untouched until uniquely resolved.
8. Extend backup/restore and test old backup compatibility before rollout.
9. Add history/config lookups by canonical IDs; unresolved records remain visible but are not merged.
10. Validate migration idempotence, restart safety, backups, offline operation and browser/source bundle parity.

## 7. Test contract added with this proposal

`tests/exercise-identity-contract.test.js` is a design-level acceptance contract. It uses representative records and pure assertions to pin the identity boundaries before production code is written. It is not evidence that the application already supports these entities. The implementation phase must move these assertions onto the actual service APIs and IndexedDB persistence.

The contract covers:
- opaque immutable IDs independent of labels;
- variation-parent relationships and distinct variation identity;
- equipment catalogue references separate from user equipment;
- immutable programme versions and version-specific slots with lineage;
- exact verified alias resolution despite normalisation collisions;
- ambiguous legacy config keys remaining unresolved;
- raw historical names/values preserved on unresolved records;
- configuration identity scoped by profile/definition/variation/equipment;
- performed record identity remaining separate from canonical exercise identity.

## 8. Explicitly open decisions

- Which movement differences warrant a separate exercise definition versus a variation.
- Exact controlled vocabularies for movement patterns, muscles, equipment and variation attributes.
- Whether system catalogue data is shipped as versioned static data, persisted IndexedDB records, or both.
- Exact programme day/section model and slot-lineage continuity rules.
- Whether identity review events are embedded in metadata or stored in a dedicated append-only store.
- The settings allowed in reusable configuration versus programme prescriptions.
- No real user legacy dataset has been examined for actual collisions; test examples characterize known source behavior, not the user's personal records.
