## 1. Why this gate is required

This work introduces durable identity decisions and new persistent relationships. Errors could silently rewrite history, lose review evidence, broaden day-specific preferences across programmes, or make old backups impossible to restore. These are difficult-to-reverse data and compatibility risks.

## 2. Current-state evidence

Inspected live source and tests at the reviewed branch:

- `src/data/database.js`: IndexedDB schema version 5; current stores include `exerciseRecords`, `setRecords`, `preferences`, `metadata` and `legacyRecords`; no canonical identity, catalogue release, audit-event or exercise-configuration stores.
- `src/data/backup.js`: backup format version 1; fixed explicit `STORE_NAMES`; validation requires every listed store and rejects unknown stores. Restore clears and replaces the listed stores atomically after confirmation and stores a pre-restore safety snapshot.
- `src/data/gym-migration.js`: creates session-scoped performed exercise records and preserves exact names/raw source values; it does not establish canonical identity.
- `src/programme-manager/programme-manager.js`: calendar schedule validation/summaries only; no programme-version/slot service.
- Protected V21.1 `index.html` (read-only): legacy exercise config key includes day number plus normalised name. Persisted values include set count, progression focus and recording mode; reads can materialise defaults. This is not a safe global identity key.
- `tests/exercise-identity-contract.test.js`: 16 design-level fixture tests; not production persistence tests.
- Browser and backup workflows both passed on the reviewed base SHA `c40309bb20551459b67ee77d2d321417bbdcf054`.

## 3. Recommended decisions

### A. Review history
Use a dedicated profile-owned append-only `identityReviewEvents` store. Write only with `add()`; mandatory profile-scoped idempotency key and unique index; corrections append a reversal/superseding event. Current alias/mapping rows are rebuildable projections, never the audit source. Include events in full backup/restore.

### B. Catalogue durability
Immutable versioned bundled releases with checksums. Pin release IDs in programme versions, sessions and review events. Retain referenced releases; tombstone retired entries and never reuse IDs. Store immutable display snapshots on programme slots and performed records so old history renders without the old release asset. Preserve raw historical names separately.

### C. Reusable configuration
Allow only `preferredProgressionFocus` and a supported `recordingModeOverride` in the first reusable exercise configuration model. Key by profile + definition + optional variation + optional equipment context. Set count, rep/time targets, rest, tempo, effort targets and cues belong to programme prescriptions; actual load/reps/duration/RIR/symptoms/notes belong to performed records. Keep global rest as a profile preference.

Do not automatically migrate V21.1 day-scoped, normalised-name configuration keys. Preserve exact key and raw value unresolved until both exercise identity and intended scope are independently established.

## 4. Implementation options and recommendation

| Option | Benefit | Risk |
|---|---|---|
| Store review state only in mutable aliases/metadata | Fewer stores | No trustworthy audit trail; edits can erase prior decisions |
| Dedicated append-only event store plus rebuildable projection | Corrections are traceable; retries can be idempotent | Requires careful service and backup design |
| Keep only current catalogue labels | Smaller snapshots | Historical display changes or fails when old release is absent |
| Immutable release archive plus display snapshots | Durable history without bundling every release into each backup | More explicit retention/reference logic |
| Treat all old config as reusable global settings | Fast migration | Spreads day-specific settings and collisions across programmes |
| Typed allow-list; legacy values unresolved pending scope evidence | Conservative, predictable | Some preferences require user re-entry/review |

**Recommendation:** adopt the dedicated event log, immutable release + snapshot model and strict typed configuration allow-list. Prefer safe unresolved legacy data over a falsely complete migration.

## 5. Scope and non-goals

In scope for a later approved implementation:
- additive stores/services and indexes for the canonical identity model;
- append-only review event writes and projection rebuild/consistency checks;
- immutable release metadata/reference checks and historical display snapshots;
- typed configuration validation and profile isolation;
- backup/restore compatibility and real browser/IndexedDB tests.

Not authorised/in scope:
- no changes to V21.1 or production `main`;
- no automatic fuzzy identity assignment or bulk legacy preference migration;
- no cross-profile/cloud synchronization or central review service;
- no release garbage collection in the first implementation;
- no production deployment or destructive data rewrite;
- no expansion of initial-release scope into advanced analytics or integrations.

## 6. Compatibility, migration and recovery requirements

1. Preserve every current V21.2 v5 record and all V21.1 raw names/config keys/values. Existing performed records remain unresolved unless explicitly verified.
2. If the branch is still schema v5 when implementation begins, plan an additive upgrade to the next schema version (likely v6 only if no intervening schema change); re-read the live branch before choosing the version.
3. Introduce a new backup writer format (recommended v2) containing all new user-owned stores. Keep a v1 reader adapter that accepts the exact old v1 store set and supplies empty arrays for newly introduced stores internally; never mutate the user's original backup object. Do not silently reinterpret unknown future formats.
4. Before migration, require a user-visible safety backup and verify its parse/validation. Keep it until the post-migration backup/restore round trip succeeds.
5. Make schema upgrade atomic, additive, restart-safe and idempotent. Do not attempt destructive IndexedDB downgrade; recover by stopping writes and restoring the pre-upgrade safety snapshot through a tested forward-compatible restore path.
6. Keep new identity writes disabled until schema, audit, backup and restore tests pass.
