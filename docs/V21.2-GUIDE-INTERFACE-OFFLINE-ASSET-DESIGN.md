# V21.2 exercise-guide interface and offline asset design

**Status:** Design specification plus an inert V21.2-local asset package. The 41-file package and SHA-256 manifest are committed; no application code, catalogue records, database schema, backup format or service-worker behaviour has changed.
**Branch basis:** `V21.2-development` at validated checkpoint `19acfef3b942342551fee34628e703c91f097f55`.
**Protected source:** root `index.html`, blob `e3eb0093648cc6c5d706bb5b1008b58ec01a5576` (read-only).
**Purpose:** define how reviewed exercise guides, equipment references, muscle illustrations and the existing celebration artwork will be delivered and used offline in V21.2.

## 1. Current V21.2 boundary

The current V21.2 app is a local-first shell with Overview, Gym history, Hiking, Assessments, Schedule and Data/backup views. It does not yet contain the legacy five-day Gym workout interface or an exercise-guide modal. Therefore this design is a future Gym-workout component contract; it must not be bolted into the existing Gym history screen as though the workout UI already exists.

The V21.2 service worker is scoped to `/v21.2/`, uses shell cache `project-comeback-v21-2a-shell-v16`, and currently precaches application files but no guide artwork or celebration GIFs. Catalogue release assets already have a separate verified cache namespace and must remain separate from static guide artwork.

The legacy root app remains the source of truth for existing interactions and artwork mapping. Do not modify it.

## 2. Existing guide behaviour to preserve

The protected legacy source establishes these behaviours:

- An exercise heading/card opens its guide after a 450 ms pointer hold.
- Pointer release, pointer leave and pointer cancel clear the pending hold.
- Enter and Space open the guide from the keyboard.
- The guide contains an equipment reference, exercise-specific how-to text, muscle-group illustrations and a safety reminder.
- The exercise card advertises the hold interaction with “HOLD FOR GUIDE”.
- Existing exercise actions, including set completion, rest, collapse and safer swap, stop pointer events from bubbling into the hold handler.
- The original workout uses the selected Gym/Home context to choose an equipment reference.
- The save-session celebration uses one of three GIFs, selected by profile preference and workout day, runs for six seconds and can be dismissed early.

V21.2 should preserve the 450 ms hold and keyboard activation, while improving the modal's accessibility and robustness:

1. Use a real labelled dialog (`role="dialog"`, `aria-modal="true"`, `aria-labelledby`) with a visible Close button.
2. Move focus into the dialog on open, keep keyboard focus inside while open, close on Escape, and restore focus to the invoking exercise heading.
3. Keep the legacy “hold the same exercise again to close” affordance where practical, but never make it the only way to close.
4. Cancel the pending hold on pointerup, pointerleave, pointercancel, lost pointer capture, or meaningful pointer movement. Do not block normal vertical scrolling on touch.
5. Do not start a hold from buttons, inputs, links, swap controls, collapse controls or set controls inside the exercise card.
6. Keyboard Enter/Space must open the guide without double-triggering; Space must not scroll the page when used on the focused exercise heading.
7. Honour reduced-motion preferences and keep the guide usable at narrow phone widths and desktop widths.
8. An image load failure must not hide the guide text or break the dialog. Show a labelled illustration-unavailable fallback and record the failed asset in tests.

The guide is read-only reference content. Opening or closing it must never change sets, workout logs, rest timers, exercise swaps, completion states or programme progression.

## 3. Proposed guide presentation

### Desktop

- Dialog header: exercise display name, optional variation label, explicit Close button.
- Main content in two columns:
  - **Movement:** equipment reference image and its “illustrative equipment reference” caption; setup; numbered movement steps; concise coaching cues.
  - **Muscles and safety:** muscle illustration tiles with accessible labels; source muscle-group wording; exercise-specific safety notes and any reviewed regression/alternative.
- Use the existing V21.2 dark visual language and accent system. Do not copy the legacy page's entire visual skin into the new app.

### Mobile

- Single-column order: title/close, equipment reference, setup, movement, cues, muscle illustrations, safety.
- Images scale to container width without horizontal scrolling. Keep Close reachable without scrolling back to the top (sticky dialog header is acceptable if tested).
- Avoid dense multi-column muscle grids on narrow screens.

### Content states

- `complete`: reviewed, exercise-specific guide fields and all required local assets resolve.
- `incomplete`: guide record exists but one or more required content/review fields are missing. Display a clear “Guide being prepared” state; do not show generic filler as if it were specific instruction.
- `unavailable`: no guide record exists for this exercise/variation. Explain that the guide is not yet available; do not silently substitute a different exercise's guide.
- A variation may inherit only explicitly approved shared content. Equipment geometry, body position, grip, angle and execution differences must not be hidden by a generic parent guide.

The 27 missing-guide drafts and the 25 existing descriptions remain review copy until qualified human review. The guide UI must not elevate draft wording to production status automatically.

- Keep all V21.2 runtime asset paths inside `v21.2/`. Do not reference root `/assets/` or root GIF paths from the V21.2 app.

The manifest at `v21.2/assets/guides/manifest.v1.json` is the authoritative inventory. It contains 41 assets totalling 2,984,584 bytes: 13 equipment SVGs, 9 unique equipment-reference JPGs, 16 muscle JPGs and 3 celebration GIFs. The package was committed at `740af8bd68ed6a1d424fa0ee3097a60c98492531`. Destination tree entries reuse the exact original Git blobs; no binary was re-encoded or recompressed. A post-commit directory/manifest check found 41 listed files, matching total byte length and zero source-blob/size mismatches. Each manifest entry contains:

- Stable `assetId` (not a display name or filesystem-derived exercise ID).
- Relative V21.2 URL/path.
- MIME type.
- Exact byte length.
- SHA-256 digest of the exact file bytes.
- Asset role (`equipment-illustration`, `equipment-reference`, `muscle-illustration`, or `celebration`).
- Source path and source Git blob SHA for provenance.
- Optional source aliases where exact duplicate content is intentionally shared.

The manifest itself should have a version and schema version. The guide records refer to `assetId`, never construct filenames from exercise names or muscle labels at runtime.

## 6. Offline delivery design

Keep the static guide-art cache separate from both the app-shell cache and the immutable exercise-catalogue release cache.

Proposed cache namespace:

`project-comeback-v21-2a-guide-assets-v1`

Proposed service-worker behaviour:

1. The versioned guide manifest is available from the V21.2 app shell.
2. During service-worker installation, fetch each manifest-listed asset from the same origin.
3. Check HTTP success, expected MIME type, exact byte length and SHA-256 before putting the response into the new guide cache.
4. Do not mark installation successful if any required guide/celebration asset is missing or corrupt.
5. If staging fails, delete the incomplete new guide cache and reject installation. The currently active service worker and its existing caches remain usable.
6. On successful activation, retain the newly verified guide cache and remove only obsolete caches with the guide-cache prefix. Never delete catalogue-release caches or user data.
7. Fetch handling for the guide/celebration asset path serves the dedicated guide cache first. It must not silently add an unverified asset to the shell cache.
8. A cold offline start must be able to open every production guide and play the selected celebration without network access.
9. If a guide image is unavailable despite the verified-cache guarantee (for example, local cache eviction/corruption), show the graceful fallback and never break the exercise/session controls.

This is a design contract, not a direction to change `sw.js` now. The final cache strategy and size must be verified in the target browsers before implementation.

## Verified guide artwork cache implementation — 2026-11-18

- Implemented a dedicated service-worker cache namespace: `project-comeback-v21-2a-guides-v1`. It is separate from shell cache v16 and the verified catalogue release cache.
- Service-worker installation fetches the V21.2-local manifest and validates its identity, schema/version, exact 41-entry inventory, unique IDs/paths, local-only paths, allowed artwork roots, MIME/extension agreement, per-file byte length, SHA-256 and aggregate 2,984,584-byte total.
- All 41 responses are fetched and verified before the staging cache is populated. Staged bytes are read back and verified. Only then are they copied into the versioned guide cache and verified again. Any install failure rejects the new service worker; staging is cleaned and the prior active worker remains in control.
- Guide and celebration requests are intercepted before generic shell caching and served from the dedicated guide cache, with network fallback only on a cache miss. Catalogue request routing remains unchanged.
- Activation removes obsolete shell and guide cache versions only after the new worker has installed successfully; catalogue caches remain outside both cleanup prefixes.
- Browser validation checks the complete 41-file dedicated cache and confirms guide artwork has not polluted shell cache v16. The manifest status is updated to `verified-offline-cache-v1`.
- This step does not wire the guide artwork into the current history-only UI, add guide content, alter the database/backup/history contracts, modify protected root `index.html`, merge or deploy.
- Exact-SHA browser and backup workflows must pass before this cache integration checkpoint is considered validated.


## Cache publication safety and browser MIME correction — 2026-11-18

The first browser run exposed a validation-harness issue: the local Playwright HTTP server did not return the declared MIME types for SVG, JPG/JPEG and GIF. The server now explicitly serves `image/svg+xml`, `image/jpeg` and `image/gif`, so the service worker's strict MIME checks test real response metadata rather than rejecting valid files due to the fixture server's generic fallback.

The cache publication algorithm is also tightened. A guide cache version is immutable once published. Installation fully verifies the manifest and all assets in a staging cache, then:
- If the target version cache already exists, it is verified read-only (manifest digest, all asset digests, and exact 42-entry inventory). It is never overwritten or repaired in place. A mismatch fails installation and requires a new cache version.
- If the target version cache does not exist, the worker creates that new version only after staging verification, copies and verifies every entry, and deletes that newly-created cache if publication fails.
- A failed install always removes staging. It never deletes or mutates an already-published guide cache that an older active worker could still use.
- The existing activation cleanup removes obsolete guide versions only after the new worker has successfully installed and activated.

This makes the cache version itself the update boundary: any changed manifest or artwork requires a new `GUIDE_CACHE_NAME` version. This avoids unsafe in-place replacement of a cache that may still be serving the active worker.


## Failed-update preservation browser test — 2026-11-18

The Playwright harness now deliberately simulates a new service-worker release using guide cache v2, then returns HTTP 503 for one manifest-listed guide SVG during installation. Acceptance requires the new worker to become redundant (install rejected), the active worker script/controller to remain unchanged, guide cache v1 to retain its manifest and all 41 assets (42 cache entries total), no v2 cache to be published, and the previously cached SVG to remain fetchable after switching the browser offline. This directly exercises the fail-closed update path rather than relying only on source-level assertions.
