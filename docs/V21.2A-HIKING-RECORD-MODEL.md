# Hiking Preparation — Record Model (V21.2A)

Status: proposed implementation contract for the initial manual-recording release.
Scope: completed hikes entered manually. This document does not assert that V21.1 contains Hiking records; no V21.1 Hiking migration is defined.

## Ownership and storage

- Store: `hikingRecords`.
- Owner: Hiking Preparation module (`moduleId: "hiking"`).
- The module registry is the only module boundary used to create/read Hiking-owned records. Gym sessions, exercise records and set records remain Gym-owned.
- Disabling Hiking prevents new Hiking writes but does not delete existing Hiking records. Re-enabling restores access to the retained records.
- A hike is not a Gym session and is never written to `sessions`, `exerciseRecords` or `setRecords`.
- Shared schedules may reference a Hiking programme through `programmeId`; schedule entries are not substitutes for completed Hiking records.

## Initial record shape

Example:

```json
{
  "id": "hike-<stable-id>",
  "moduleId": "hiking",
  "status": "completed",
  "date": "2026-11-16",
  "title": "You Yangs circuit",
  "routeName": "East-West Walk",
  "distanceKm": 7.4,
  "durationMinutes": 105,
  "elevationGainM": 240,
  "terrain": "Rocky trail",
  "notes": "Manual entry",
  "programmeId": null,
  "createdAt": "2026-11-16T01:00:00.000Z",
  "updatedAt": "2026-11-16T01:00:00.000Z"
}
```

### Fields

| Field | Requirement | Meaning |
|---|---|---|
| `id` | Required | Stable, unique record ID |
| `moduleId` | Required; fixed value `hiking` | Establishes Hiking ownership |
| `status` | Required; initial completed-record value is `completed` | Keeps completed activity distinct from planned schedule entries |
| `date` | Required | Local calendar date of the hike, `YYYY-MM-DD` |
| `title` | Required | User-facing name for the activity |
| `routeName` | Optional | User-entered route/trail name; descriptive only |
| `distanceKm` | Optional | Manually entered distance in kilometres |
| `durationMinutes` | Optional | Manually entered elapsed duration in minutes |
| `elevationGainM` | Optional | Manually entered ascent in metres |
| `terrain` | Optional | Short free-text terrain description |
| `notes` | Optional | User notes |
| `programmeId` | Optional | Related Hiking programme, when applicable |
| `createdAt`, `updatedAt` | Repository-managed | ISO timestamps maintained by the data layer |

Optional measurement fields remain optional: a user may save a hike when only some measurements are known. Missing duration is reported as missing by the descriptive workload summary; it is not estimated.

## Validation contract

- Reject missing/blank IDs, title, date or module ownership.
- Require `moduleId === "hiking"`; reject writes through the Hiking boundary to any non-Hiking store.
- Validate dates as real calendar dates in exact `YYYY-MM-DD` form; reject impossible dates.
- For a completed hike record, require `status === "completed"`. Planned, skipped or cancelled activities belong in the shared schedule model, not in completed Hiking history.
- If supplied, `distanceKm` must be a finite number greater than zero.
- If supplied, `durationMinutes` must be a finite number greater than zero. Omitted duration is valid and remains visibly missing.
- If supplied, `elevationGainM` must be a finite number greater than or equal to zero.
- Text fields must be strings when supplied; trim title and reject it if empty.
- `programmeId`, when supplied, must refer to a Hiking programme, not a Gym programme.
- Do not silently convert units or infer missing values.

## Recording workflow

1. User finishes a hike and opens Hiking Preparation's manual record form.
2. User enters the date and title, then any measurements and descriptive details they have.
3. The form validates values and saves through the Hiking module ownership boundary.
4. The saved record is available in Hiking history and full JSON backup.
5. The descriptive workload summary may count the completed hike and its recorded duration. Gym and Hiking summaries remain separate.

## Backup and restore

- The existing full versioned JSON envelope already includes the `hikingRecords` store and identifies both `gym` and `hiking` as included modules.
- No selective Hiking-only backup is introduced in this phase.
- Restore validates stable IDs and duplicate IDs for every store, previews changes, snapshots current data and restores all stores transactionally.
- New Hiking fields are stored as ordinary record properties and preserved by full JSON backup/restore. A future incompatible schema change must increment/document the relevant format or migration version; do not silently reinterpret old fields.

## Explicit exclusions from the initial record model

- No GPS coordinates, route geometry, automatic tracking, maps or background location.
- No imported V21.1 Hiking history is assumed.
- No calorie, intensity, heart-rate, effort or recovery score is inferred.
- No combined Gym/Hiking load score.
- No automatic programme changes or recovery thresholds.
- No requirement to provide every measurement before saving.

These exclusions preserve the approved initial scope: manual Hiking recording, offline-capable local storage, full backup and separate Gym/Hiking ownership.
