# C2 Stage Gate — User Equipment Inventory

**Gate ID:** V21.2-C2-USER-EQUIPMENT-INVENTORY  
**Status:** DESIGN PROPOSAL — awaiting owner decision  
**Inspected branch:** `V21.2-development`  
**Inspected HEAD:** `40a52fd1a150d3177608abfa6c4f665eb0a1e432`  
**Classification:** G2 — personal data contract, migration compatibility and backup/restore semantics

## 1. Goal and boundary

Introduce a reliable personal inventory of equipment the user can access at named locations, without confusing it with system catalogue definitions, exercise requirements, or historical V21.1 gear records.

This gate proposes a typed record contract and repository/API behaviour using the existing V6 `equipment` store and Backup V2. It does not authorise implementation until the owner passes this gate.

Included after PASS:
- typed personal equipment-access records in the existing `equipment` store;
- explicit association to a reviewed system equipment definition, or a visibly custom user-described item;
- multiple physical instances of the same definition;
- user-named locations such as Gym and Home;
- user-confirmed configuration attributes and availability;
- strict legacy-record coexistence and backup/restore coverage;
- tests for migration collision, data preservation, V1/V2 restore behaviour and exact round trips.

Not included:
- new IndexedDB store, index or database version;
- Backup V3 or any backup-format change;
- writing system equipment definitions into the personal store;
- equipment selector UI, exercise-library UI or programme builder;
- production catalogue curation, production IDs or qualified review approvals;
- injury restriction store/engine (C3), Adaptive Brain, Pages changes, deployment or merge.

## 2. Live source findings

At the inspected HEAD:

- `src/data/database.js` defines IndexedDB schema V6. The existing `equipment` store has key path `id` and only the `by_module` index on `moduleId`.
- `equipment` is part of the original V1 store set and is included in Backup V1 and V2.
- `commitLegacyMigration` projects legacy equipment into this store. It retains source `id`, `legacyKey`, `legacyRawValue` and the `migratedFromLegacy` marker. A conflicting existing record causes the whole migration transaction to abort.
- The legacy gear projection is a container of historical gym gear data, not a validated per-item inventory. It must not be interpreted as typed inventory or rewritten into the new contract.
- `src/data/backup.js` treats `equipment` as a replace store in both V1 and V2 restore. Preview calculates added/changed/removed records. Restore takes a pre-restore safety snapshot, clears replace stores and writes incoming records.
- V1 restore on a V6 database preserves the nine V6 identity stores untouched, but it currently replaces the V1 `equipment` store. Therefore a V1 backup would omit and remove any future C2 typed inventory records unless restore semantics are deliberately extended.
- Backup V2 includes the complete `equipment` store. It remains a replace store: the backup's complete equipment contents become the restored contents.

## 3. Proposed typed record contract

Use a discriminated record in the existing personal store. Suggested shape (illustrative contract, not a production record):

```js
{
  id: "user-equipment:<stable-unique-id>",
  recordType: "user-equipment-access",
  schemaVersion: 1,
  moduleId: "gym",
  profileId: "<active-profile-id>",
  itemKind: "catalogue" | "custom",
  equipmentDefinitionId: "<verified-definition-id>", // catalogue only
  catalogueId: "<catalogue-id>",                    // catalogue only
  catalogueReleaseId: "<exact-release-id>",          // catalogue only
  catalogueVersion: 1,                               // catalogue only
  customName: "<user-entered-name>",                 // custom only
  location: { id: "gym", label: "Gym" },
  instanceLabel: "<optional user label>",
  availability: "available" | "temporarily-unavailable" | "unknown",
  confirmedConfiguration: {
    loadingSystem: "<confirmed controlled value or omitted>",
    movementMechanics: "<confirmed controlled value or omitted>",
    orientation: "<confirmed controlled value or omitted>",
    setup: { /* only explicitly confirmed attributes */ }
  },
  createdAt: "<timestamp>",
  updatedAt: "<timestamp>"
}
```

The final implementation must define exact allowed keys and enums from the accepted schema. This example deliberately does not establish the catalogue vocabulary or create a real definition ID.

### Required invariants

1. **Profile ownership:** every typed record belongs to one active profile. Reads and writes must be profile-scoped; a record for another profile must not appear in the active inventory.
2. **Discriminator:** only records with the exact supported `recordType` and `schemaVersion` are treated as C2 inventory. Legacy records remain opaque legacy data.
3. **Catalogue vs custom:** a catalogue record references a system definition and exact immutable release identity. A custom record has a user-entered name and cannot satisfy a system equipment requirement by name similarity.
4. **Multiple instances:** every physical item has its own stable record ID. Two machines of the same definition at the same location are allowed and remain separately editable.
5. **Location:** Gym, Home and Other/user-named locations are location labels, not catalogue attributes. Do not assume an item is available at every location.
6. **Availability:** default to `unknown` unless the user explicitly confirms otherwise. Temporary unavailability does not delete the item or alter its configuration.
7. **Configuration:** store only user-confirmed values. Missing/unknown configuration never becomes a default inferred from the equipment name, loading system, picture or another machine.
8. **No implicit matching:** custom equipment, legacy gear strings and ambiguous records do not satisfy a reviewed catalogue requirement without an explicit, validated association.
9. **No destructive conversion:** do not auto-convert, rename, delete, split or reinterpret existing migrated records. Any future explicit association is a separate user-confirmed action and must retain original legacy evidence.
10. **No system catalogue writes:** equipment definitions remain in the exact immutable catalogue release asset/cache.

### Configuration dimensions stay orthogonal

Keep separate fields for loading/resistance system (including pin-selected and plate-loaded), movement mechanics (including fixed path or independent/iso-lateral where reviewed), physical orientation, and user fit/setup. The owner has confirmed both pin-selected and plate-loaded equipment exist in the Gym, but no particular machine's mechanics or orientation are known. Do not pre-fill individual machines from that general fact.

## 4. Database/API proposal

- Keep IndexedDB at V6 and reuse the existing `equipment` store.
- Keep the existing `by_module` index; do not add an index in this gate.
- Add dedicated validated API operations for listing, adding, updating and retiring typed inventory records. Do not rely on unrestricted generic `put` calls as the inventory validation boundary.
- Validate exact discriminator, schema version, profile ownership, item-kind-specific fields, stable IDs, location and availability enums, and the distinction between confirmed and unknown configuration.
- Updates must read the existing record and preserve immutable identity/creation fields. Retiring an item should preserve history or use a clearly defined non-destructive status; do not silently hard-delete an item.
- Generic legacy records remain accessible to migration and backup code, but are never returned as typed inventory unless they pass the discriminator and schema validator.
- Do not alter `commitLegacyMigration` projections or its idempotency/conflict rules.

## 5. Backup and restore requirements — mandatory

### Backup V2

- Keep Backup V2 unchanged as a format.
- Full V2 export includes every typed C2 inventory record in the existing `equipment` array, together with untouched legacy records.
- V2 preview must correctly count typed records as additions, changes, unchanged and removals.
- V2 restore replaces the complete equipment store as it does today. The pre-restore safety snapshot must contain the complete previous store.
- Tests must prove exact field/value round-trip, multiple same-definition instances, custom records, locations, unknown configuration, and legacy raw-source preservation.

### Backup V1 compatibility — unresolved risk that this gate must close

A V1 backup has an `equipment` array but cannot contain C2 records created after V1. Current V1 restore replaces the whole equipment store, so restoring an older V1 backup would erase those newer typed records.

Proposed safe behaviour: during V1 restore on V6, preserve valid C2 typed inventory records already in the live `equipment` store while replacing the legacy V1 equipment records from the backup. Include this preservation in preview with an explicit `preserve-untouched` or equivalent per-record/store diagnostic. Preserve only records that pass the exact C2 validator; do not preserve arbitrary malformed records as trusted inventory. Keep the V1 restore's established behaviour for all original V1 records and keep V6 identity stores untouched.

If this selective preservation cannot be implemented atomically and tested, the alternative is to block V1 restore when typed C2 records exist and explain that a V2 backup is required. Silent deletion is not acceptable.

### Required restore tests

- V2 full backup → fresh V6 database → exact typed and legacy record round-trip.
- V2 restore over existing inventory: replace semantics, safety snapshot and preview agree.
- V1 restore with no C2 inventory: existing V1 compatibility unchanged.
- V1 restore with valid C2 inventory: preserve it under the accepted policy, or block before any write.
- V1 restore with malformed discriminator/schema record: never treat it as valid C2 inventory.
- Any injected conflict/transaction failure: rollback leaves all pre-restore equipment and safety data unchanged.
- Verify restore preview matches actual committed behaviour, including preserved record counts.

## 6. Acceptance tests and release evidence

Before implementation is considered complete, tests must prove:
- legacy migrated records retain exact IDs, `legacyKey`, `legacyRawValue`, raw values and migration markers;
- migration rerun remains idempotent and collisions still abort atomically;
- new typed records cannot collide with legacy IDs or masquerade as legacy records;
- two physical instances of one system definition remain distinct;
- custom names never auto-match system definitions;
- profile boundaries are enforced;
- unknown/unconfirmed configuration remains unknown;
- catalogue record references retain their exact release identity and do not silently rebind to the newest release;
- all V1/V2 restore behaviours above;
- existing database, migration, integrity, catalogue and backup suites remain green;
- no changes to V21.1 localStorage, schema version, store/index definitions, Backup V2 format, main, Pages candidate or deployment.

The exact final branch SHA must pass both Chromium/browser validation and backup validation. Source/mirror parity must be checked for any shipped browser asset.

## 7. Decision requested

**Recommended decision:** PASS the bounded C2 data-contract/API and backup-compatibility implementation described above, including the proposed V1 selective-preservation behaviour. If that cannot be safely implemented, block V1 restore when typed inventory exists rather than silently deleting it.

A PASS does not approve the inventory UI, exercise library, programme builder, C3 restriction store, Adaptive Brain, production catalogue content or deployment. Those remain separate decisions.
