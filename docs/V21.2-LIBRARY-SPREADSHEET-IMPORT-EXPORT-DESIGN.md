# V21.2 — Library spreadsheet import/export design

**Status:** design specification only. No spreadsheet generation/import, catalogue content, UI, database change, backup change or publication is implemented here.

**Design checkpoint:** `V21.2-development` at `842f3898907f05edaed2032adffb15bbfdc2e0e9` (20 November 2026).

## 1. Purpose and boundary

The Equipment and Exercise Library must be maintainable outside the application through a structured spreadsheet workflow. An authorised catalogue maintainer should be able to download the current catalogue into an Excel workbook, edit reviewed names and descriptions, propose new equipment/exercise entries, maintain controlled muscle-group and movement vocabularies, then upload the workbook for validation and review.

This is a **system-catalogue maintenance workflow**, not a user's personal equipment inventory import. Personal equipment access, quantities, weights, machine configurations, availability and locations remain user-owned records. A catalogue workbook must never overwrite them.

The workbook is an authoring/review format, not a published catalogue release. Uploading must never activate changes automatically.

## 2. Format and compatibility

- Preferred exchange format: `.xlsx`, because the catalogue is relational and benefits from separate sheets, validation lists and protected identifier columns.
- Export and import must work offline. CSV may be considered later for individual-sheet interoperability, but is not part of the first implementation contract.
- Every workbook carries a workbook schema version, catalogue ID, exported release ID/version, export timestamp and locale (initial default `en-AU`).
- The importer supports only explicitly declared workbook schema versions. It rejects unsupported versions; it never guesses or silently reinterprets columns.
- Stable IDs and relationships are preserved. Display names and descriptions are editable; IDs are not ordinary editable fields.
- Formula cells are not authoritative catalogue values. The importer reads validated literal values, not executable formulas. Macros and embedded executable content are not required.
- Where mass is represented, integer grams are canonical and kilograms are human-facing; floating-point mass is not an identity or comparison key.

## 3. Workbook structure

Exact column names and required/optional status must be finalised in the implementation schema before coding.

| Sheet | Purpose | Proposed core fields |
|---|---|---|
| Read Me | Instructions, schema compatibility and safe editing rules | workbook schema version, catalogue ID, base release ID/version, locale |
| Equipment | System equipment definitions | equipment ID, canonical name, description, equipment family IDs, supported loading-system IDs, movement-mechanic IDs, orientation IDs, setup-attribute IDs, review status |
| Exercises | Canonical exercise definitions | exercise ID, canonical name, description, body-region IDs, movement-pattern IDs, review status, provenance/review reference |
| Variations | Meaningful execution variations | variation ID, parent exercise ID, variation name, description, relevant setup attributes, review status |
| Muscle Groups | Controlled muscle/body-region vocabulary | stable vocabulary ID, canonical label, approved parent/body-region ID, aliases, definition/notes, review status |
| Movement & Demand Vocabularies | Controlled movement and demand terms | vocabulary category, stable term ID, canonical label, aliases, definition, review status |
| Equipment Requirements | Explicit equipment paths | subject type/ID, requirement group ID, alternative ID, equipment-definition ID, configuration attribute, configuration value ID |
| Aliases | Search names and alternate terms | subject type, subject ID, alias text, locale, alias type, review status |
| Change Notes | Human-readable rationale | record type/ID, change summary, evidence/source, reviewer note |

Exercise muscle involvement is relational. Each involvement entry references stable body-region/muscle IDs and has an explicit role (primary, secondary or other relevant involvement). It must not be reduced to a comma-separated free-text cell.

The current catalogue delivery contract already has a v2 payload concept for equipment definitions, controlled vocabularies, movement-demand profiles and equipment requirement alternatives. The workbook should map losslessly to that contract where it fits. It must not silently introduce a new runtime payload schema, clinical claims or database store. Any required schema evolution is a separate review and approval gate.

## 4. Identifier, naming and relationship rules

1. IDs are stable opaque identifiers. Renaming a label or description never changes its ID.
2. New rows may use a clearly marked temporary proposal key. The staging importer assigns or proposes a permanent ID only after collision and reference checks. Identity is never derived from a mutable display name.
3. References use stable IDs, never row numbers or display names.
4. Aliases are separate records. An alias does not become a canonical name and does not prove two exercises are biomechanically equivalent.
5. Canonical labels are unique within the applicable vocabulary unless an explicit reviewed disambiguation rule permits otherwise.
6. Muscle groups, body regions, movement patterns and equipment families are controlled vocabulary records, not arbitrary text values. New terms remain proposed/unreviewed until approved.
7. Muscle involvement roles are explicit. Primary/secondary involvement is never inferred from exercise names, old muscle keys or descriptions.
8. Equipment requirements use explicit alternative groups and equipment-definition IDs. Similar wording is not a valid equipment match.
9. Retirement is a status change, not hard deletion. Records referenced by exercises, programmes, historical sessions, review events or retained releases remain resolvable.
10. Original/source labels remain separate from approved canonical names wherever traceability requires it.

## 5. Download/export behaviour

- Export the selected immutable catalogue release, not unsaved staging edits.
- Include every record needed to reconstruct that release and its relationships: vocabularies, equipment definitions, exercise definitions, variations, requirement groups and aliases.
- Include release identity and integrity metadata so the importer can identify the exact base catalogue.
- Clearly mark approved, incomplete, proposed and retired records. Unreviewed source labels must not appear as approved facts.
- An untouched export re-imports to an empty semantic change set.
- Export excludes personal inventory, profile information, workout history, programme performance and private user notes.

## 6. Upload and staging validation

Upload creates a **staging change set only**. It does not write to the active catalogue, IndexedDB user equipment store, programme stores or workout history.

Validate at minimum:

- File type, workbook schema version, catalogue ID, required sheets and columns.
- Base release identity and whether the workbook is stale against the current release.
- Duplicate IDs, prohibited duplicate canonical names, duplicate/conflicting aliases.
- Missing required values, invalid statuses, locales, units and malformed identifiers.
- Broken parent, vocabulary, exercise, variation and equipment references.
- Unsupported vocabulary categories or values.
- Requirement groups with missing alternatives or unknown equipment IDs.
- Invalid configuration constraints, including values unsupported by the referenced equipment definition.
- Muscle involvement with missing/ambiguous role or IDs, and attempts to treat unreviewed terms as approved metadata.
- Attempts to change immutable IDs, delete referenced records, or overwrite protected provenance/review evidence.
- Unexpected columns or values that cannot be represented losslessly. Never silently discard unknown data.
- Formula/error cells in fields requiring literal values.

Errors block approval; warnings require explicit acknowledgement. Reports identify sheet, row, column, record ID where available, severity and a plain-language correction. Incomplete or ambiguous movement profiles remain incomplete and cannot support injury-aware alternatives.

A stale workbook is not automatically rebased. Show the base/current release difference and require a fresh export or an explicit reviewed merge.

## 7. Preview, approval and publication

After validation, show a semantic preview grouped into new records, changed records (before/after), retirements, unchanged records, validation findings and downstream references affected.

The maintainer explicitly approves the complete change set. High-impact changes (identity, equipment requirements, muscle involvement, movement-demand metadata and retirement of referenced records) require an explicit review decision and evidence reference. No silent bulk acceptance.

Approved content is compiled into a new immutable catalogue release through the existing integrity/delivery process. It receives a new release ID/version and content digest. The active release pointer changes only after the release passes validation and atomic activation checks.

Retain prior releases and their references for historical display and recovery. Rollback selects a previously retained immutable release; it does not mutate an old release or rewrite workout history.

Record the change-set identity, base release, resulting release, approval decision, reviewer scope and timestamp in an auditable manner. The persistence mechanism must be designed against existing append-only review and catalogue-release stores before implementation.

## 8. Separation and safety guarantees

- Catalogue import/export never edits a user's personal equipment, including weights, quantities, Gym/Home locations, availability or custom equipment.
- Catalogue changes never rewrite the original five-day programme, programme versions, started/completed sets or historical workout snapshots.
- Renaming a canonical exercise keeps its stable identity; old display snapshots remain unchanged.
- An alias or similar name cannot automatically verify a legacy programme-slot identity.
- Injury-aware metadata remains fail-closed. Unknown, incomplete, ambiguous or unreviewed data cannot be treated as evidence that an exercise avoids a restricted area.
- No spreadsheet field can clear a user's active training restriction or provide medical clearance.
- The workflow is offline-capable. A release is usable offline only after normal integrity-checked installation.
- The workbook is not a security boundary. The eventual workflow must define who is authorised to create, approve and publish catalogue releases; hiding a button is not sufficient authorisation.

## 9. Out of scope

- Building the workbook exporter/importer or UI.
- Creating production equipment/exercise/muscle-group content or assigning production IDs.
- Approving source labels, aliases, exercise identities, muscle involvement or injury-related claims.
- Changing the catalogue payload/manifest schema.
- Adding database stores/indexes or changing Backup V2.
- Changing personal equipment records or the Step 1 weight-inventory contract.
- Building the library UI, Equipment Manager, Programme Builder, substitutions or Adaptive Brain.
- Changing the five-day source programme, workout history, Pages candidate, deployment or `main`.
