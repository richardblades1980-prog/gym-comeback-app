# Universal Equipment Foundation — Step 1 data contract

**Status:** Step 1 implementation scope approved  
**Branch:** `V21.2-development`  
**Scope:** structured personal equipment weights and physical quantities only

## Purpose and boundaries

Step 1 extends the existing personal equipment record so users can accurately describe weights they physically own or can access. It keeps three concepts separate:

1. System equipment catalogue: the reviewed definition of what an equipment type is.
2. My Equipment: the user's own instances, locations, quantities and confirmed configurations.
3. Exercise Library: the equipment and loading requirements of a reviewed exercise.

This step implements only the personal data contract and validation tests. It does not add catalogue definitions, exercise definitions, equipment or exercise screens, programme changes, substitutions, injury logic or Adaptive Brain matching.

## Compatibility

- Keep IndexedDB at V6 and reuse the existing `equipment` store and `by_module` index.
- Keep Backup V2 unchanged. Its complete equipment-store payload already round-trips additional record fields.
- Keep existing typed record schema version 1 valid and unchanged. A version 1 record does not gain inferred or empty weight fields.
- New structured inventory uses typed record `schemaVersion: 2`. It is not an IndexedDB schema upgrade.
- Version 2 is immutable once created; updates cannot silently convert a record between schema versions.
- V1 restore continues to preserve valid typed inventory using the record validator, now including valid version 2 records. Legacy equipment records continue to be replaced from the V1 backup. ID collisions stop restore before commit.

## Weight inventory envelope

Every version 2 record has an explicit `weightInventory`:

```js
{
  status: "unknown" | "not-applicable" | "confirmed",
  entries: []
}
```

- `unknown`: the user has not confirmed the available weights; entries must be empty.
- `not-applicable`: the item has no separately recorded weight inventory; entries must be empty.
- `confirmed`: one or more validated entries are present. An empty array is not interpreted as a confirmed zero inventory.
- New version 2 records default to `unknown`, never to an assumed weight or quantity.

All mass values are positive safe integers in **grams**. Kilograms are a display/input convention; conversion to grams occurs before persistence. No floating-point mass values are stored.

## Entry types

Each entry has a unique, non-empty ID within its parent record.

### Fixed dumbbells, kettlebells and medicine balls

```js
{
  id: "db-5kg-pair",
  kind: "fixed",
  equipmentType: "dumbbell" | "kettlebell" | "medicine-ball",
  massGrams: 5000,
  quantity: 2,
  grouping: "individual" | "matched-pairs"
}
```

`quantity` is the actual number of physical items, not a count of pairs. A matched-pairs group must therefore have an even physical quantity. A single kettlebell is quantity 1 and grouping `individual`.

### Adjustable dumbbells

```js
{
  id: "adjustable-pair",
  kind: "adjustable-dumbbell",
  handleCount: 2,
  minimumMassGrams: 2500,
  maximumMassGrams: 24000,
  incrementMassGrams: 500
}
```

The range describes the usable mass per handle. Handle count is the actual number of handles (one or two). The minimum, maximum and increment are positive integer grams; maximum cannot be below minimum, and the range must divide exactly into the stated increment. Record the actual available increment, not merely the maximum.

### Bars

```js
{
  id: "bar-20kg",
  kind: "bar",
  barType: "barbell" | "ez-curl-bar",
  massGrams: 20000,
  quantity: 1,
  compatibilityGroup: "olympic-50mm"
}
```

Bar mass is recorded separately from plates. A bar never implies that plates are included. `compatibilityGroup` is optional user-confirmed text; absence means compatibility is unknown, not assumed.

### Weight plates

```js
{
  id: "plate-2-5kg",
  kind: "plate",
  massGrams: 2500,
  quantity: 4,
  grouping: "matched-pairs",
  compatibilityGroup: "olympic-50mm"
}
```

Plate quantity counts individual physical plates. Matched-pair quantities must be even. A plate and bar are only associated by an explicitly confirmed matching compatibility group; names or weights do not establish fit.

## Validation and safety rules

- Reject fractional grams, non-positive mass, non-integer or non-positive quantities, duplicate entry IDs and unknown fields.
- Reject odd physical quantities when grouping is `matched-pairs`.
- Reject adjustable ranges that cannot be represented exactly by the declared increment.
- Reject entries when status is `unknown` or `not-applicable`; reject empty `confirmed` inventories.
- Do not assume a pair, set, bar, plates, plate fit, adjustable increment, machine loading system or weight from an equipment name.
- Keep Gym, Home and named Other locations independent from weight data.
- Preserve the existing version 1 record contract and legacy raw equipment data without automatic conversion.

## Acceptance evidence

The Step 1 test suite must prove version 1 compatibility, version 2 validation, exact integer-gram round trips, physical quantity semantics, adjustable range validation, V1 restore preservation of version 2 inventory, V2 backup round-trip and unchanged legacy records. The exact final commit must pass both backup and Chromium/browser workflows.

No production catalogue, exercise library, UI, programme, injury, Adaptive Brain, Pages or deployment change is included.
