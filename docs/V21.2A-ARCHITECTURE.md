# Project Comeback — V21.2A Architecture

Status: approved design baseline; implementation not yet complete.
Baseline: Gym Comeback V21.1B.2.1.
Development branch: V21.2-development.

## Approved decisions

- IndexedDB is the primary application database.
- Full JSON backup is the primary backup format.
- Full backups include shared data and both modules. Selective module exports are deferred until the full backup/restore path is proven.
- Gym Comeback and Hiking Preparation are both first-class modules.
- The existing main branch and V21.1B.2.1 release remain untouched during development.

## Architecture boundaries

1. Presentation layer: shared shell and module-specific screens.
2. Module layer: Gym and Hiking own their specialised programme logic and records.
3. Shared services: profile, objectives, equipment, readiness, recovery, scheduling and backup.
4. Persistence layer: IndexedDB repositories, migration and validation.
5. Offline layer: service worker caches application files; it does not synchronise user data.

Modules communicate through documented shared-service interfaces. Hiking records must not be written as gym workouts, and gym logic must not directly mutate hiking records.

## Initial IndexedDB stores

- profile
- objectives
- equipment
- readiness
- weighIns
- modules
- programmes
- sessions
- exerciseRecords
- setRecords
- hikingRecords
- schedules
- progression
- preferences
- metadata
- legacyRecords (temporary compatibility and exact-value preservation for the V21.1 migration)

All module-owned records include moduleId (gym or hiking), stable IDs, createdAt and updatedAt. Shared records remain module-neutral.

## Migration requirements

Migrate V21.1B.2.1 localStorage data without deleting the source keys during the migration.

Migration sequence:
1. Detect source version and existing destination database.
2. Create a complete safety JSON backup.
3. Initialise the IndexedDB schema.
4. Copy and normalise legacy records using deterministic IDs.
5. Verify counts and critical values, including workout logs, timed sets, profile, objectives, equipment, readiness, weigh-ins, swaps, exercise configuration and preferences.
6. Mark migration complete only after verification.
7. Keep legacy data until a later release explicitly retires it.

Migration must be restart-safe and idempotent. A failed migration must leave original data intact.

## Backup format

The V21.2A backup service currently implements the full JSON envelope. It validates every expected store, checks stable record IDs and duplicate IDs, and provides a non-destructive restore preview showing per-store additions, changes, unchanged records and removals. Restore writes all stores in one IndexedDB read-write transaction. A complete pre-restore snapshot is retained in metadata as part of that same transaction. Restore requires an explicit confirmation flag at the service boundary.

The versioned envelope includes:
- app identifier and app version
- backup format version
- export timestamp
- included modules
- shared data
- gym data
- hiking data
- programme-manager data

Restore must validate before writing, preview changes, create a pre-restore safety backup, detect duplicates and conflicts, and use an IndexedDB transaction. It must never silently overwrite newer records.

## Programme manager

The shared programme-manager service now supports dated schedule entries for Gym and Hiking, status validation, module-separated day summaries, date-range summaries, readiness context, and a same-day coordination flag when both modules are scheduled. It does not rewrite workouts, prescribe recovery thresholds, or combine gym and hiking workloads into a single score. These behaviours are deliberately conservative until explicit progression and recovery rules are approved.

The service requires an initialised module registry before new schedule entries can be saved. Disabling a module prevents new schedule entries for it but does not delete its existing records.

## Module removal

Disabling Hiking must leave Gym and shared data operational. Hiking records are retained unless the user explicitly requests deletion. Disabling a module is not deletion of its data.

## Build sequence

- V21.2A.1: IndexedDB schema and repository layer.
- V21.2A.2: legacy localStorage migration and verification.
- V21.2A.3: versioned full backup and safe restore.
- V21.2A.4: module registry and service boundaries (foundation committed).
- V21.2A.5: programme-manager scheduling and regression checks (in progress).
- V21.2A.6: browser/device regression tests and offline verification.

## Non-goals for this phase

- No automatic cloud synchronisation.
- No rewrite of the existing workout interface before data migration is proven.
- No changes to the main branch.
