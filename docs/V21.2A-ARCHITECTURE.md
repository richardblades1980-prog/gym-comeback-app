# Project Comeback — V21.2A Architecture

Status: approved design baseline; implementation not yet complete.
Baseline: Gym Comeback V21.1B.2.1.
Development branch: V21.2-development.

## Approved decisions

- IndexedDB is the primary application database.
- Full JSON backup is the primary backup format.
- Full backups include shared data and both modules. Selective module exports are deferred until the full backup/restore path is proven.
- Gym Comeback and Hiking Preparation are both first-class modules.
- The existing main branch and V21.1B.2.1 release remain untouched during development.

## Architecture boundaries

1. Presentation layer: shared shell and module-specific screens.
2. Module layer: Gym and Hiking own their specialised programme logic and records.
3. Shared services: profile, objectives, equipment, readiness, recovery, scheduling and backup.
4. Persistence layer: IndexedDB repositories, migration and validation.
5. Offline layer: service worker caches application files; it does not synchronise user data.

Modules communicate through documented shared-service interfaces. Hiking records must not be written as gym workouts, and gym logic must not directly mutate hiking records.

## Initial IndexedDB stores

- profile
- objectives
- equipment
- readiness
- weighIns
- modules
- programmes
- sessions
- exerciseRecords
- setRecords
- hikingRecords
- schedules
- progression
- preferences
- metadata
- legacyRecords (temporary compatibility and exact-value preservation for the V21.1 migration)

All module-owned records include moduleId (gym or hiking), stable IDs, createdAt and updatedAt. Shared records remain module-neutral.

## Migration requirements

Migrate V21.1B.2.1 localStorage data without deleting the source keys during the migration.

Migration sequence:
1. Detect source version and existing destination database.
2. Create a complete safety JSON backup.
3. Initialise the IndexedDB schema.
4. Copy and normalise legacy records using deterministic IDs.
5. Verify counts and critical values, including workout logs, timed sets, profile, objectives, equipment, readiness, weigh-ins, swaps, exercise configuration and preferences.
6. Mark migration complete only after verification.
7. Keep legacy data until a later release explicitly retires it.

Migration must be restart-safe and idempotent. A failed migration must leave original data intact.

## Backup format

The V21.2A backup service currently implements the full JSON envelope. It validates every expected store, checks stable record IDs and duplicate IDs, and provides a non-destructive restore preview showing per-store additions, changes, unchanged records and removals. Restore writes all stores in one IndexedDB read-write transaction. A complete pre-restore snapshot is retained in metadata as part of that same transaction. Restore requires an explicit confirmation flag at the service boundary.

The versioned envelope includes:
- app identifier and app version
- backup format version
- export timestamp
- included modules
- shared data
- gym data
- hiking data
- programme-manager data

Restore must validate before writing, preview changes, create a pre-restore safety backup, detect duplicates and conflicts, and use an IndexedDB transaction. It must never silently overwrite newer records.

## Programme manager

The shared programme-manager service now supports dated schedule entries for Gym and Hiking, status validation, module-separated day summaries, date-range summaries, readiness context, and a same-day coordination flag when both modules are scheduled. It does not rewrite workouts, prescribe recovery thresholds, or combine gym and hiking workloads into a single score. These behaviours are deliberately conservative until explicit progression and recovery rules are approved.

The service requires an initialised module registry before new schedule entries can be saved. Disabling a module prevents new schedule entries for it but does not delete its existing records.

## Module removal

Disabling Hiking must leave Gym and shared data operational. Hiking records are retained unless the user explicitly requests deletion. Disabling a module is not deletion of its data.

## Non-goals for this phase

- No automatic cloud synchronisation.
- No rewrite of the existing workout interface before data migration is proven.
- No changes to the main branch.

## Workload summary foundation

The shared workload-summary service provides descriptive date-range summaries for completed Gym sessions and completed Hiking records. It reports counts and recorded duration separately by module, identifies records with missing duration, and rejects invalid recorded duration values. It does not combine the two modules into a single load score, infer intensity, prescribe recovery, or change schedules. This is a measurement foundation only; any effort scale, progression thresholds or recovery recommendations require separate explicit design and validation.

## Legacy Gym workout normalisation

A pure, deterministic normaliser has been added for V21.1 Gym workout-day logs. It creates Gym-owned session, exercise and set records with stable IDs; preserves each source workout JSON string and raw exercise/set values; maps the legacy sessionTime field to durationMinutes; and retains cardio, warm-up, cool-down, body-weight and note context. A session is marked completed only when a matching date-scoped legacy set-status snapshot explicitly marks every recorded set complete. Missing or partial completion evidence remains incomplete, and unsupported workout log shapes produce warnings rather than being silently discarded. This normaliser is not yet wired into the migration write path. Readiness, profile, equipment, weigh-ins, preferences, swaps, extras and exercise configuration still require separate mapping and verification.


## Legacy shared-data normalisation

A separate pure normaliser now projects the V21.1 profile, selected/custom equipment, readiness check-ins and standalone weigh-ins into their corresponding IndexedDB stores. Remaining Gym-prefixed settings are retained as individually addressable preference records, including swaps, extras, exercise configurations, day unlocks, adapted-day flags, display preferences, rest-timer settings and programme preferences. Every projected record retains its source key and raw source string (or the original item JSON for array/object entries); malformed or unsupported data produces warnings and remains preserved in the raw legacy snapshot. This is a mapping foundation only: it has not yet been connected to migration writes or completion verification.


## Transactional legacy migration orchestration

The migration service now exposes migrateAndVerify() as the full V21.1-to-V21.2A path. It first preserves and verifies every original localStorage string in legacyRecords, then runs the pure Gym and shared-data normalisers, checks that source localStorage has not changed, and asks the database layer to commit all typed projections and the final migration marker in one IndexedDB read-write transaction. The database layer rejects ID collisions with records that do not match the same legacy source, while allowing an identical prior projection to be recognised as an idempotent retry. A failed normalisation leaves the raw safety snapshot preserved and the marker at snapshot-verified rather than complete. The migration does not delete or modify localStorage. This orchestration is covered by mocked-service tests; real-browser IndexedDB transaction behaviour still requires browser validation.


## Hiking manual record model

The initial Hiking Preparation record contract is documented in [V21.2A Hiking Record Model](V21.2A-HIKING-RECORD-MODEL.md). Completed manual hikes are owned by the Hiking module and stored only in `hikingRecords`; Gym sessions and sets remain separate. Date and title are required, while distance, duration, elevation gain and descriptive details are optional. Missing measurements are not inferred. Planned activities remain in the shared schedule model. GPS/route tracking and any assumed V21.1 Hiking migration are explicitly out of scope. The full versioned JSON backup already includes the `hikingRecords` store.


## V21.2A app integration boundary

The live V21.1 root `index.html` and root `sw.js` remain unchanged. The isolated V21.2 integration sequence and service-worker scope rules are documented in [V21.2A Integration Boundaries](V21.2A-INTEGRATION-BOUNDARIES.md). The proposed first UI lives under a V21.2 subdirectory with its own entrypoint and service worker scope, so the existing root app shell is not replaced. Migration is explicit and user-confirmed only, preceded by a downloadable JSON safety snapshot; localStorage is retained.
