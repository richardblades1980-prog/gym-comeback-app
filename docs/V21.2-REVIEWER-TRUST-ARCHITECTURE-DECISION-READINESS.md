## 1. Executive position

The recommended direction remains a **separate authenticated trust chain** layered over the existing content-integrity and catalogue-delivery foundations. The project should not reuse SHA-256 content digests as reviewer authentication.

The current source baseline confirms:
- `src/data/catalogue-delivery.js` validates catalogue delivery and exact target/digest bindings, but its review-binding metadata is not proof of reviewer identity, qualification, scope, signature or current authority.
- `src/modules/exercise-guide-crypto.js` supplies canonical SHA-256 digest functions; it is not a digital-signature or key-management service.
- `src/modules/exercise-guide-registry.js` validates guide, asset-set, assignment and review metadata against exact digests and targets; it does not authenticate the reviewer.
- `src/modules/exercise-guide-runtime.js` checks programme snapshot and local-asset relationships, not professional authority.
- `v21.2/sw.js` has application-shell/guide asset caching boundaries; any future trust-state persistence must be designed with cache lifecycle and backup/restore in mind.
- Existing tests cover digest/registry/runtime and browser/offline/backup behaviour, but not an end-to-end reviewer trust chain, real credential verification, revocation operations, or privacy controls in a live governance service.

The existing foundations should be preserved, not overclaimed. The architecture must remain fail-closed when identity, scope, signature, status, trusted time, evidence or freshness cannot be established. Historical workouts and user-owned data must remain readable and unchanged.

**No preferred vendor, cryptographic algorithm, registry host, key-custody product, legal basis, retention period, freshness interval or operational role is selected in this package.**

## 2. Decision classification and sequence

Not all open questions are technical. The following sequence prevents technical convenience from silently deciding professional or legal matters.

| Class | Decision area | Required decision owner / evidence | Can technical design settle it? |
|---|---|---|---|
| P — Professional | Qualifications, issuing authorities, scope boundaries and evidence standards for each review scope | Appropriately qualified Australian professionals; documented authoritative sources; owner acceptance | No |
| G — Governance | Registrar authority, independence, delegation, conflicts, appeals, funding and audit responsibilities | Owner plus qualified governance/legal input where needed | No |
| L — Legal/privacy | Responsible entity, lawful handling, notices, access, retention, disclosure, providers and cross-border processing | Australian privacy/legal assessment for the actual operating model | No |
| T — Technical | Trust bootstrap, signature format, key custody pattern, status distribution, time/rollback and hosting architecture | Security architecture analysis and independent security review | Yes, but only after P/G/L constraints are known |
| O — Owner | Risk acceptance, cost/operational trade-offs and bounded product behaviour | Explicit owner decision informed by the above | No |

**Dependency rule:** do not ask the owner to select a technical option whose safety depends on unresolved professional, governance or legal facts. Technical choices may be narrowed for evaluation, but cannot remove those blockers.

## 3. Trust-root bootstrap and recovery

A trust root is the pre-established authority from which the app verifies governance and release signatures. A key delivered only inside the data it is supposed to authenticate is not a trust root.

| Option | How it would work | Advantages | Main risks / failure cases | Evidence required before selection |
|---|---|---|---|---|
| A. Root key pinned in an application release | A public root key or root-set identifier is shipped with a trusted app release; later signed metadata chains to it | Simple verification model; bootstrap is explicit; works offline after install | Root rotation may depend on app update; compromised app release can substitute root; old installed clients may lag; emergency recovery is difficult | App update trust assumptions, supported client lifecycle, root rotation and compromise runbooks, offline first-install tests |
| B. Separately signed trust bundle | App contains a small initial trust anchor and downloads or imports a separately signed, versioned trust bundle | Governance metadata can update independently of app code; bundle can be mirrored and cached | Bootstrap still depends on initial anchor; bundle delivery outage/staleness; rollback/replay; bundle parser becomes security-critical | Bundle format, signing authority, freshness, sequence/rollback design, distribution resilience and parser threat review |
| C. Staged root rotation with cross-signing | Current root authorises a successor during an overlap; clients verify the transition and retain a monotonic root epoch | Planned rotation can support old and new clients; explicit succession record | Old-root compromise may undermine transition; lost root or interrupted overlap; device reset/high-water loss; emergency rotation remains difficult | Formal root succession policy, multi-person control, compromise scenarios, device persistence guarantees and recovery drills |
| D. Hybrid | Pinned bootstrap root plus signed trust bundle, with staged root succession and a separately governed emergency recovery procedure | Separates initial trust, routine metadata updates and planned root rotation | More moving parts; operational discipline and test burden; hybrid can conceal unclear authority if responsibilities are not explicit | End-to-end threat model, independent design review, runbooks and test evidence for all transitions |

**Decision guidance:** a hybrid is a candidate worth evaluating because routine reviewer-status changes should not necessarily require an application release, while bootstrap and root rotation must remain anchored in a trust source the payload cannot replace. This is not a selection. The root authority, recovery authority and actual app-update trust model must be settled before approval.

Questions that must be answered:
1. Who legally/operationally controls the root authority, and who can act if that person or service is unavailable?
2. What independent approval is required to add, rotate, revoke or recover a root?
3. How does a fresh install establish trust, and what does an offline first install show?
4. How does a reset device recover without accepting arbitrary cached metadata?
5. What happens to clients that miss one or more root rotations?

## 4. Key custody and role separation

Private signing keys must not be placed in the repository, app bundle, browser storage, ordinary user backup or a general-purpose shared account. Distinct authorities require distinct keys or cryptographically separated identities.

| Option | Advantages | Main risks / operational costs | Appropriate evaluation questions |
|---|---|---|---|
| A. Managed HSM/KMS service | Protected key operations; access controls and audit features may be available; reduces direct private-key handling | Provider concentration, recurring cost, account compromise, service outage, jurisdiction/region and exit dependence | Does it support required algorithms, multi-person approval, export/exit, audit retention, incident response and acceptable data location? |
| B. Organisation-managed hardware security | Direct custody and control; can reduce dependence on a single cloud provider | Hardware procurement, physical security, backup/recovery, availability and specialist operational burden | Who holds devices, how is dual control enforced, how are disaster recovery and succession tested, and can operations be sustained? |
| C. Software-held keys in controlled server environment | Potentially lower initial cost and simpler integration | Greater exposure to host compromise, backups, secrets leakage, privileged access and operational error | Can the threat model justify this for each authority? What isolation, access, monitoring and recovery controls are demonstrable? |
| D. Hybrid / multi-party control | High-impact root operations can require multiple independent custodians while routine signing uses a managed operational boundary | More complex ceremonies, coordination, failure recovery and role administration | Which actions require multiple parties? How are quorum, absence, conflict, compromise and succession handled? |

**Candidate evaluation direction:** evaluate managed hardware-backed custody for routine operational signing alongside a separately controlled multi-person root process. Do not treat this as a provider recommendation or procurement decision. The appropriate pattern may differ between reviewer keys, registrar/governance keys, catalogue release keys and root keys.

Before any key exists, require:
- named accountable roles and a documented separation-of-duties matrix;
- approved generation ceremony and proof-of-control procedure;
- least-privilege access and auditable signing authorisation;
- backup/recovery that does not create uncontrolled private-key copies;
- rotation, expiry, suspension, compromise, revocation and destruction procedures;
- provider/service exit and continuity plans;
- independent security review and recovery exercises.

Reviewer private keys may need a different custody model from institutional registrar/release keys. A reviewer signing key must not be shared with the registrar or release authority. The final design must account for a reviewer losing a device, leaving a role or having a key compromised without rewriting historical user data.

## 5. Signature format, algorithms and canonical payloads

The existing SHA-256 module is an integrity helper. A future signature-verification capability must be a separate, explicitly versioned trust boundary.

| Candidate family | Potential benefits | Constraints to investigate | Not yet decided |
|---|---|---|---|
| Browser-native Web Crypto signatures | Native browser API; avoids shipping a large cryptographic implementation; asynchronous operation is compatible with the existing async digest direction | Algorithm/key-format support differs by browser and platform; key import/export formats; signature encoding; older device support; testability | Algorithm, curve/key size, encoding and minimum supported clients |
| Standardised signed-data envelope (for example, a compact JWS-style envelope) | Widely understood envelope concepts; explicit protected headers and payload/signature separation; ecosystem tooling | Header/payload canonicalisation, algorithm allowlists, critical-header handling, key discovery, parser complexity and algorithm-confusion risks | Exact envelope profile, allowed algorithms, canonicalisation and key identifiers |
| Deterministic binary signed envelope (for example, a COSE-style profile) | Compact structured encoding; explicit algorithm and key parameters; can suit constrained/offline metadata | Browser library availability, deterministic encoding requirements, parser/library assurance and interoperability | Exact profile, encoding rules, browser implementation and migration plan |
| Custom application-specific signature format | Can be tightly scoped to project contracts | Highest risk of subtle design flaws, ambiguous encodings, non-interoperability and long-term maintenance | Should not be preferred without compelling evidence and independent cryptographic review |

**Evaluation requirements for any candidate:**
- use a maintained, reviewed implementation or platform primitive; do not invent cryptographic primitives;
- explicit allowlist of algorithms and key types; reject unsupported or downgraded algorithms;
- deterministic, unambiguous payload encoding and domain separation;
- signatures cover exact semantic fields: target type/ID/version/digest, scope, decision, evidence references, policy version, time and lifecycle context as applicable;
- reject duplicate/unknown critical fields, malformed encodings, invalid key identifiers and ambiguous canonical forms;
- test browser compatibility across the actual supported device matrix, including offline verification;
- plan format versioning and migration without silently reinterpreting historical signatures.

A signature only proves that a key signed a payload. The separate trust chain must establish why that key was authorised for the claimed role and scope at the relevant time.

## 6. Governance registry and revocation distribution

The registry is the authoritative source for reviewer authorisations, scope, lifecycle and revocation. Publicly distributable signed status metadata must not expose restricted identity or case records.

| Option | Advantages | Main risks / offline behaviour | Evidence required |
|---|---|---|---|
| A. Signed static snapshots | Simple immutable distribution; easy to mirror/cache; natural sequence and timestamp boundary; offline verification | Revocation is only as fresh as the last snapshot; snapshot size and update cadence; stale clients must not claim current | Snapshot signing, sequence/high-water retention, freshness policy, distribution and rollback tests |
| B. Online status API | Potentially fresher status; central operational updates; can return current decision state | Network dependency; API outage; privacy/availability exposure; API response itself must be authenticated; no current claim offline | Service availability objectives, authenticated responses, rate limits, audit, privacy assessment and outage behaviour |
| C. Event feed plus periodic snapshots | Efficient change distribution with a recoverable snapshot baseline; supports append-only lifecycle history | Event gaps, ordering, replay, compaction, recovery and client complexity | Event sequence model, gap detection, snapshot reconciliation and replay/rollback tests |
| D. Hybrid API plus signed snapshots | Online clients can refresh frequently; offline clients retain a verifiable last-known state | Most complex; API and snapshot may disagree; unclear precedence can create split-brain status | Explicit precedence, reconciliation, signed responses, freshness policy, outage and disagreement tests |

**Candidate evaluation direction:** compare a signed snapshot baseline with an optional online refresh path. This could preserve offline verification while allowing faster status updates, but it does not solve the revocation gap while offline. The system must call cached evidence “historically verified” or “stale/unknown” when the approved freshness condition cannot be met.

The registry must distinguish at least: active, restricted, suspended, expired, withdrawn/revoked and superseded. These must not be collapsed into a generic inactive flag. Status must be scoped to the reviewer, credential, jurisdiction, review scope and effective time.

Open governance dependencies:
- who is authorised to create each status event;
- whether precautionary restriction is distinct from a final finding;
- who investigates, hears an appeal and restores authority;
- what public projection may be disclosed;
- which scope-specific freshness and revocation objectives are professionally justified.

## 7. Trusted time and anti-rollback

A user-controlled device clock cannot by itself prove that a cached approval is current. Monotonic sequence numbers can help detect rollback, but only if a trusted high-water mark is retained in a way the device threat model supports.

| Option | Advantages | Limitations / risks |
|---|---|---|
| A. Device wall clock only | Simple and available offline | User can change it; clock drift/reset; not sufficient for current-authority claims |
| B. Signed timestamped snapshots | Authority signs issue time and validity metadata; supports offline historical verification | Signature does not make the device clock trustworthy; expiry evaluation still needs a trustworthy time basis |
| C. Online trusted-time/status check | Can establish a recent server-side observation when online | Unavailable offline; service compromise/outage; response needs authentication and audit |
| D. Monotonic sequence plus protected local high-water mark | Detects older snapshots after a higher sequence has been securely retained | Browser storage may be cleared, restored or manipulated; platform guarantees vary; new device has no high-water mark |
| E. Hybrid signed snapshots, online refresh and best-effort retained sequence | Can distinguish online current checks from offline historical checks and detect many rollback attempts | Cannot eliminate first-use, reset, storage-clearing or long-offline uncertainty; needs precise state semantics |

**Candidate evaluation direction:** use signed status snapshots with sequence numbers, trusted issue-time evidence and online refresh where available; retain a high-water mark only where the supported platform provides a defensible persistence model. Do not claim hardware-backed anti-rollback if the browser cannot provide it. When trusted time or sequence continuity is unavailable, current status is unknown rather than assumed.

No freshness interval, offline grace period or scope-specific risk window is selected. Those are G-10 governance decisions requiring risk justification and explicit owner approval after professional input.

## 8. Hosting, privacy and data separation

Hosting architecture cannot be chosen independently of G-09's responsible-entity, lawful handling, retention and cross-border assessment.

| Option | Advantages | Risks / conditions |
|---|---|---|
| A. Static public signed metadata with separately hosted restricted governance records | Clear public/restricted separation; static metadata can be mirrored and cached; limited client exposure | Restricted record operations still need secure hosting, access control, audit, retention and continuity; public snapshots may be copied |
| B. Single managed platform with logical separation | Fewer vendors and potentially simpler operations | Logical separation must be proven; broad admin access, backups, logs or analytics can leak restricted data; provider location/exit risk |
| C. Split providers for public distribution and restricted records | Stronger separation of duties and exposure domains; public distribution can be highly available | More integration, contracts, incident coordination, identity/access management and service exit complexity |
| D. Self-hosted restricted registry plus static public outputs | Direct control over data location and operations | Highest internal operational burden; security patching, backup, access review, audit, availability and succession must be funded |

**Non-negotiable boundaries regardless of option:**
- identity documents, credential evidence, conflict declarations, complaints, appeals and private case material stay in restricted governance systems;
- never store restricted governance records in Git, app assets, public catalogue payloads, public issue trackers, normal user backups or ordinary client-side storage;
- public traceability is a deliberate allowlisted projection, not a redacted dump of the source record;
- user workouts, injury/user-entered health context and profile data remain separate from reviewer trust records and must not be sent to reviewer telemetry or public trust metadata;
- governance-service failure or approval withdrawal must not corrupt, erase or block access to historical workouts.

No provider, country/region, retention period or lawful basis is approved.

## 9. Release signing and verification boundary

The logical chain should keep these responsibilities separate:

1. Credential verifier records a restricted verification outcome.
2. Registrar issues a finite signed reviewer authorisation bound to key, scope and jurisdiction.
3. Reviewer signs an exact-target review attestation.
4. Independent reviewers sign separately where required.
5. Governance authority publishes signed status/revocation metadata.
6. Catalogue release authority verifies all required attestations and signs the immutable release manifest.
7. App verifies the release signature, underlying attestations, authorisation chain, exact target binding and freshness state.

The catalogue release signer must not be able to waive missing reviewer approval. A valid release signature cannot make an unsupported professional claim valid. A valid reviewer signature cannot make an expired or out-of-scope authorisation current.

Potential integration boundary:
- retain existing content digest functions for integrity;
- introduce a separate signature-verification/trust-chain layer only after format and policy approval;
- make catalogue staging/activation depend on the complete required trust result, not review metadata alone;
- preserve the prior active catalogue if any verification step fails;
- do not make a trust outage rewrite programme snapshots, workout records or historical display values.

No source files or interfaces are approved for modification by this package.

## 10. Cache, service-worker, backup and restore implications

This is a high-risk integration boundary because trust state must not be accidentally reset by ordinary cache cleanup or restored from an untrusted user backup.

| Area | Design requirement | Failure that must be tested |
|---|---|---|
| App shell cache | Keep shell lifecycle separate from trust metadata lifecycle | App update deletes trust state or accidentally restores an older trust bundle |
| Trust metadata cache | Store immutable, versioned signed snapshots with explicit sequence and source | Corrupt cache entry or replayed lower sequence appears current |
| IndexedDB/local persistence | Persist only the minimum trust state justified by the approved design | Storage clear/reset silently loses anti-rollback evidence but UI still claims current |
| User backup | Never treat ordinary personal backup as authority to restore governance keys, root state or current reviewer status | Backup transplant overwrites a newer trusted sequence or installs forged authority |
| Restore to new device | Restore personal data/history; re-establish governance trust through trusted bootstrap | Missing trust state blocks history or restored stale trust appears current |
| Cache cleanup/quota | Cache eviction must degrade trust to unavailable/stale, never to implicitly trusted | Browser eviction produces an unsafe fallback |
| Catalogue activation | Verify staged release and trust chain before activation; retain prior valid release on failure | Partial trust verification activates a candidate release |

The current catalogue delivery design separates immutable release delivery from user history and uses transactional activation concepts. Any future trust implementation must preserve that separation and be reviewed against the actual current backup and service-worker code before implementation is proposed.

## 11. Cross-cutting failure cases and required outcomes

| Scenario | Required outcome |
|---|---|
| Valid SHA-256 digest, no trusted reviewer signature | Not approved; integrity is not authentication |
| Valid signature, untrusted key | Reject |
| Trusted key, reviewer scope mismatch | Reject for that claim/scope |
| Reviewer was authorised at signing time but later suspended/revoked | Preserve historical decision record; current reliance follows authoritative lifecycle and approved policy |
| Status snapshot stale or missing | Historical/stale/unknown; never current |
| Offline device cannot establish trusted time | Unknown for current-authority claim |
| Lower snapshot sequence replayed | Reject or mark trust unavailable; never roll back trusted state |
| Root compromised or lost | Follow separately approved emergency recovery; no self-signed replacement |
| API/provider unavailable | Preserve app and user data; no downgrade or bypass |
| Public projection contains restricted fields | Block publication; privacy incident process if already disclosed |
| Catalogue release signature valid but underlying review incomplete | Reject release |
| Reviewer trust withdrawn after user has completed workouts | Keep historical workouts and snapshots accessible and unchanged |
| Device backup contains old trust metadata | Do not restore it as current governance authority |

## 14. Explicit non-authorisations and stop conditions

This package does not authorise:
- application code, schema, API, database, backup, migration, service-worker, cache or UI changes;
- selecting or connecting any identity, credential, registry, hosting, HSM/KMS or other provider;
- generating, importing, storing, using or rotating real private keys or trust roots;
- collecting identity, qualification, conflict, complaint, appeal or other personal information;
- appointing, authorising or recruiting reviewers;
- approving production exercise, equipment, guide, programme, movement-demand or injury-related content;
- publishing a public reviewer register or operating a complaints/appeals service;
- changing `main`, Pages release candidate/settings, production cutover or deployment.

Stop and return for a decision if:
- a technical option requires an unresolved professional or legal assumption;
- a vendor's terms or data location are unknown;
- no accountable operator or recovery authority exists;
- offline behaviour would imply current approval without adequate status/time evidence;
- a change could affect historical workout integrity or user-owned data;
- a test or validation result is incomplete, mismatched to the exact commit or not independently evidenced.
