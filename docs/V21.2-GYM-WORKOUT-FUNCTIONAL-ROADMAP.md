# V21.2 Gym workout — functional-first implementation roadmap

**Priority decision (2026-11-18):** get the app's core Gym workflow working before spending more time on artwork style or decorative UI. The existing artwork is sufficient as temporary functional artwork. The user's preferred visual ideas can be revisited after the workout flow works end to end.

**Branch baseline:** `V21.2-development` following the source-preserved programme data commit.
**Protected source:** `main` root `index.html`, blob `e3eb0093648cc6c5d706bb5b1008b58ec01a5576`. Read-only.

## 1. Source-grounded current position

V21.2 already has:
- A local-first app shell with Overview, Gym history, Hiking, Assessments, Schedule and Data & backup views.
- IndexedDB stores for `sessions`, `exerciseRecords`, `setRecords`, `progression`, profile, equipment and programme data.
- Module ownership boundaries that keep Gym writes separate from Hiking.
- V1/V2 backup compatibility and a V6 canonical exercise-identity foundation.
- An immutable verified exercise catalogue delivery mechanism and separate verified artwork cache.
- A source-preserved Gym migration that retains original exercise names and raw workout values.

The current V21.2 Gym view is history-only. There is no screen to start or run a Gym workout, no set-entry workflow, no live set-state interface, and no workout-save/celebration flow. The shared programme manager only handles calendar scheduling; it is not a workout runner.

The protected legacy app remains the behavioural reference for the working workout experience.

## 2. New source-preserved programme data foundation

The data module contains the exact five-day source programme:

- Day 2: 7 slots

Each slot retains its original source label, description, group key, muscle keys, source slot ID and source provenance. The legacy default of three sets is retained. Plank uses the source default timed-hold recording mode; the other base slots default to repetitions.

The source module is loaded by `v21.2/index.html`, mirrored through the bundle parity test and included in service-worker shell cache v17. It is available offline. It is not yet connected to a workout UI.

## 3. Functional-first build sequence

### G3.2 — Start, resume and persist a workout

Build a simple, usable Gym workout flow in the existing Gym module. Reuse the V21.2 app shell and current temporary assets; do not redesign the visual system.

Minimum behaviour:
1. Select one of the five base programme days and start a dated session.
2. Create a session record plus its performed exercise and set records in the existing IndexedDB stores.
3. Preserve the programme slot ID and exact source exercise label on each performed exercise.
4. Allow the user to enter/edit reps, weight and actual timed-set duration.
5. Auto-save changes so reloading the app does not lose a live workout.
6. Resume an in-progress session instead of silently creating a duplicate when returning to it.
7. Save a session as completed only when all required sets are complete; preserve explicitly saved incomplete sessions without falsely marking them complete.

The session start must write its session, exercise and initial set graph atomically across the existing stores. Do not add a DB version or store solely for this step. Add a dedicated transaction helper if required and keep it within the existing DB/backup boundary.

### G3.3 — Restore the core set interactions

Preserve the established set behaviour:
- Set states: not started, in progress and completed.
- Later sets stay locked until the previous set is complete.
- Undoing a completed set resets later completion states in that exercise; entered weight/reps/time values remain available for correction.
- Completing all sets marks the exercise complete.
- Per-exercise set count, progression focus and recording mode are configurable.
- Timed sets support Start, Stop, Reset and manual elapsed-time correction. Timed-reps mode also records repetitions completed during the interval.

### G3.4 — Smart rest and save flow

Preserve the existing rest-timer behaviour:
- Default rest: 90 seconds; selectable values 45, 60, 75, 90, 120, 150 and 180 seconds.
- Per-exercise rest setting.
- `+15 seconds`, `Skip rest` and `Cancel rest` controls.
- Persist an absolute timer end time so the countdown catches up after reload or switching apps.
- Keep the alert preference (sound, vibration, visual or combined) and graceful permission fallbacks.

Saving must persist first, then show the existing six-second celebration. The user can skip or dismiss it early. Use the current verified GIFs; do not create a new artwork batch for this feature.

### G3.5 — Day/week flow and history

- Restore the five-day selection and existing sequential day/week progression rules.
- Keep manual unlock/relock behaviour where supported by the legacy workflow.
- Show saved and in-progress workout history using the existing Gym history view.
- Preserve the legacy migration snapshot and raw values.
- Verify that a completed V21.2 workout appears in history, workload summaries and the Gym progress journey.

### G3.6 — Equipment, swaps and progression

Only after the unadapted five-day workout works end to end:
- Port the equipment availability and manual safer-swap flow.
- Keep equipment matching separate from exercise aliases.
- Keep slot substitutions explicit and preserve the original programme slot/source label.
- Add progression summaries from saved sets without silently changing the user's weights or repetitions.
- Review adaptive/recovery rules before enabling any automatic recommendations. Do not add unapproved clinical thresholds.

### G3.7 — Exercise guide

Add the accessible 450 ms hold and keyboard guide interaction after the exercise-card workflow is in place. Until guide copy is reviewed, show an honest `Guide being prepared` or unavailable state. Never present the 27 draft guides or generic fallback wording as reviewed exercise-specific instructions.

## 4. Functional acceptance gates

The first working Gym session is not accepted until automated browser coverage confirms:
- A user can open Gym, choose each of the five days and start a session.
- The initial session creates the correct exercise and set graph (7/7/6/6/6 exercises, three default sets each).
- No canonical identity is fabricated for unresolved source labels.
- Entered reps, weight and duration survive navigation and a cold browser restart.
- Set sequence locks, completion, undo and exercise-completion indicators behave correctly.
- Timed-set controls and manual corrections work.
- Rest timer start, +15, skip, cancel and reload catch-up work.
- Save persists before the six-second celebration; skip/dismiss does not alter the saved session.
- A failed write cannot leave a partially created session graph.
- Backup/restore round-trips the new workout records.
- Offline cold start can load the workout runtime and programme data.
- Hiking, Assessments, Schedule, catalogue delivery, artwork cache, historical data and protected legacy source remain unchanged.

## 5. Explicitly deferred until the app works

Do not spend the next development cycles on:
- New hero character styles or poses.
- Reillustrating the full equipment or muscle collection.
- Redesigning celebration visuals.
- Fine visual polish, animation polish or decorative layouts.

The existing artwork remains temporary but acceptable. Only replace an asset when it is broken, misleading or blocks a required interaction. Visual ideas supplied later can become a separate refresh project after the core Gym workflow is usable.

## 6. Data and repository safety boundaries

- No canonical exercise ID, variation or alias may be assigned from a similar display name alone.
- No draft guide wording may be published as complete.
- No schema/store addition without a separate source-grounded migration and backup review.
- Any runtime service mirrored into `v21.2/assets/` must pass source/bundle parity checks.
- Keep `main`, protected root `index.html`, and deployment untouched.
- Each functional increment must pass exact-SHA browser and backup workflows before being treated as validated.


## 7. G3.2 first implementation increment — 2026-11-18

Implemented on the development branch; exact-SHA browser validation is pending on the current head.

- Added `src/modules/gym-workout.js` and the identical offline browser bundle `v21.2/assets/gym-workout.js`.
- Added `ProjectComebackGymWorkout` service operations to start/resume a session, load its saved exercise/set graph, update entered set values, start/complete/undo a set, and finish a session.
- Reuses the existing `sessions`, `exerciseRecords` and `setRecords` stores and the atomic `createGymWorkoutBundle` / `updateGymWorkoutBundle` IndexedDB transactions. No database version, object store or index change.
- Start creates 7/7/6/6/6 exercise slots with three sets per exercise by default. The exact source label, source slot ID and `identityLinkStatus: unreviewed` are preserved; no canonical identity is fabricated.
- The first set starts available; later sets remain locked until the preceding set is completed. Undo returns the selected set to in-progress and relocks all later sets while retaining entered values.
- Repeated start for the same day/date resumes an existing in-progress session. Inputs persist as text values in the existing set records.
- A session can be marked completed only when every set is completed. The session's completion timestamp and elapsed minutes are stored before it appears as completed history.
- Added a minimal Gym screen to select a day/date, start or resume a workout, enter weight/reps or timed-hold seconds, complete/undo sets, and finish the session. This deliberately uses the existing app style and temporary assets; no artwork refresh is part of this increment.
- Shell cache advanced to v18 and includes the workout service for offline loading. The verified artwork cache v1 and catalogue release cache are unchanged.
- Added `tests/gym-workout.test.js` for all five day graphs, duplicate resume, set locking/unlocking, persistence, undo, disabled-module write rejection and finish gating. Added the test to browser and backup workflows.
- Added Chromium browser coverage for a real day-1 session, entering weight/reps, set completion, reload and resume. It also checks that the next set unlocks and the following set remains locked.
- Deferred: rest timer, timed-set stopwatch/manual correction, configurable set count/progression mode in the UI, six-second celebration, week progression, swaps/equipment adaptations and the accessible exercise guide. These remain on the roadmap; this increment is not the full Gym workflow acceptance gate.
