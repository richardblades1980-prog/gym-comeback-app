# V21.2 catalogue delivery and offline lookup — source-grounded design audit

**Audit date:** 17 November 2026  
**Inspected branch:** `V21.2-development`  
**Inspected base commit:** `117cb5d98a0e5c16b6fb000d4ba80a4c28e4435e`  
**Classification:** Design-only G2 proposal; no catalogue delivery or lookup implementation is authorised by this audit.

## 1. Executive finding

The canonical identity persistence foundation is present, but a production exercise catalogue is not yet delivered. The current code stores immutable catalogue release metadata and checks that a checksum string exists. It does not fetch, hash, parse, stage, cache, materialise or activate a catalogue asset. The real service worker caches the V21.2 application shell and identity service, not a catalogue release. The browser test proves the identity script cold-starts offline; it does not prove catalogue lookup works offline.

The safest direction remains the hybrid model: a versioned immutable bundled system catalogue release is the authority; IndexedDB is the local materialisation used for offline lookup; profile-owned custom definitions, aliases, review events and configurations remain separate. CacheStorage holds verified immutable release bytes as a recoverable artifact, not the editable catalogue authority.

- `src/data/database.js` — schema v6 stores and indexes, including `catalogueReleases`, definitions, variations and metadata.

- `v21.2/index.html` — script order and application shell.
- `v21.2/sw.js` — shell cache, activation cleanup and runtime GET caching.
- `tests/exercise-identity-contract.test.js`, `tests/identity-persistence.test.js`, `tests/browser-validation.js` — design fixtures, real IndexedDB/backup tests and actual browser/offline coverage.
- Both V21.2 browser and backup workflows.

### Current source facts

1. `storeCatalogueRelease()` requires a release ID, positive integer version and non-empty checksum string. It enforces immutable release IDs and monotonically increasing versions in the service API. It does not validate a checksum algorithm, hash asset bytes, fetch an asset, validate a payload schema or materialise catalogue definitions.
2. `catalogueReleases` stores manifests in IndexedDB. There is no catalogue asset store, release loader, active-release selector or asset-to-definition import transaction.
3. `v21.2/index.html` loads `assets/exercise-identity.js`; it does not load a catalogue manifest or asset.
4. `v21.2/sw.js` uses a versioned shell cache (currently v15). Its precache list contains the app shell and JavaScript services but no catalogue asset. Its generic same-origin GET fallback stores responses in the shell cache. On activation it deletes older caches with the shell prefix. A future catalogue asset put into this generic cache would be coupled to shell-version cleanup.
5. Browser validation checks that the identity service is cached and the actual V21.2 app cold-starts offline. The separate offline fixture proves a minimal fixture shell works offline. Neither test exercises a catalogue release, verified materialisation or offline exercise search.
6. Backup V2 contains the `catalogueReleases` metadata store and records carrying catalogue release IDs and self-contained display snapshots. It does not embed system catalogue asset bytes. Validation checks that the manifest exists and its checksum is a non-empty string; it cannot prove the asset is installed or that its bytes match. Restore merges metadata/history without fetching an old system asset.
7. `getCatalogueReleaseReferences()` counts published programme versions, sessions not marked cancelled/deleted, and identity-review events. It does not scan `programmeSlots`, although V2 backup validation accepts and validates a slot-level `catalogueReleaseId`. Align this reference contract before retention is implemented.

## 3. Risk and gap register

| Area | Observed gap | Consequence |
|---|---|---|
| Integrity | Checksum is only a required string; no digest of exact bytes | Corrupt or mismatched JSON could be accepted |
| Manifest | No required asset URL, byte length, content type, schema version or entry count | Release bytes are not fully identified |
| Delivery | No loader or bundled catalogue asset exists | Manifest persistence can be mistaken for a working catalogue |
| Cache lifecycle | Runtime assets share shell cache; activation deletes prior shell caches | Catalogue retention becomes coupled to UI updates |
| Activation | No staged/verified release state or active-release pointer | Interrupted update could expose partial data |
| Offline lookup | No verified IndexedDB materialisation contract | App cold-start does not prove exercise lookup is available |
| Restore | Backup has metadata/snapshots but not system asset bytes | Restored history may reference an absent asset |
| Retention | Reference scan omits slot references while backup validates them | A future pruning process could remove a referenced release |
| Fallback | No distinction between rendering history and editing against a pinned release | Current definitions could silently replace historical context |

## 4. Recommended bounded architecture

### A. Immutable release artifact and manifest

Package each system catalogue as a versioned JSON artifact under an immutable path such as `catalogues/exercise/<releaseId>/<sha256>.json`. A source-controlled manifest should include `catalogueId`, immutable `releaseId`, monotonically increasing `version`, `schemaVersion`, `assetUrl`, `contentType`, exact `byteLength`, `checksumAlgorithm: "SHA-256"`, `checksum: "sha256:<64 lowercase hex chars>"`, `entryCount`, build timestamp and minimum compatible reader version.

The digest covers exact UTF-8 asset bytes before JSON parsing or reserialization. Verify byte length and digest first; then validate schema, catalogue/release/version agreement, unique opaque IDs, required fields, foreign-key references and supported vocabularies. A checksum detects corruption/mismatch; it is not a digital signature or publisher authentication. Keep the manifest and artifact in the trusted app release. A future remote/CDN publisher needs a separate signing/authenticity design.

Never replace bytes or metadata behind an existing release ID/version. A changed catalogue is a new release ID and higher version. Content-addressed paths reduce mutable URL reuse.

### B. Separate release cache from app shell cache

Use a dedicated CacheStorage namespace such as `project-comeback-v21-2a-catalogue-<catalogueId>-<releaseId>-<digest>`. Do not put catalogue payloads in the shell cache. Shell activation cleanup must delete obsolete shell caches only and must never delete catalogue release caches.

Cache exact verified bytes. IndexedDB materialisation remains the queryable local cache and carries the source release ID/checksum. CacheStorage is the immutable artifact/recovery copy, not the editable catalogue authority. Ordinary runtime GET caching must not silently publish a catalogue.

### C. Stage, verify, then activate

1. Read the currently active verified release and leave it usable.
2. Fetch the exact immutable asset URL (or use a bundled asset); require success, expected content type and byte length.
3. Compute SHA-256 over received bytes and compare with the manifest before parsing.
4. Validate payload schema, IDs, references, counts and catalogue identity.
5. Write verified bytes to the release-specific staging cache; re-read and verify cached bytes.
6. In one IndexedDB read-write transaction, store the immutable manifest, materialise system definitions/variations with source release IDs, retire removed system definitions without deleting IDs, and update the active-release metadata pointer last. Do not touch custom definitions, aliases, audit events, configurations, performed records or historical snapshots.
7. Only after transaction completion is the new release active. On failure, the prior active release remains selected. An orphaned staging cache is unreferenced and harmless; no automatic historical release GC is included.

CacheStorage and IndexedDB do not share a transaction. Stage and verify bytes first, then commit materialisation and active pointer atomically in IndexedDB. On restart, reconcile staging cache with the IndexedDB active pointer; never infer activation from a cache file alone.

### D. Offline lookup and pinned history

- First install with no verified materialisation: show catalogue unavailable while offline; do not present an empty catalogue as valid.
- After successful seed: offline lookup reads the matching IndexedDB materialisation and confirms its active release ID/checksum. CacheStorage permits artifact re-verification/recovery.
- Programme versions/sessions pin exact releases. Never silently substitute current release for a missing pinned release.
- Historical display uses its self-contained `canonicalDisplaySnapshot` and exact raw performed name/value; it does not need the old asset.
- If a pinned release is unavailable, history remains readable; editing/replaying against that release is unavailable until exact recovery. A current release can be offered only as a separately labelled new context.

### E. Retention and backup/restore

Retention is the union of explicit references from published programme versions, versioned programme slots, non-cancelled/non-deleted sessions that pin a release, and identity-review events. Include direct slot references in the scan or remove slot-level release references from the contract; do not leave the paths inconsistent. No automatic GC.

V2 personal backup carries release IDs/checksums, user-owned definitions/aliases/review/configuration records, programme/session lineage and display snapshots. It does not need system catalogue bytes. Restore on a new device must restore personal records/snapshots without requiring old system asset bytes, preserve missing release references as unavailable metadata, render history from snapshots, report unavailable pinned releases for future editing, and seed the app's bundled current release separately without rewriting historical pins/snapshots.

The current V2 validator requires manifests for several references. Preserve those manifest IDs/checksums in backup even when corresponding asset bytes are absent. Do not drop IDs or snapshots to make restore pass.

## 5. Failure and recovery matrix

| Failure | Required behaviour | Recovery |
|---|---|---|
| Missing asset/offline first run | Keep catalogue unavailable; preserve app shell and user data | Retry online or use an already verified materialisation |
| Wrong digest/truncated bytes | Reject before parse/materialisation; preserve active pointer | Retry exact immutable URL; keep prior release active |
| Valid digest, invalid schema/IDs/references | Reject without mutating current catalogue | Correct source as a new release ID/version |
| Interrupted fetch/cache write | Never activate partial release | Resume/re-fetch exact immutable asset; clean only unreferenced staging data |
| IndexedDB transaction abort | Prior active release and definitions remain unchanged | Retry idempotently after checking active pointer |
| App/shell update | Retain independent catalogue release caches | Shell cleanup stays prefix-scoped |
| Stale manifest/asset URL | Require exact release ID/version/digest; no mutable latest URL as a pin | Fetch exact versioned asset or remain unavailable |
| Old release absent after restore | Keep history readable from snapshots; pinned editing unavailable | Fetch exact archived release if available; never substitute current |
| Restore without old asset | Restore data and snapshots without asset download | Seed current release separately; expose unavailable historical pin |
| CacheStorage entry missing/corrupt after seed | Use matching verified IndexedDB materialisation if intact; otherwise mark unavailable | Re-fetch exact asset before rematerialising |

## 6. Regression evidence added

`tests/catalogue-delivery-contract.test.js` adds source-characterization and design-level cases for:
- current metadata-only release registration, shell-only precache and identity-service offline test boundary;
- exact-byte SHA-256/byte-length, schema, release identity, count and unique-ID validation;
- immutable IDs/monotonic versions;
- interrupted staging, corrupt bytes and IndexedDB abort preserving prior active release;
- offline lookup only after verified matching materialisation;
- snapshot-based history/restore without old asset and no silent pin substitution;
- retention across published versions, slots, sessions and review events;
- separate release cache namespace surviving shell activation cleanup.

These tests are not a production loader, CacheStorage integration or catalogue lookup implementation. Later implementation must add real Playwright, service-worker/CacheStorage and IndexedDB transaction tests.

## 7. Implementation boundary

This audit makes no application, schema, backup-format or catalogue-asset change. It does not authorize release GC, remote delivery, cloud sync, fuzzy legacy mapping or V21.1/`main` changes. The companion `docs/V21.2-G2-CATALOGUE-DELIVERY-GATE.md` records the bounded implementation proposal as **HOLD pending explicit user decision**.
