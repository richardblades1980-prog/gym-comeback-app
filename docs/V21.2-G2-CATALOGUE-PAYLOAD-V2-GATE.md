## 1. Trigger and goal

The next exercise library needs reviewed system equipment definitions, precise exercise-to-equipment requirements and reviewed movement-demand metadata. The existing v1 catalogue payload contains exercise definitions and variations, but no equipment-definition collection or injury-relevance profile. Its optional \`requiredEquipmentDefinitionIds\` field is a simple string array and does not specify AND/OR semantics.

These gaps matter to exercise selection, equipment filtering and the later injury-aware alternative engine. A vague requirement matcher or incomplete movement profile could present an unavailable setup, or worse, imply that an unreviewed movement does not load a restricted body area.

**Goal:** define a v2 immutable catalogue payload and a verified offline equipment lookup path that:
- adds reviewed equipment definitions and structured exercise/variation requirements;
- preserves the existing v1 reader path and installed v1 releases;
- keeps system equipment definitions in the exact verified catalogue release bytes, not the personal equipment store;
- carries explicit, review-bound movement-demand metadata so future injury-aware matching can fail closed;
- makes no IndexedDB schema/store/index or personal-backup-format change;
- leaves production catalogue data unpublished until curation and qualified review have actually occurred.

This is G2 because it changes the durable catalogue contract and offline interpretation. The approved v1 loader is not blanket approval for v2.

## 3. Bounded proposal after PASS

### 3.1 Payload schema v2

The immutable payload continues to identify \`catalogueId\`, \`releaseId\`, release \`version\` and \`schemaVersion\`. The v2 reader must validate a version-2 payload while retaining the current v1 validation path without coercing v1 records into v2 semantics.

V2 adds:
- \`equipmentDefinitions\`: reviewed system equipment families with opaque IDs, canonical names, families, supported configuration dimensions, provenance and review bindings;
- \`controlledVocabularies\`: versioned IDs and definitions for the body regions, muscle references, joint actions, movement patterns, support/position, stabilisation/balance, foot contact, weight-bearing, impact/landing, propulsion and setup/bracing terms used by the payload;
- structured equipment requirements on every exercise definition and variation;
- explicit movement-demand profiles and review-completeness status on every exercise definition and variation;
- counts for the added equipment/vocabulary records, included in the immutable manifest and exact-byte integrity checks.

The schema is not a production data-authoring shortcut. The 44 legacy equipment labels and 42 exercise rows remain curation candidates; combined/ambiguous labels must be resolved before IDs are issued. A definition cannot be marked reviewed because an old source field, illustration, matching phrase or generated summary exists.

### 3.2 Equipment-definition record

Each equipment definition has:
- stable opaque \`id\`, canonical display name and equipment family ID;
- supported configuration dimensions expressed using controlled-vocabulary IDs;
- source/provenance reference and review status/digest;
- optional reviewed artwork reference (never used as identity evidence).

Configuration dimensions remain orthogonal:
- loading/resistance system (for example selectorised/pin-selected or plate-loaded);
- movement mechanics (for example fixed path, converging or independent/iso-lateral arms);
- physical orientation/body position (for example 45-degree sled, horizontal seated or vertical leg press);
- setup/fit attributes (seat, pad, pivot, handles/attachments, stance).

A loading-system value must not imply a handle path or orientation. Unknown user machine attributes remain unknown; they are not guessed from name, picture or category.

### 3.3 Explicit equipment requirement semantics

Replace the ambiguous v1 flat-list interpretation for v2 with named requirement groups and alternatives:

- **Across groups = AND:** every group must be satisfied.
- **Within a group = OR:** any one complete alternative can satisfy that group.
- **Within one alternative = AND:** every equipment definition and every specified configuration constraint in that alternative must be available.

For example, a single exercise can require either one approved machine configuration or the complete pair of dumbbells plus an adjustable bench. That is an illustration of the rule, not a production exercise mapping.

Every exercise and variation must state one of:
- \`reviewed-required\`: one or more complete groups are present;
- \`reviewed-none\`: there are no external equipment requirements, explicitly reviewed;
- \`incomplete\`: equipment requirement evidence is not sufficient for matching.

An absent field is invalid in v2. It is not equivalent to \`reviewed-none\`. For a variation, requirement inheritance from its parent is allowed only when an explicit reviewed inheritance mode is present. Otherwise the variation supplies its own reviewed requirement profile or remains incomplete.

User custom equipment cannot satisfy a system requirement by substring/name similarity. A user may explicitly associate a physical item with a system equipment definition. Only that explicit association plus user-confirmed required configuration can satisfy a reviewed requirement.

### 3.4 Movement-demand profile for future injury-aware matching

Every exercise definition and variation has an explicit \`movementDemandReviewStatus\` and profile. A complete profile must provide all required coverage arrays, even when a qualified review records an empty array. Missing, null, stale or incomplete data means **unknown**, not “no involvement”.

The profile uses controlled-vocabulary references for:
- primary, secondary and other relevant body-region/muscle involvement;
- joint actions and movement pattern;
- body position, laterality, range and support points;
- stabilisation and balance demands;
- foot contact and foot-pressure demands;
- weight-bearing and impact/landing demands;
- propulsion demands;
- setup/bracing and equipment-configuration constraints.

Do not add unreviewed low/medium/high load scores or a numerical “safe” score. Empty arrays are meaningful only inside a complete, approved profile and only for its explicit review scope.

A definition/variation can be a possible alternative only when its movement profile is complete, current and approved for the relevant review scope. Candidate screening must distinguish:
1. known conflict — reviewed material loading conflict; exclude as an alternative;
2. unknown/incomplete — fail closed; do not suggest it;
3. reviewed candidate — may be offered for user consideration, with a clear warning that the app cannot guarantee suitability or provide medical clearance.

A primary-muscle list alone is insufficient. Direct and secondary involvement plus support, stabilisation, balance, foot pressure, impact, propulsion, weight-bearing, positioning and bracing must be considered. A restriction record is not part of this payload gate; it is a separate C3 data gate.

### 3.5 Review/evidence binding

A production item must not be treated as reviewed merely because a payload contains \`reviewStatus: "approved"\`.

The v2 release must bind each equipment definition, equipment requirement and movement-demand profile to:
- an immutable target digest/version;
- a review-record reference and decision;
- the reviewer's verified scope for the type of content being approved;
- the exact source/evidence set supporting the decision.

Credential proof must be held in the project's approved controlled review record, not exposed as unnecessary personal information in the public catalogue asset. A digest establishes what was reviewed; it does not authenticate a reviewer or prove professional qualification.

No qualified reviewers or review approvals currently exist in the production guide registry. No v2 record may be marked production-approved until the project's qualified-review process has actually produced evidence. The owner's design approval is not content approval.

## 4. Compatibility and storage decisions

### Included after PASS

- Keep IndexedDB at schema v6.
- Keep full personal backup at format V2.
- Materialise exercise definitions and variations through the existing V6 transaction.
- Keep system equipment definitions and controlled vocabularies in the immutable versioned catalogue asset, cached in the existing separate release-specific CacheStorage namespace.
- Expose an API such as \`lookupEquipment(query)\` that loads the exact active release manifest, retrieves the exact cached immutable asset (or re-fetches that exact immutable URL if online), verifies byte length/SHA-256/content type and full v2 schema, then returns equipment definitions. It must not trust an unverified arbitrary cache entry.
- Keep the existing personal \`equipment\` store for user/legacy equipment-access records. No system definition records are written there.
- Preserve the prior active release if the new v2 release fails to stage or validate.
- Keep old v1 release bytes and pins available; do not rewrite v1 manifests or release payloads.

### Backward and rollback behaviour

- A new v2-capable reader must continue to validate/read v1 releases under the existing v1 contract.
- A v1 release does not have structured equipment definitions or reviewed movement-demand profiles. Equipment-definition lookup reports unavailable for that release; injury-aware alternatives fail closed. It must not return an empty equipment catalogue that appears to be a valid reviewed list.
- A client that cannot read v2 must never be directed to a v2 manifest/asset. The shell release and manifest selection must be version-compatible. Do not mutate a v1 asset or reuse a release ID/path for v2 bytes.
- During interrupted fetch, invalid digest/schema/references, CacheStorage read-back failure or loader/activation failure, keep the prior active release usable and keep the candidate unavailable.
- If v2 bytes are missing/corrupt after restore, preserve history and display snapshots. Exact equipment lookup is unavailable until the exact pinned release is recovered; never silently substitute a newer release.

### Explicit exclusions

- No new IndexedDB store, index, schema version or migration.
- No new personal backup format or change to V1/V2 restore semantics.
- No personal equipment-access UI or new typed personal equipment records.
- No persistent training restriction store (C3 is separate).
- No exercise-library/Equipment UI, programme builder or live adaptive alternative engine.
- No production catalogue records or IDs until source curation and qualified review are complete.
- No guide publication, programme-slot assignments or alias approval.
- No remote/CDN catalogue service, cloud sync, digital signatures/publisher authentication, server-side editor or automatic release garbage collection.
- No fuzzy identity matching, source-label rewriting, automatic equipment association or injury safety inference from text/images.

Any newly discovered need for a database/backup change, wider trust boundary, remote delivery or historical rewrite stops C1 and requires a new/revised gate.

## 5. Failure and recovery analysis

| Failure | Required behaviour | Recovery |
|---|---|---|
| v2 asset missing on first/offline install | Catalogue/equipment lookup unavailable; do not show a false empty catalogue | Retry exact immutable release URL when online |
| Wrong digest, byte length or MIME type | Reject before parse/materialisation; current release remains active | Correct as a new release ID/version |
| Unknown equipment or vocabulary ID | Reject entire candidate v2 release; no partial exposure | Correct references and publish a new immutable release |
| Invalid OR/AND requirement structure | Reject candidate; never guess requirement semantics | Correct schema/data and revalidate |
| Missing/incomplete movement profile | Mark candidate not assessed; do not recommend for restricted-area alternatives | Qualified review and new release |
| Reviewer approval missing/stale/wrong scope | Reject publication or mark affected record unavailable | Complete new exact-digest review |
| Cache staging/read-back interrupted | Candidate remains inactive | Retry exact immutable asset; prior release remains usable |
| Loader activation failure | Do not switch active release | Retry after verifying active pointer and candidate cache |
| New shell not v2-capable | Do not select v2 manifest for that client | Update shell/reader first, then select compatible v2 release |
| Restored backup references older v1 release whose asset is absent | History remains readable from snapshots; v1 equipment lookup stays unavailable | Recover exact old asset if available; never rebind to latest |
| Corrupt v2 cache after successful install | Do not return unverified equipment data | Re-fetch/re-verify exact immutable URL; otherwise unavailable |

No cross-store transaction is required for equipment definitions because they remain in the verified asset bytes. The existing exercise-definition materialisation and active pointer still commit atomically through the established V6 transaction.

## 6. Acceptance evidence required before C1 implementation can close

### Payload and compatibility

- v1 fixtures continue to validate and remain readable without being rewritten;
- v2 manifest/payload identity, exact-byte SHA-256, byte length, content type and every declared count validate;
- equipment-definition, exercise-definition and variation IDs are unique, including cross-type collision checks;
- every configuration, vocabulary, equipment requirement and variation reference resolves within the same release;
- malformed groups, unsupported vocabulary IDs, incomplete required fields and stale/missing review references reject before activation;
- reviewed-none and incomplete are separate states; absent fields never default to no equipment/no loading.

### Offline/cache/release lifecycle

- real CacheStorage retains catalogue releases through shell cache activation/cleanup;
- new public equipment lookup reads only the exact active, verified release bytes;
- equipment lookup works offline after successful v2 installation;
- equipment lookup reports unavailable on v1 releases or absent/corrupt/unverified v2 asset;
- failure injection for wrong digest, invalid references, interrupted stage, cache read-back and activation failure leaves the previous release active;
- v2-capable shell never selects v2 for an old reader; v1 compatibility is tested;
- no IndexedDB version/store/index or V1/V2 backup behaviour changes.

### Injury metadata contract

- every exercise and variation has explicit complete/incomplete review state;
- a complete profile contains all required coverage arrays and evidence/review bindings;
- unknown or incomplete metadata produces no injury-aware candidate;
- known conflict is excluded;
- a reviewed candidate is only a candidate, never a safety guarantee or medical clearance;
- no automated test or generated copy is treated as qualified human movement review.

Passing source-contract tests alone does not prove v2 runtime, real production content or qualified human review.
