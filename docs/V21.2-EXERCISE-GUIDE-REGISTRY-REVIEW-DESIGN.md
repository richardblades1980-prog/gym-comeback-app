# V21.2 exercise guide registry and review workflow — design contract

**Status:** Design-only checkpoint. No runtime registry, guide records, slot assignments, reviews or publication have been created.
**Branch basis:** `V21.2-development` HEAD `7458cf67c50711b19cb13b9fd2f5f5d182d03f34`.
**Scope:** Define safe, explicit assignment and human review contracts for exercise guides.
**Non-goals:** No guide authoring/approval, canonical exercise identity changes, catalogue changes, DB/backup changes, UI changes, asset/cache changes, merge or deployment.

## 1. Core separation

Keep three distinct data concepts:

1. **Guide content/version** — reviewed instructions for a specific exercise definition/variation and relevant equipment/configuration.
2. **Review record** — human decision bound to one exact guide version/content digest.
3. **Programme-slot assignment** — explicit permission to show a specific approved guide version in a specific programme slot.

A guide record does not automatically apply to a programme slot. A programme slot does not establish canonical exercise identity. Display-name similarity is never a matching mechanism.

## 2. Stable identifiers and versioning

- Programme slot IDs from the source-preserved base programme are the assignment key; repeated labels across days remain distinct.
- Guide IDs and version numbers are explicit and stable. Published versions are immutable.
- Content edits, asset changes, equipment/setup changes, steps/cues/safety edits, or variation changes create a new guide version and invalidate approval for the new version until it is reviewed.
- Assignment records bind to a guide ID **and exact version**, not a floating “latest” version.
- Source programme snapshot/provenance is retained in the assignment to detect assignment against an unexpected programme source.
- No aliases, exercise definition IDs or variation IDs are created by this workflow; identity curation remains a separate gate.

## 3. Proposed logical contracts (illustrative, not runtime code)

### Guide version
Required fields:
- `guideId`, `version`, `status` (`draft`, `in-review`, `approved`, `rejected`, `withdrawn`)
- `title`, `setup`, ordered `steps`, `cues`, `safetyNotes`
- Explicit target exercise identity/variation scope (reviewed reference, not inferred from title)
- Relevant equipment/configuration scope, including whether Gym/Home context affects instructions
- Explicit local `assetIds` resolving through the immutable verified manifest
- `contentDigest` computed over canonical review-relevant content and asset references
- `createdAt`, `updatedAt`, source/provenance and draft authoring notes as appropriate

Required content is validated independently of status. Draft or in-review content must never be rendered as complete production instruction.

### Review record
Required fields:
- Unique `reviewRecordId`
- `guideId` and exact `guideVersion`
- Reviewed `contentDigest`
- Reviewer identity/role (recorded in the project’s approved review format; never invented)
- Review timestamp
- Decision: approve, reject, or request changes
- Scope/outcome and notes, including unresolved limitations

An approval is valid only when it matches the current guide ID, version and digest. A review for a prior version cannot approve edited content. Reviewer qualification requirements must be decided by the project owner before accepting clinical/safety-sensitive instructions; the system must not assume qualifications.

### Programme-slot assignment
Required fields:
- Exact `programmeSlotId`
- Source programme snapshot ID
- Exact `guideId` + `guideVersion`
- Assignment status (draft/reviewed/approved/withdrawn)
- Assignment review record and digest
- Explicit compatibility scope/limitations where applicable

Only approved assignments with valid guide-version approval may resolve to complete at runtime. The registry starts empty.

## 4. Review and publication lifecycle

Draft → In review → (Approved | Rejected | Changes requested) → revised draft/new version.

- Review is a human decision, not a test-generated status.
- Approval binds to the exact digest and version.
- Approved versions are immutable; corrections create a new version.
- Assignment approval is separate from guide-content approval and also digest/version-bound.
- Withdrawal/revocation makes the assignment unavailable without silently selecting another guide.
- No workflow step auto-approves, auto-maps, or publishes guide copy.

## 5. Variation, inheritance and equipment rules

- Exact reviewed exercise/variation scope is required.
- A variation must not inherit movement instructions, setup, safety notes, or equipment geometry merely because it has a common parent/name.
- Shared sections may be inherited only through explicit reviewed section-level inheritance metadata, tied to the exact parent version/digest and reviewed for the target variation. Otherwise use a self-contained guide.
- Equipment/context differences must be represented explicitly and tested; no assumed Gym/Home interchangeability.
- Similar names, source descriptions, muscle keys, artwork matches or fuzzy scores are not evidence of identity or guide suitability.

## 6. Substitution boundary

Manual substitution metadata in a performed workout is not an approved guide assignment. A substituted exercise must resolve to its own explicitly reviewed guide or show unavailable/incomplete. The original programme-slot guide must not be shown as instructions for a substituted exercise unless a separate explicit compatibility assignment has been reviewed and approved.

Substitution selection must not change source slot identity, set values, recording mode, progression focus, target or rest settings.

## 7. Fail-closed validation

Reject a registry/assignment if any of the following apply:
- Unknown or missing slot, guide, version or programme snapshot ID.
- Duplicate/conflicting active assignment for one slot.
- Guide version is draft, in-review, rejected, withdrawn or missing.
- Review is absent, invalid, or binds to a different version/digest.
- Content digest does not match canonical guide content.
- Required content is absent/invalid.
- Asset ID is absent from the verified local manifest or its integrity contract fails.
- Exercise/variation/equipment scope is ambiguous or incompatible.
- Inheritance is implicit, unreviewed, circular or bound to a changed parent.
- Assignment approval is absent or digest/version-mismatched.
- The performed exercise is a substitution without an explicitly approved applicable mapping.

Failure must produce `incomplete` or `unavailable`, never guessed content or a fallback guide from a similar exercise.

## 8. Required test contract before implementation

Unit/contract tests must cover:
- Empty registry is valid and resolves all slots unavailable.
- Exact slot IDs resolve; display-name matching is not used.
- Duplicate active assignments are rejected.
- Unknown slots/guides/versions and stale source snapshots are rejected.
- Approved guide version without matching review digest is rejected.
- Editing content/assets after approval invalidates approval.
- Prior-version review cannot approve a new version.
- Draft/rejected/withdrawn guide and assignment states cannot publish.
- Required fields and verified manifest assets are enforced.
- Explicitly reviewed variation scope works; unapproved inheritance fails.
- Equipment/context mismatch fails closed.
- Manual substitutions do not inherit original slot guide.
- Revoked assignment resolves unavailable.
- Registry validation is deterministic and does not mutate programme slots or workout/history records.

Browser/offline tests must then prove approved guide rendering uses only the exact registry assignment, and all failure states preserve workout controls and recorded data.

## 10. Safety boundary

This is a technical workflow design, not exercise/medical content approval. The existing 27 drafts and 25 descriptions remain unpublished and unmapped. Do not alter the protected root app, database/backup/history, catalogue, programme source, guide artwork/cache, `main`, or deployment under this gate.


## 10. G3.7.2b implementation boundary

The pure validation module is not wired to production rendering. It accepts the registry, current source programme slots/snapshot, verified asset-ID set and injected digest verifier. It validates explicit guide versions, review records, assignments, source provenance, scope and asset references. A registry error downgrades complete resolutions to `incomplete`; unassigned or withdrawn slots resolve `unavailable`.

It does not compute SHA-256 or create review approvals. Test digests are deterministic placeholders, not cryptographic hashes. Production digest implementation, runtime integration, review tooling, registry population and rendering remain separate gates. Inheritance is rejected by this version.

## 11. G3.7.2c cryptographic integrity design

See `docs/V21.2-EXERCISE-GUIDE-CRYPTO-INTEGRITY-DESIGN.md`. Production digests use strict canonical schema payloads, Web Crypto SHA-256, domain separation and explicit field contracts. Asset binding includes exact manifest and asset tuples. Guide content, assignment and review digests are distinct. Because Web Crypto is async, registry validation/resolution must be async. Missing crypto fails closed. Digests do not authenticate reviewers. This gate is docs-only; no registry or approvals.
