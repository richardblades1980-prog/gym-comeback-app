## 1. Purpose and threat boundary

The G3.7.2b validator accepts an injected digest verifier; its unit fixtures use deterministic placeholder digests. Production validation must use Web Crypto SHA-256 and must never silently fall back to a weaker digest or report complete when cryptography is unavailable.

Client-side hashes provide integrity/corruption and binding checks, **not reviewer authentication**. A person with write access to local records can replace content and digests. Review metadata remains traceability data unless a later server/authenticated signing gate is added.

## 2. Canonical representation

Do not use the existing `stableJson` as a cryptographic canonical format. Define a versioned, strict canonical representation:
- Schema-specific allowlists for each digest input; unknown fields are rejected or explicitly excluded by schema.
- Deterministic canonical JSON compatible with a documented standard (recommend RFC 8785/JCS), then UTF-8 encoding.
- Reject unsupported values, non-finite numbers, invalid shapes, and ambiguous/missing required fields.
- Keep canonicalisation version in the digest domain and record schema.
- Verify vectors for key ordering, Unicode, arrays, numeric edge cases and rejected values.

## 3. SHA-256 and domain separation

Use platform `crypto.subtle.digest("SHA-256", bytes)` async API. Output encoding: lowercase hex with fixed `sha256:` prefix.

Digest inputs are domain-separated, with explicit versioned prefixes:
- `PC-GUIDE-CONTENT-v1\0`
- `PC-GUIDE-ASSET-SET-v1\0`
- `PC-GUIDE-ASSIGNMENT-v1\0`
- `PC-GUIDE-REVIEW-v1\0`

Digest helper fails closed if Web Crypto is absent, rejects unsupported input, and does not use a custom JS SHA implementation or weaker fallback. HTTPS/secure-context availability is an environment requirement; tests must exercise unavailable-crypto failure.

## 4. Digest payload contracts

### Guide content digest
Bind immutable review-relevant fields: guide ID/version, title, setup, ordered steps, cues, safety notes, explicit exercise/variation/equipment/context scope, and asset references. Exclude mutable lifecycle state, review status, timestamps, reviewer notes or publication metadata. Content edits or changed asset binding require a new version and fresh review.

### Asset-set digest
Bind manifest schema/version/identity and exact referenced asset tuples: asset ID, path, MIME type, byte length and SHA-256. Existing guide artwork manifest has per-asset SHA-256/byte-length fields; service worker verifies downloaded bytes before cache publication. Guide content binds exact asset set and verified manifest release, not merely asset IDs. Manifest verification remains fail-closed.

### Assignment digest
Bind exact programme slot ID, source programme snapshot ID/digest, exact guide ID/version/content digest, explicit compatibility scope and any substitution identity/scope. No display-name/fuzzy matching. Lifecycle status and review events are outside immutable payload; changing target/scope requires a new assignment and review.

### Review record digest
Bind review target type/ID/version, exact target digest, decision, reviewer identifier/role metadata, timestamp and review notes/outcome as required by schema. A review digest detects inconsistency but does not authenticate the reviewer. Do not invent reviewer identity or qualifications.

## 5. Async API boundary

Web Crypto is asynchronous; G3.7.2b validation is synchronous. Production API should be async (e.g. `verifyDigest`, `validateRegistryAsync`, `resolveAssignmentAsync`) and propagate failures explicitly. Never convert a rejected digest promise into a pass. Registry errors or unavailable crypto prevent complete resolution.

## 6. Lifecycle and immutability

- Published guide versions and approved assignments are immutable.
- Content/scope/asset changes create a new guide version and fresh review.
- Withdrawal/revocation is a separate lifecycle event and makes the target unavailable; it does not rewrite the reviewed content digest.
- Review/assignment lifecycle events should be auditable. Local append-only conventions cannot prevent local-storage tampering; no authenticity claim is made.
- No automatic approvals. Tests must never create human approval records as production data.

## 7. Required tests before implementation acceptance

Canonicalisation vectors and invalid-input rejection; SHA-256 known vectors and domain-separation tests; output encoding/prefix and mismatch; crypto unavailable/rejected promise fails closed; included fields invalidate digest and excluded lifecycle metadata does not; asset tuple/manifest changes invalidate binding; target/version cross-binding failures; async validation determinism, rejection propagation and non-mutation; source/offline parity and browser/offline tests; empty production registry remains empty and all slots unavailable.

## 8. Sequencing / scope

G3.7.2c is design only. Next gates: (1) strict canonicalisation and SHA-256 helpers with vectors; (2) async digest contracts for guide, asset set, assignment and review; (3) async pure registry validation tests; (4) runtime resolver integration in a separate gate; (5) human review and registry population remain separate approval gates.

No DB/schema/store/index, backup/history, catalogue/identity, programme source, artwork/cache, UI, protected root app, merge or deployment changes.
